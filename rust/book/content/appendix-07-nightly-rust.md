## 附录 G - Rust 的构建过程与“Nightly Rust”版本

本附录介绍了 Rust 的构建方式及其对您作为 Rust 开发者的影响。

### 稳定性而不停滞

作为一种语言，Rust 非常注重代码的稳定性。我们希望 Rust 成为一个稳固的基础，供您在此基础上进行开发；如果一切不断变化，那就不可能实现这一点。同时，如果我们无法尝试新功能，可能直到功能发布后才会发现重要的缺陷，而那时也无法再修改了。

我们解决这一问题的方案就是所谓的“稳定性而不停滞”，我们的指导原则是：您永远不必担心升级到新的稳定版 Rust。每次升级都应该是无痛苦的，但也应带来新功能、更少的错误以及更快的编译时间。

### 选择！发布通道与搭乘列车

Rust 的开发工作遵循“列车调度”模式。也就是说，所有开发都在 Rust 仓库的主分支中进行。发布则采用软件发布列车模型，这种模型被 Cisco IOS 和其他软件项目所使用。Rust 有三个发布通道：

- Nightly - Beta - Stable

大多数 Rust 开发者主要使用稳定通道，但那些想尝试实验性新功能的人可以使用 nightly 或 beta 通道。

以下是开发和发布过程的一个示例：假设 Rust 团队正在准备 Rust 1.5 的发布。该版本于 2015 年 12 月发布，但这会给出合理的版本号。新的功能被添加到 Rust 中：一个新提交进入主分支。每晚都会生成一个新的 nightly 版本。每天都是发布日，这些发布由我们的发布基础设施自动创建。因此，随着时间的推移，我们的发布每晚都呈现如下样子：

```text
nightly: * - - * - - *
```

每六周就是准备新发布的时刻！Rust 仓库的 `beta` 分支从用于 nightly 的主分支分离出来。现在有两个发布：

```text
nightly: * - - * - - *
                     |
beta:                *
```

大多数 Rust 用户不会积极使用测试版，但会在 CI 系统中对测试版进行测试，以帮助 Rust 发现可能的缺陷。与此同时，每晚都会有一个夜间版本发布：

```text
nightly: * - - * - - * - - * - - *
                     |
beta:                *
```

假设发现了缺陷。好在我们在缺陷进入稳定版本之前有时间测试测试版！修复方案被应用到主分支，因此夜间版本得到了修正，然后该修复方案又被回退到 `beta` 分支，并生成一个新的测试版：

```text
nightly: * - - * - - * - - * - - * - - *
                     |
beta:                * - - - - - - - - *
```

在第一个测试版创建六周后，就是稳定版本的发布时间了！`stable` 分支是从 `beta` 分支生成的：

```text
nightly: * - - * - - * - - * - - * - - * - * - *
                     |
beta:                * - - - - - - - - *
                                       |
stable:                                *
```

太好了！Rust 1.5 已经完成！然而，我们忘记了一件事：因为六周已经过去了，我们还需要一个 _下一个_ 版本 Rust 的测试版，即 1.6。因此，`stable` 分支从 `beta` 分支分离后，`beta` 分支又从 `nightly` 分支分离出来：

```text
nightly: * - - * - - * - - * - - * - - * - * - *
                     |                         |
beta:                * - - - - - - - - *       *
                                       |
stable:                                *
```

这被称为“火车模型”，因为每六周就会有一个版本“离开车站”，但在成为稳定版本之前仍需通过测试版通道进行传播。

Rust 以每六周为周期发布，非常规律。如果你知道某个 Rust 版本的发布日期，就可以知道下一个版本的发布日期：即六周后。每六周发布的一个优点是，下一列火车即将到来。如果某个功能错过了某个特定版本，不必担心：很快会有另一个版本发布！这有助于减少在发布截止日期前偷偷加入可能不完善的功能的压力。

通过这一过程，你可以随时查看下一个 Rust 构建版本，并亲自确认升级是否容易：如果测试版没有按预期工作，你可以向团队报告并在下一次稳定版本发布之前得到修复！测试版中的损坏情况相对罕见，但 `rustc` 仍然是一段软件，因此确实存在错误。

### 维护时间

Rust 项目支持最新的稳定版本。当新的稳定版本发布时，旧版本就会达到其生命周期结束点（EOL）。这意味着每个版本仅得到六周的支持。

### 不稳定的功能

这次发布模式还有一个问题：不稳定功能。Rust 使用一种称为“特性标志”的技术来决定在特定版本中启用的功能有哪些。如果某个新功能正在积极开发中，它就会进入主分支，从而出现在 nightly 版本中，但受到 _特性标志_ 的约束。作为用户，如果您想尝试正在开发中的功能，可以这样做，但您必须使用 nightly 版本的 Rust，并在源代码中添加相应的标志以启用该功能。

如果您使用的是 beta 或稳定版 Rust，则无法使用任何特性标志。这是允许我们在新功能永久成为稳定版本之前进行实际使用的关键。希望体验最新功能的用户可以这么做，而希望获得稳定体验的用户则可以坚持使用稳定版本，因为他们的代码不会出错。稳定性与不停滞并存。

本书仅包含关于稳定功能的信息，正在开发中的功能仍在变化，而且从本书撰写时到它们在稳定构建中启用时肯定会有差异。您可以在网上找到仅适用于 nightly 版本的文档。

### Rustup 与 Rust Nightly 的作用

Rustup 使得在全局或项目级别之间轻松切换不同版本的 Rust 变得容易。默认情况下，您会安装稳定版 Rust。例如，要安装 nightly 版本：

```console
$ rustup toolchain install nightly
```

您也可以通过 `rustup` 查看所有已安装的 _工具链_（Rust 版本及相关组件）。以下是某作者 Windows 电脑上的示例：

```powershell
> rustup toolchain list
stable-x86_64-pc-windows-msvc (default)
beta-x86_64-pc-windows-msvc
nightly-x86_64-pc-windows-msvc
```

如您所见，默认使用的是稳定工具链。大多数 Rust 用户大部分时间都使用稳定版本。您可能希望大部分时间都使用稳定版本，但在特定项目中使用 nightly 版本，因为您关注前沿功能。为此，可以在该项目的目录中运行 `rustup override` 命令，将 nightly 工具链设置为在该目录中时 `rustup` 应使用的工具链：

```console
$ cd ~/projects/needs-nightly
$ rustup override set nightly
```

现在，每当你在 _~/projects/needs-nightly_ 目录下调用 `rustc` 或 `cargo` 时，`rustup` 会确保你使用的是 nightly 版本的 Rust，而不是默认的稳定版 Rust。当你拥有许多 Rust 项目时，这一点非常实用！

### RFC 流程与团队

那么如何了解这些新功能呢？Rust 的开发模式遵循 _请求评论 (RFC) 流程_。如果你希望改进 Rust，可以撰写提案，称为 RFC。

任何人都可以撰写 RFC 来改进 Rust，这些提案会被 Rust 团队审查并讨论，该团队由多个主题子团队组成。在 [Rust 网站](https://www.rust-lang.org/governance) 上有一份完整的团队列表，其中包括项目各个领域的团队：语言设计、编译器实现、基础设施、文档等。相应的团队会阅读提案和评论，提出自己的意见，最终通过共识决定是接受还是拒绝该功能。

如果该功能被接受，会在 Rust 仓库中打开一个问题，有人可以实施它。实施得很好的人可能并非最初提出该功能的那个人！当实现完成后，它会通过特性门进入主分支，正如我们在 “[“不稳定功能”](#unstable-features)<!-- ignore --> 部分所讨论的。

一段时间后，一旦使用 nightly 版本的 Rust 开发者能够尝试新功能，团队成员会讨论该功能在 nightly 版本中的表现，并决定是否将其纳入稳定版 Rust。如果决定继续推进，特性门将被移除，该功能现在被视为稳定版本！它将随着新的稳定版 Rust 发布而正式加入。
