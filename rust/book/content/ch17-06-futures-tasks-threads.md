## 综合应用：Future、任务与线程

正如我们在[第16章][ch16]<!-- ignore -->中看到的那样，线程提供了一种并发实现方式。在本章中，我们看到了另一种方法：使用 异步 和 Future 以及流。如果你在考虑何时选择其中一种方法而非另一种，答案是：视情况而定！在许多情况下，选择不是线程 _或_ 异步，而是线程 _与_ 异步 的结合。

许多操作系统几十年来一直提供基于线程的并发模型，因此许多编程语言也支持这些模型。然而，这些模型并非没有缺点。在许多操作系统中，每个线程会占用大量内存。此外，只有当你的操作系统和硬件支持时，才可以使用线程。与主流桌面和移动计算机不同，一些嵌入式系统根本没有操作系统，因此也不具备线程。

异步 模型提供了一套不同的——且最终是互补的——权衡方案。在 异步 模型中，并发操作不需要独立的线程。相反，它们可以在任务上运行，就像我们在流部分使用 `trpl::spawn_task` 从同步函数启动工作一样。任务类似于线程，但它不是由操作系统管理，而是由库级代码：运行时来管理。

创建线程和创建任务的函数接口如此相似是有原因的。线程作为一组同步操作的边界；并发可以在线程之间实现。任务则作为一组异步操作的边界；并发既可以在任务之间也可以在任务内部实现，因为任务可以在其体内切换 Future。最后，Future 是 Rust 最细粒度的并发单位，每个 Future 可能代表一棵树的其他 Future。运行时——特别是其执行器——管理任务，而任务又管理 Future。在这方面，任务类似于由运行时管理的轻量级线程，但具有来自运行时管理的额外功能。

这并不意味着异步任务总是优于线程（或反之）。与线程进行并发处理在某些方面是一种更简单的编程模型，而使用 `async` 则不然。这既可能是优势，也可能是劣势。线程具有“即发即忘”的特性；它们没有类似于未来的原生等价物，因此只能运行到完成，不会被操作系统本身中断。

事实证明，线程和任务通常可以很好地协同工作，因为至少在某些运行时中，任务可以被移动到不同线程之间。实际上，我们使用的运行时——包括 `spawn_blocking` 和 `spawn_task` 函数——默认就是多线程的！许多运行时采用一种称为“工作窃取”的方法，根据线程当前的使用情况透明地将任务移动至其他线程，从而提升系统的整体性能。这种方法实际上需要线程、任务以及未来（futures）。

在决定使用哪种方法时，可以参考以下经验法则：

- 如果工作可以非常并行处理（即 CPU 密集型），例如处理大量数据且每个部分可以独立处理，那么选择线程更为合适。
- 如果工作是高度并发的（即 I/O 密集型），例如处理来自不同来源的消息，这些消息可能以不同的间隔或速率到达，那么使用异步方式更为合适。

如果你既需要并行性又需要并发性，不必在线程和异步之间做出选择。你可以自由地同时使用它们，让每种机制发挥其最佳作用。例如，列表 17-25 展示了现实世界 Rust 代码中这种混合方式的常见例子。
