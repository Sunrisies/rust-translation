# Roadmap 2021

# Summary

此路线图概述了 2021 年 Clippy 的规划：

- 提升可用性与可靠性 - 改善贡献者和维护者的体验 - 开发并明确流程

Clippy 团队成员将从以下一个或多个主题中分配任务。团队成员负责完成所分配的任务，这可以通过实现这些任务或指导感兴趣的贡献者来完成。

# Motivation

随着 Rust 语言及整个生态系统的不断发展，Clippy 的用户和贡献者也越来越多。这对项目有利，但也带来了挑战。其中一些挑战包括：

- 出现更多关于可靠性或可用性的问题 - 小型团队难以处理大量流量 - 由于流程缺失和/或团队成员时间不足，较大的项目无法完成

此外，根据 [Rust Roadmap 2021]，每个团队应定义明确的流程，并在不同团队之间实现统一。此路线图是迈向这一目标的第一步。


# Explanation

本部分将说明 2021 年应完成的任务。需要注意的是，本文档重点在于“做什么”，而非“如何做”。具体方法将在后续跟踪问题中由指定团队成员处理。

内容分为两个主要部分。第一部分涵盖面向用户的计划，第二部分涵盖内部计划。

## 面向用户

Clippy 应尽可能易于使用和配置。本部分涵盖了为改善 Clippy 状况而需实施的计划。

### Usability

接下来将介绍提升可用性的计划。

#### `cargo check` 后无输出

目前，当在 `cargo check` 之后运行 `cargo clippy` 时，不会产生任何输出。这尤其令人困扰，因为 `rust-analyzer` 正在逐渐普及，而它使用 `cargo check` 来检查代码。虽然已经实现了修复方案，但仍需将其推广到更广泛的场景。这还包括稳定化 `cargo clippy --fix` 命令，或支持在 `rustfix` 中处理多段建议。

- [#4612](https://github.com/rust-lang/rust-Clippy/issues/4612)

#### `lints.toml` 配置

这是一个偶尔会出现的问题：需要一个可复用的配置文件，用于定义检查级别。关于此问题的讨论通常没有具体结果，或者只是说“我们需要为此制定 RFC”。而这正是需要做的事情。与 cargo 团队合作，制定一个 RFC，并在某个地方实现这样的配置文件。

- [#3164](https://github.com/rust-lang/rust-Clippy/issues/3164) - [cargo#5034](https://github.com/rust-lang/cargo/issues/5034) - [IRLO](https://internals.rust-lang.org/t/proposal-cargo-lint-configuration/9135/8)

#### 检查组

关于在 Clippy 中管理检查的问题越来越多。实现检查时很难保证没有或只有少量误报（FPs）。一种解决方式可能是引入更多的检查组，使用户能够更好地管理检查，或者改进检查分类的过程，从而减少因误报而禁用检查的情况。需要注意的是，Clippy 的检查不如 `rustc` 的检查保守，后者在未来不会改变。

- [#5537](https://github.com/rust-lang/rust-Clippy/issues/5537) - [#6366](https://github.com/rust-lang/rust-Clippy/issues/6366)

### Reliability

接下来将介绍提高可靠性的计划。

#### 误报率

在最糟糕的情况下，新的检查器仅在夜间版本中提供2周时间，之后才会进入测试版并最终成为稳定版本。如今夜间版本的 Rust 使用人数较少，因此拥有大量错误报告的检查器更有可能成为稳定版本。这会导致用户感到烦恼，在最好的情况下他们会禁用这些新检查器；在最糟糕的情况下则会让更多用户不再使用 Clippy。应该制定并实施相关流程来防止这种情况发生。

- [#6429](https://github.com/rust-lang/rust-Clippy/issues/6429)

## Internal

2020年底表明，Clippy 需要考虑可用资源，尤其是在项目管理和维护方面。本节将讨论影响团队成员和贡献者的问题。

### Management

2020年，Clippy 有超过1000个公开问题，且平均有25-35个开放 PR。这既是优势也是劣势。更多的问题和 PR意味着更多人对 Clippy 感兴趣并愿意贡献代码。另一方面，这意味着团队成员需要承担更多工作，贡献者则需要更长的审查等待时间。以下将描述改善团队成员和贡献者状况的计划。

#### 为团队成员明确期望

根据[2021年 Rust 路线图](https://github.com/rust-lang/rust-Clippy/issues/6429)文档，应制定关于成为团队成员意味着什么的说明。这不应给团队成员带来更多压力，而应帮助他们和感兴趣的人了解期望是什么。通过此文件，招募新成员也会更加容易，并可能鼓励有兴趣的人联系我们以加入。

#### 扩大团队规模

人员增多意味着每个人需要承担的工作减少。除了关于团队成员期望的文档外，还应制定一份关于如何加入团队的流程说明文档。这还可以提高团队的稳定性，以防现有成员暂时退出。团队中也可能存在不同的角色，例如分类人员与审查人员。

#### 定期会议

其他团队都有定期会议。Clippy的规模足够大，进行这些会议可能也是值得的。尤其是当更多人员加入团队时，这对于协调一致非常重要。除了异步通信适用于处理不同的lint时，会议则提供了在已知时间进行的同步交流方式。如果需要讨论较大的问题（如此路线图中的项目），这种方式尤其有用。首先，在Rust同步之前每两周举行一次会议可能较为合适。

#### Triaging

为了应对大量开放问题的涌入，应制定一个问题与PR分类流程。官方上，Clippy遵循Rust的分类流程，但目前没有人执行这一流程。通过跨项目共享分类团队或实施简化分类的仪表板/工具可以改进这一点。

### Development

提升开发者和贡献者的体验是Clippy团队定期致力于做的事情。不过，有些事项可能需要特别的关注和规划。这些主题列在下面。

#### 新lint与现有lint的流程

如上所述，对新lint进行分类非常困难，因为有问题的lint进入稳定版本的概率很高。应制定一种分类lint的流程。此外，应开发测试系统来识别现实世界代码中哪些lint目前存在问题，以便修复或禁用它们。

- [#6429 (评论)](https://github.com/rust-lang/rust-Clippy/issues/6429#issuecomment-741056379) - [#6429 (评论)](https://github.com/rust-lang/rust-Clippy/issues/6429#issuecomment-741153345)

#### Processes

与前述点相关，应实施一个建议和讨论重大变更的流程。此外，还不清楚何时默认启用或禁用lint。上述测试系统也可以改善这一点。

#### 开发工具

已经存在`cargo dev`这一工具，它使Clippy的开发更加便捷愉快。这还可以进一步扩展，以涵盖更多开发流程领域。

- [#5394](https://github.com/rust-lang/rust-Clippy/issues/5394)

#### 贡献者指南

类似于描述如何使用 Clippy 的《Clippy Book》，一本关于如何为 Clippy 做贡献的书可能对新成员和现有贡献者都有帮助。在 Clippy 仓库中已经存在 `doc` 目录，这可以被转化为一个 `mdbook`。

#### `rustc` 集成

最近，Clippy 通过 `git subtree` 被集成到 `rust-lang/rust` 仓库中。这使得两个仓库之间的同步变得更加容易。仍然可以改进的事项列表如下：

1. 使用与 `rustc` 相同的 `rustfmt` 版本和配置。2. 让 `cargo dev` 在 Rust 仓库中正常工作，就像在 Clippy 仓库中一样。例如：`cargo dev bless` 或 `cargo dev update_lints`。甚至可以添加更多可能对 Rust 仓库有用的功能，如 `cargo dev deprecate`。3. 更简单的同步过程。`subtree` 方式并不理想。

## Prioritization

对于 Clippy 用户来说，最紧迫的问题当然是用户面临的问题。因此应该优先处理这些问题，但不应忽视本文档中列出的内部问题。

控制默认警告和拒绝 lint 的 FP 率应该是最高优先级。其他用户面临的问题也应得到高优先级，但不应妨碍解决内部问题的进程。

为了更好地管理即将到来的项目，应尽快建立基本的内部流程，如会议、问题跟踪和文档编写。对于涉及用户面临的问题，这些流程可能也是正确管理项目的必要条件。

# 现有技术

## Rust 路线图

Rust 的路线图机制由 [RFC 1728] 在 2016 年确立。自那时起，每年都会发布一份路线图，明确未来几年的主要计划。今年的路线图可以在 [这里][Rust Roadmap 2021] 找到。


# Drawbacks

## 大型路线图

这个路线图非常庞大，本文档中列出的所有项目并不都在 2021 年得到解决。由于这是 Clippy 的首次路线图，在 2021 年底保留开放任务是可以的，但在 2022 年的路线图中应重新评估这些任务。
