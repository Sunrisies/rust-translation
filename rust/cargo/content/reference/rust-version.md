# Rust 版本

`rust-version` 字段是一个可选键，用于告诉 Cargo 你的包所支持的 Rust 工具链版本。

```toml
[package]
# ...
rust-version = "1.56"
```

Rust 版本必须是一个包含至少一个部分的纯版本号；它不能包含 semver 运算符或预发布标识符。在检查 Rust 版本时，编译器预发布标识符如 -nightly 将被忽略。

> **MSRV:** 从 1.56 开始受尊重

## 使用场景

**Diagnostics:**

当你的包在不受支持的工具链上编译时，Cargo 会向用户报告此问题作为错误。这明确了支持预期，并避免了像标准库中的无效语法或缺失功能这样的间接诊断信息。这影响包中的所有 [Cargo targets](cargo-targets.md)，包括二进制文件、示例、测试套件、基准测试等。用户可以使用 `--ignore-rust-version` 标志选择不受支持的包构建方式。


**开发辅助工具:**

`cargo add` 会自动选择依赖项的版本要求，使其与你的 `rust-version` 兼容的最新版本。如果不是最新版本，`cargo add` 会通知用户，以便他们决定是保留当前版本还是更新 `rust-version`。

[解析器](resolver.md#rust-version)在选择依赖项时可能会考虑 Rust 版本。

其他工具也可能利用这一点，例如 `cargo clippy` 的 [`incompatible_msrv` lint](https://rust-lang.github.io/rust-clippy/stable/index.html#incompatible_msrv)。

> [!NOTE]
> 可以使用 `--ignore-rust-version` 选项忽略 `rust-version`。

## 支持预期

这些是一般预期；某些包可能会说明它们不遵循这些预期。

**Complete:**

所有功能，包括二进制文件和 API，都在每个 [特性](features.md) 支持的 Rust 版本上可用。

**Verified:**

包的功能在其支持的 Rust 版本上经过验证，包括自动化测试。请参阅我们的 [Rust 版本 CI 指南](../guide/continuous-integration.md#verifying-rust-version)。

**Patchable:**

如果许可证允许，用户可以通过克隆你的包来[覆盖本地依赖](overriding-dependencies.md)。在这种情况下，Cargo可能会加载整个工作空间中的补丁依赖项，该依赖项在支持的 Rust 版本上应该能够正常工作，即使工作空间中的其他包具有不同的支持版本。

**依赖项支持：**

为了支持上述情况，预计每个依赖项的版本要求至少支持一个与你的 `rust-version` 兼容的版本。然而，**不**期望依赖项规范排除与你的 `rust-version` 不兼容的版本。实际上，同时支持这两种情况可以让你平衡那些支持旧版 Rust 版本的用户的需求与不支持这些版本的用户的需求。

## 设置和更新 Rust 版本

支持哪些 Rust 版本是一个权衡问题——对于维护者来说，不使用 Rust 工具链或其依赖项的新功能会带来成本；对于从 polyfill 迁移到标准库中的新功能从而缩短构建时间的用户来说，使用这些新功能的包也会带来成本；对于支持旧版 Rust 版本的用户来说，则涉及包的可用性。

> [!NOTE]
> [更改 `rust-version`](semver.md#env-new-rust)通常被视为一种轻微的不兼容问题。

> [!TIP]
> 选择支持哪些 Rust 版本以及何时变更该政策，以便用户能够将其与自己的政策进行比较；如果不符合预期，则可以决定是否接受失去一般改进或面临无法修复的阻塞错误的风险。
>
> 最简单的支持策略是始终使用最新的 Rust 版本。
>
> 根据你的风险承受能力，下一个最简单的做法就是继续支持支持旧版 Rust 版本的你包的旧主要或次要版本。

### 选择支持的 Rust 版本

您的包的用户通常会关注他们的支持 Rust 版本，以： - 他们的 Rust 工具链供应商的支持政策，例如 Rust Project 或某个 Linux 发行版 - 注意：Rust Project 仅提供最新版本的漏洞修复和安全更新。 - 用户重新验证其包的新工具链的固定时间表，例如每年首次发布时，每 5 次发布后一次。

此外，用户不太可能立即使用新的 Rust 版本，但他们需要时间注意到并重新验证，或者可能并不遵循相同的安排..

示例版本政策： - “N-2”，意为“具有 2 个月更新宽限期的最新版本” - 每个偶数版本具有 2 个月更新宽限期 - 本财年每个版本具有 1 年更新宽限期

> [!NOTE]
> 要找到与您的项目兼容的最低 `rust-version`，您可以使用像 [`cargo-msrv`](https://crates.io/crates/cargo-msrv)这样的第三方工具。

### 更新时间表

当您的政策规定您不再需要支持某个 Rust 版本时，您可以立即或按需更新 `rust-version`。

通过允许 `rust-version` 偏离您的政策，您为用户提供了更多的升级宽限期。然而，这种不可预测性使得无法依赖它来与用户关注的 Rust 版本保持一致。

`rust-version` 偏离指定政策的程度越严重，用户就越有可能推断出一个您未打算的政策，导致对未满足期望的沮丧。

当允许偏差时，问题在于什么才“足够合理”以放弃支持的版本。每个人都可以提出不同的合理理由；进行这种讨论可能会让相关方感到沮丧。这将使那些希望避免此类冲突的人失去能力，尤其是新成员或临时贡献者，他们可能觉得没有资格提出问题，或者认为冲突可能会妨碍他们的更改被合并的机会。

### 工作区中的多种政策

Cargo 允许在一个工作空间内支持多种策略。

在特定的 Rust 版本下验证特定包可能会变得复杂。像 [`cargo-hack`](https://crates.io/crates/cargo-hack) 这样的工具可以提供帮助。

对于跨策略共享的依赖项，必须使用最低共同版本，因为 Cargo 会统一 SemVer 兼容版本（resolver.md#semver-compatibility），这可能会限制具有较高 `rust-version` 的工作空间成员访问该共享依赖项的特性。

为了允许用户修改工作空间成员中的依赖项，工作空间中的所有包都需要能够在工作空间支持的最旧 Rust 版本中加载。

当使用 [`incompatible-rust-versions = "fallback"`](config.md#resolverincompatible-rust-versions) 时，一个包的 Rust 版本会影响为另一个不同 Rust 版本的包选择的依赖版本。更多细节请参见 [resolver](resolver.md#rust-version) 章节。

### 一个或多个策略

缓解支持旧版 Rust 版本带来的负面影响的一种方法是，将你的策略应用于你仍然支持的包的较旧主版本或次版本。你可能还需要针对这些主版本或次版本的开发分支与发布分支相比所支持的 Rust 版本制定策略。

仅在“必要时”更新开发分支有助于减少受支持发布分支的数量。

还有一个问题是关于哪些功能可以回退到这些发布分支中。如果在不同次版本之间回退新功能，下一个可用版本将缺少这些功能，这可能被视为破坏性变更，违反 SemVer 规范。回退更改也存在引入错误的风险。

支持旧版本是有成本的。这种成本取决于包内错误的风险和影响程度以及对回退的接受程度。按需创建发布分支并将回退负担交给社区是一种平衡这一成本的方法。

目前，依赖管理工具还无法报告非最新版本仍被支持的情况，因此责任需要由用户自己在文档中注意这一点。

例如，Rust版本支持政策可能如下：- 开发分支会追踪Rust项目的最新稳定版本，并在必要时进行更新- 当更改`rust-version`时，次要版本号将会提升- 该项目在本年度内支持所有版本，并保留一年的过渡期- 最后一个支持特定Rust版本的次要版本将获得社区提供的错误修复- 修复必须被回退到开发分支与所需支持的Rust版本之间的所有受支持次要版本中
