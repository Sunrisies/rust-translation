# 报告构建时间 `--timings` 选项提供有关每次编译所花费时间的信息，并跟踪随时间变化的并发情况。

```sh
cargo build --timings
```

这将生成 `target/cargo-timings/cargo-timing.html` 文件中的 HTML 报告。如果您希望查看之前的运行结果，该工具还会将报告副本保存到同一目录中，文件名中会包含时间戳。

## 阅读图表

输出中包含两张表格和两张图表。

第一张表格显示项目的构建信息，包括构建的单位数量、最大并发数、构建时间以及当前使用的编译器的版本信息。

![build-info](../images/build-info.png)

“单位”图表展示了各个单位的持续时间。一个“单位”指的是一次单独的编译器调用。某些线条显示了当某个单位完成时哪些额外的单位被“解锁”。也就是说，这些新单元现在可以运行，因为它们的依赖项都已完成。将鼠标悬停在某个单位上即可高亮显示相关线条。这有助于可视化依赖关系的关键路径。由于各单位的完成顺序可能不同，此数据在多次运行之间可能会发生变化。

“代码生成”时间以淡紫色突出显示。在某些情况下，构建流水线允许在依赖项进行代码生成时开始执行单位。这些信息并不总是被显示出来（例如，二进制单元在代码生成开始时不会显示）。

“自定义构建”单位是 `build.rs` 脚本，当这些脚本运行时会以橙色高亮显示。

![build-unit-time](../images/build-unit-time.png)

第二张图表展示了 Cargo 的并发情况随时间的变化。背景区域表示 CPU 使用率。三条线条分别为：- “等待中”（红色）--- 这是正在等待 CPU 资源可用的单位数量。- “不活跃”（蓝色）--- 这是正在等待依赖项完成的单位数量。- “活跃”（绿色）--- 这是当前正在运行的单元数量。

![cargo-concurrency-over-time](../images/cargo-concurrency-over-time.png)

> [!NOTE]
> 此图表并未显示编译器本身的并发情况。`rustc` 通过“作业服务器”与 Cargo 协作，以保持在并发限制范围内。目前这主要适用于代码生成阶段。

解决编译时间问题的建议： - 查找耗时的依赖项。 - 检查这些依赖项是否包含您可能希望禁用的功能。 - 考虑尝试完全移除该依赖项。 - 寻找被多次构建且使用不同版本的 crate。尝试从依赖关系图中移除旧版本。 - 将大型 crate拆分为多个较小的部分。 - 如果许多 crate都受到某个单一 crate的阻碍，请重点改进该 crate以提升并行性。

最后一张表格列出了每个单元的总耗时和“代码生成”时间，以及每个单元编译时启用的功能。
