对于任何一个给定的特质 `Trait`，都可能存在一个相关的 _类型_，称为 _特质对象类型_，通常写作 `dyn Trait`。在Rust的早期版本中，特质对象类型被写成普通的 `Trait`（仅包含特质名称，位于类型位置），但这有点令人困惑，因此现在我们采用 `dyn Trait` 的形式。

某些特质不允许被用作特质对象类型。那些可以被用作特质对象类型的特质被称为“dyn兼容”[^1]特质。尝试将特质对象类型用于非 dyn兼容的特质将会触发错误 E0038。

特质对象类型的两个一般特性导致了这些限制：

  1. 特质对象类型是动态大小类型（DST），这些类型的特质对象只能通过指针访问，例如 `&dyn Trait` 或 `Box<dyn Trait>`。这样的指针大小是已知的，但被指向的 `dyn Trait` 对象的大小对处理它的代码来说是 _不透明的_，相同特质对象类型的不同特质对象可能具有不同的大小。

  2. 用于访问特质对象的指针与另一个指向“虚拟方法表”或 “vtable”的指针配对，该表用于实现对对象实现特质方法的动态分派。每个特质实现都有唯一的 vtable，但相同特质对象类型的不同特质对象可能指向来自不同实现的 vtable。

违反 dyn-兼容性 specific 条件包括大多数与缺失大小信息以及由这些特性引起的 vtable 多态性相关的问题。

[^1]：以前称为“对象安全”。

### 该特质要求 `Self: Sized`

被声明为 `Trait: Sized` 或继承 `Self:Sized` 约束的特质不是 dyn兼容的。

其背后的理由有些微妙。这源于 Rust 要求（并定义）每个特质对象类型 `dyn Trait` 自动实现 `Trait`。Rust 这样做是为了简化错误报告并便于静态与动态多态性之间的互操作。例如，以下代码可以正常工作：

```
trait Trait {
}

fn static_foo<T:Trait + ?Sized>(b: &T) {
}

fn dynamic_bar(a: &dyn Trait) {
    static_foo(a)
}
```

这段代码能够正常工作是因为如果存在 `dyn Trait`，它总是实现了 `Trait`。

然而，正如我们所知，任何 `dyn Trait` 都是无大小的，因此它永远无法实现像 `Trait:Sized` 这样的有大小限制的 trait。所以，Rust 选择禁止存在这样的 `dyn Trait`，而不是允许违反规则的情况发生。

只有无大小限制的 trait 才被视为与 dyn 兼容的。

通常，`Self: Sized` 用于表明该 trait 不应被用作 trait object。如果 trait 来自你自己的 crate，考虑移除这一限制。

### 参数或返回类型引用了 `Self` 类型的方法

当 trait 包含如下方法时会发生这种情况：

```
trait Trait {
    fn foo(&self) -> Self;
}

impl Trait for String {
    fn foo(&self) -> Self {
        "hi".to_owned()
    }
}

impl Trait for u8 {
    fn foo(&self) -> Self {
        1
    }
}
```

（注意 `&self` 和 `&mut self` 是可以的，是额外的 `Self` 类型导致了这个问题。）

在这种情况下，编译器无法预测如下情况中 `foo()` 的返回类型：

```compile_fail,E0038
trait Trait {
    fn foo(&self) -> Self;
}

fn call_foo(x: Box<dyn Trait>) {
    let y = x.foo(); // What type is y?
    // ...
}
```

如果只有某些方法不是 dyn 兼容的，可以在它们上添加 `where Self: Sized` 约束，以明确表明这些方法不可用于 trait object。功能仍然对所有其他实现者可用，包括 `Box<dyn Trait>`（假设你实现了 `Trait for Box<dyn Trait>`）。

```
trait Trait {
    fn foo(&self) -> Self where Self: Sized;
    // more functions
}
```

现在，`foo()` 不能再在 trait object 上调用，但你现在可以创建 trait object，并且该对象能够调用任何 dyn 兼容的方法。通过这种约束，仍然可以在非 trait object 类型的实现该 trait 的实例上调用 `foo()`。

### 方法具有泛型类型参数

如前所述，trait object 包含指向方法表的指针。因此，如果我们有：

```
trait Trait {
    fn foo(&self);
}

impl Trait for String {
    fn foo(&self) {
        // implementation 1
    }
}

impl Trait for u8 {
    fn foo(&self) {
        // implementation 2
    }
}
// ...
```

在编译时，`Trait` 的每个实现都会生成一个包含与实现相关的各种方法（及其他项）的表，该表将作为从该实现派生的 `dyn Trait` 对象的虚拟方法表使用。

这运作良好，但当该方法具有泛型参数时，就会出现问题。

通常，泛型参数会被 _monomorphized_。例如，如果我有

```
fn foo<T>(x: T) {
    // ...
}
```

`foo::<u8>()`、`foo::<bool>()`、`foo::<String>()` 或任何其他实例化的机器代码均有所不同。因此，编译器会按需生成实现代码。如果你使用 `bool` 参数调用 `foo()`，编译器将仅生成 `foo::<bool>()` 的代码。当存在额外的类型参数时，编译器生成的单态化实现数量不会大幅增加，因为编译器仅在函数使用完全具体的参数（即不包含任何泛型参数的参数）时才会生成实现代码。

然而，对于 trait 对象，我们必须创建一个包含所有实现该 trait 的对象的表格。如果对象具有类型参数，则需要对每个实现该 trait 的类型添加实现代码，而理论上可能存在无限多的类型。

例如：

```
trait Trait {
    fn foo<T>(&self, on: T);
    // more methods
}

impl Trait for String {
    fn foo<T>(&self, on: T) {
        // implementation 1
    }
}

impl Trait for u8 {
    fn foo<T>(&self, on: T) {
        // implementation 2
    }
}

// 8 more implementations
```

现在，如果我们有以下代码：

```compile_fail,E0038
# trait Trait { fn foo<T>(&self, on: T); }
# impl Trait for String { fn foo<T>(&self, on: T) {} }
# impl Trait for u8 { fn foo<T>(&self, on: T) {} }
# impl Trait for bool { fn foo<T>(&self, on: T) {} }
# // etc.
fn call_foo(thing: Box<dyn Trait>) {
    thing.foo(true); // this could be any one of the 8 types above
    thing.foo(1);
    thing.foo("hello");
}
```

我们不仅需要为 `Trait` 的所有方法的所有实现创建一张表格，还需要为传入 `foo()` 的每个不同类型创建这样的表格。在这种情况下，相当于 (10 种实现 `Trait` 的类型) * (3 种传入 `foo()` 的类型) = 30 个实现！

对于现实世界中的 trait，这些数字可能会大幅增加。

为了解决这个问题，建议使用类似于上述子错误修复的 `where Self: Sized` 约束，如果你不打算使用类型参数调用该方法：

```
trait Trait {
    fn foo<T>(&self, on: T) where Self: Sized;
    // more methods
}
```

如果这不是一个选项，考虑用另一个 trait 对象替换类型参数（例如，如果 `T: OtherTrait`，则使用 `on: Box<dyn OtherTrait>`）。如果你想传递给该方法的类型数量有限，可以考虑手动列出不同类型的所有方法。

### 方法没有接收者

不接受 `self` 参数的方法无法被调用，因为无法获取指向该方法表的指针。

```
trait Foo {
    fn foo() -> u8;
}
```

这可以被称为 `<Foo as Foo>::foo()`，这样就无法选择实现了。

通常将 `Self: Sized` 约束添加到这些方法中可以使其编译通过。

```
trait Foo {
    fn foo() -> u8 where Self: Sized;
}
```

### trait 包含关联常量

与静态函数一样，关联常量也不存储在方法表中。如果特质或任何子特质包含关联常量，它们就不具备动态兼容性。

```compile_fail,E0038
trait Foo {
    const X: i32;
}

impl dyn Foo {}
```

一个简单的解决方法是使用辅助方法：

```
trait Foo {
    fn x(&self) -> i32;
}
```

### 特质在子特质列表中将 `Self` 作为类型参数使用

这类似于第二种子错误情况，但更为微妙。这种情况发生在以下场景：

```compile_fail,E0038
trait Super<A: ?Sized> {}

trait Trait: Super<Self> {
}

struct Foo;

impl Super<Foo> for Foo{}

impl Trait for Foo {}

fn main() {
    let x: Box<dyn Trait>;
}
```

在这里，子特质可能包含如下方法：

```
trait Super<A: ?Sized> {
    fn get_a(&self) -> &A; // note that this is dyn-compatible!
}
```

如果特质 `Trait` 是从类似 `Super<String>` 或 `Super<T>`（其中 `Foo` 本身为 `Foo<T]`）派生出来的，这是可以的，因为给定类型 `get_a()` 肯定会返回该类型的对象。

然而，如果它从 `Super<Self>` 派生出来，尽管 `Super` 具有动态兼容性，但在调用方法时 `get_a()` 将返回未知类型的对象。`Self` 类型参数使得动态兼容的特质不再具备兼容性，因此在指定子特质时禁止使用这种情况。

没有简单的解决方案。通常需要重构代码，以便不再需要从 `Super<Self>` 派生。
