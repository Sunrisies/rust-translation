# Nuxt 中文文档 — 部署与维护手册

本文档记录站点在自有服务器上的**实际部署情况**，以及后续的更新操作。

- **线上地址**：https://nuxt.sunrise1024.top/
- **服务器**：47.111.168.59（阿里云 ECS，Ubuntu 22.04）
- **文档版本**：Nuxt v4.6.4（与官网稳定版一致）
- **翻译**：本地 Hy-MT2-1.8B 模型，增量翻译系统

## 一、实际部署架构（重要）

服务器上的 Caddy **不是 systemd 服务，而是跑在 Docker 容器里**：

```
容器名: caddy (镜像 caddy:latest)
占用端口: 80 / 443
容器挂载:
  主机 /home/www/caddy/Caddyfile      -> 容器 /etc/caddy/Caddyfile
  主机 /home/www/caddy/caddy-config   -> 容器 /config
  主机 /home/www/caddy/caddy-data     -> 容器 /data
  主机 /home/3s                       -> 容器 /home/www/3s/cloud (只读)
```

**注意**：容器内的 `/var/www/nuxt-docs` **不是挂载目录**，是容器内部独立的一份文件。所以站点文件在主机和容器里**各有一份**，更新时必须两边都更新（见第四节）。

现有站点共用这个 Caddy：`image / excalidraw / file / docker / app / admin / nuxt .sunrise1024.top`。

## 二、当前 Caddy 配置

配置段（已追加在 `/home/www/caddy/Caddyfile` 末尾）：

```caddyfile
nuxt.sunrise1024.top {
    root * /var/www/nuxt-docs
    encode gzip zstd
    try_files {path} {path}.html {path}/ =404
    handle_errors {
        rewrite * /404.html
        file_server
    }
    file_server {
        index index.html
    }
}
```

**`try_files` 这行不能删**：Docus 生成的站内链接无后缀（`/getting-started/introduction`），但实际文件是 `introduction.html`，靠这行补 `.html`，否则点链接全 404。

DNS：`nuxt.sunrise1024.top` A 记录 → `47.111.168.59`（DNSPod），Caddy 自动签发并续期 Let's Encrypt 证书。

## 三、部署时踩的两个坑（以后维护注意）

### 坑 1：改主机 Caddyfile 不会同步到容器

虽然配置是 bind mount，但实测主机文件改了、容器内没变（md5 不同）。而且因为 mount 占用 inode，`docker cp` 和 `sed -i` 都会报 `Resource busy`。

**正确改法**（在容器内用重定向覆写，不换 inode）：

```bash
ssh root@47.111.168.59
docker exec caddy sh -c "sed 's|旧域名|新域名|g' /etc/caddy/Caddyfile > /tmp/new && cat /tmp/new > /etc/caddy/Caddyfile"
docker exec caddy caddy validate --config /etc/caddy/Caddyfile
docker exec caddy caddy reload --config /etc/caddy/Caddyfile
```

### 坑 2：文件在主机、但 Caddy 在容器里读不到

站点文件解压在主机 `/var/www/nuxt-docs`，但容器内最初没有 `/var/www`，导致全站 404。

**解决**：把文件复制进容器：

```bash
docker exec caddy mkdir -p /var/www/nuxt-docs
docker cp /var/www/nuxt-docs/. caddy:/var/www/nuxt-docs/
```

## 四、以后更新站点（标准流程）

官方文档更新后，本地跑一条命令完成"翻译 + 生成 + 打包"：

```bash
bash D:/hy-mt2-bench/nuxt-docs/update.sh
```

它会自动：git pull → 增量翻译（只翻变化的）→ 内联图标 → 生成静态站 → 同步到 `deploy/public` → 重新打包 `nuxt-docs-dist.tar.gz`。

然后上传到服务器，**注意要更新主机和容器两份**：

```bash
# 1. 上传服务器专用包（注意是 deploy-server 目录，不是 deploy）
scp D:/hy-mt2-bench/nuxt-docs/deploy-server/nuxt-docs-dist.tar.gz root@47.111.168.59:/tmp/

# 2. 更新主机那份
ssh root@47.111.168.59 'rm -rf /var/www/nuxt-docs && mkdir -p /var/www/nuxt-docs && tar -xzf /tmp/nuxt-docs-dist.tar.gz -C /var/www/nuxt-docs'

# 3. 更新容器那份（关键，别漏）
ssh root@47.111.168.59 'docker cp /var/www/nuxt-docs/. caddy:/var/www/nuxt-docs/'
```

WorkBuddy 托管站则用 `deploy/nuxt-docs-dist.tar.gz` 对应的产物（直接跑发布工具即可）。

静态文件更新**不需要 reload Caddy**。

> 更彻底的方案：重建 Caddy 容器时把 `/var/www/nuxt-docs` 挂载进去，以后只需更新主机一份。但重建会影响现有 6 个站点，需谨慎。

## 七、Umami 统计说明（重要）

**两个部署目标用不同的脚本 + website-id**（不要混用）：

| 部署目标 | 脚本 | website-id | 产物目录 |
|---|---|---|---|
| WorkBuddy 托管 | `script.js` | `1b580d0f-9fca-40f0-a513-1401faa8d557` | `deploy/` |
| 自有服务器 | `recorder.js` | `a95f5257-96c9-4c01-aa90-8c9d683ac000` | `deploy-server/` |

`update.sh` 会自动产出两份：site 生成的是 WorkBuddy 版，`scripts/make-server-dist.mjs` 再转换成服务器版。

**这个 Umami 实例是定制版，不提供传统的"页面浏览量（pageview）"统计。** 实测结论：

- 服务端 `/api/send` 只接受 `type = error | event | identify | performance`，发 `pageview` 返回 400
- `recorder.js` 是录屏/热力图插件（采样率 15%），配套 `script.js` 也只做事件追踪（暴露 `umami.track()`），两者都不产生 pageview
- 所以在后台看不到"访问次数/访客数"是**正常的**，这个实例看的是事件与录屏回放

如果以后要传统访问统计，需换成官方标准 Umami 实例（支持 pageview），或让服务端开启 pageview 类型支持。
