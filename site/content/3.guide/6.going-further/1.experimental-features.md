Nuxt 包含一些实验性功能，你可以在配置文件中启用这些功能。

内部而言，Nuxt 使用 `@nuxt/schema` 来定义这些实验性功能。你可以参考 [API 文档](/docs/guide/going-further/experimental-features) 或 [源代码](https://github.com/nuxt/nuxt/blob/main/packages/schema/src/config/experimental.ts) 以获取更多信息。

::note
请注意，这些功能是实验性的，未来可能会被移除或修改。
::

## alwaysRunFetchOnKeyChange

当键发生变化时是否运行 `useFetch`，即使设置为 `immediate: false` 且尚未触发时也是如此。

如果设置为 `immediate: true` 或已经触发过，则键发生变化时 `useFetch` 和 `useAsyncData` 将始终运行。

此标志默认被禁用，但你可以启用此功能：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    alwaysRunFetchOnKeyChange: true,
  },
})
```

```ts twoslash [nuxt.config.ts]

    asyncContext: true,
  },
```

## extractAsyncDataHandlers

从 `useAsyncData` 和 `useLazyAsyncData` 调用中提取处理函数到单独的块中，以提高代码分割和缓存效率。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    extractAsyncDataHandlers: true,
  },
})
```

此功能将内联处理函数转换为动态导入的块：

```vue
<!-- Before -->
<script setup>
const { data } = await useAsyncData('user', async () => {
  return await $fetch('/api/user')
})
</script>
```

```vue
<!-- After transformation -->
<script setup>
const { data } = await useAsyncData('user', () =>
  import('/generated-chunk.js').then(r => r.default()),
)
</script>
```

这种转换的好处是，我们可以分离数据获取逻辑——同时仍允许在需要时加载代码。

::important
此功能仅推荐用于具有负载提取的 **静态构建**，且数据在运行时不需要重新获取的情况。
::

## emitRouteChunkError

当加载 vite/webpack 块出现错误时，触发 `app:chunkError` hook。默认行为是在块无法加载时，导航到新路由时执行重新加载操作。

默认情况下，当导航到新路由时某个 chunk 无法加载时，Nuxt 会执行新路由的重新加载（`automatic`）。

将 `automatic-immediate` 设置为 `false` 会导致 Nuxt 在 chunk 无法加载时立即执行当前路由的重新加载（而不是等待导航操作）。这对于由导航引发的之外的 chunk 错误非常有用，例如当您的 Nuxt 应用无法加载 [延迟组件](/docs/directory-structure/app/components#dynamic-imports) 时。这种行为的潜在缺点是可能会产生不必要的重新加载，例如当您的应用不需要导致错误的 chunk 时。

您可以将此设置设置为 `false` 来禁用自动处理，或者将设置改为 `manual` 以手动处理 chunk 错误。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    emitRouteChunkError: 'automatic', // or 'automatic-immediate', 'manual' or false
  },
})
```

## restoreState

允许在 chunk 错误或手动调用 [`reloadNuxtApp()`](/docs/api/utils/reload-nuxt-app) 后重新加载页面时，从 `sessionStorage` 恢复 Nuxt 应用状态。

为了避免 hydration 错误，此功能仅在 Vue 应用已挂载后应用，这意味着在初始加载时可能会出现闪烁现象。

::important
在启用此功能之前请仔细考虑，因为它可能导致意外行为，
并且建议为 [`useState`](/docs/api/组合式函数/use-state) 提供明确的键值，因为自动生成的键可能在不同构建中不匹配。
::

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    restoreState: true,
  },
})
```

## payloadExtraction

控制预渲染和缓存（ISR/SWR）页面中负载数据的传递方式。

- `'client'` - 在初始服务器渲染时，负载数据会被内联到 HTML 中，并在客户端导航时提取为 `_payload.json` 文件。
- `true` - 初始服务器渲染和客户端导航时，载荷都会被提取到单独的 `_payload.json` 文件中。
- `false` - 完全禁用载荷提取。载荷始终直接嵌入到 HTML 中，不会生成 `_payload.json` 文件。

默认值为 `true`，当设置 `compatibilityVersion: 5` 时则为 `'client'`。当设置 `ssr: false` 时，强制设置为 `false`。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    payloadExtraction: 'client',
  },
})
```

了解更多关于载荷提取及每种模式带来的后果的信息。

## clientNodePlaceholder

在服务器端渲染期间，使用注释节点 (`<!--placeholder-->`) 代替 `<div>` 元素作为仅针对客户端的组件占位符。

启用后，`.client.vue` 组件和 `createClientOnly()` 包装器会在服务器上渲染 HTML 注释，而不是空 `<div>`。这解决了 Vue  hydration 问题，即当占位符 `<div>` 和实际组件根节点共享相同的标签名时，范围样式可能无法应用。

::warning
启用此功能意味着传递给 `.client.vue` 组件的属性（如 `class`、`style` 等）不会出现在 SSR HTML 中。如果您需要样式化的占位符以防止布局偏移，请使用带有 `#fallback` 插槽的 `<ClientOnly>`。
::

当设置 `future.compatibilityVersion` 为 `5` 或更高时，此标志会被启用，但您也可以显式启用它：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    clientNodePlaceholder: true,
  },
})
```

## serverPathFallback

加载一个作为完整文档的、与任何页面路由不匹配的客户端导航，因此服务器可以响应 `public/` 下的文件、服务器路由或其 404 页面。启用此功能后，`<NuxtLink to="/brochure.pdf">` 和 `<NuxtLink to="/rss.xml">` 在点击时工作方式与硬加载时相同。

如果当前文档已经提供该路径，则不会重新加载路径，因此对于以 SPA 回退方式响应未知路径的主机，会渲染客户端 404 页面。

此标志默认启用，但您可以将其禁用：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    serverPathFallback: false,
  },
})
```

当启用 `hashMode` 时，此选项无效。

## early404

对于无法匹配任何页面路由的请求，在服务器上不加载 Vue 应用、其插件或中间件的情况下，会返回早期的 404 错误。

页面路由（包括别名）在构建时会被编译成静态路由匹配器，进入的请求会在服务器端渲染开始之前进行检查。无法匹配任何页面的请求将完全跳过应用加载，直接显示错误页面。

没有 `Accept: text/html` 头部的请求（API 客户端、大多数扫描器）会在根本不加载应用的情况下收到 JSON 错误，除非 `future.compatibilityVersion` 为 `5`。HTML 请求仍然会服务器渲染错误页面。涵盖该路径的 [`cache` 路由规则](/docs/guide/concepts/rendering#hybrid-rendering) 在 GET/HEAD 请求中将其 `maxAge` 设置为 `Cache-Control` 也会失效，从而让 CDN 能够处理未知路径的重复请求。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    early404: true,
  },
})
```

::warning
这是可选的，因为它可能会破坏依赖运行时路由的应用。

- 通过插件中的 `router.addRoute()` 动态添加页面。为了尽早暴露此功能，当启用该选项时，`[useRouter](/docs/api/composables/use-router)` 返回的路由器类型中已移除 `addRoute`。
- 将未知路径重定向到现有页面的路由中间件。

在开发环境中，当启用 `hashMode`、根级通用页面（如 `pages/[...slug].vue`）匹配所有路径，以及自定义 `app/router.options` 文件可能修改 `routes` 时，该选项会自动禁用（默认导出为不含 `routes` 键的普通对象的文件仍然兼容）。
::

## watcher

设置替代的 watcher，作为 Nuxt 的监视服务使用。

默认情况下，Nuxt 使用 `chokidar-granular`，它会忽略未被监视的顶级目录，
（如 `node_modules` 和 `.git`）。

您可以将此设置改为 `parcel`，以使用 `@parcel/watcher`，这可能会提高
大型项目或 Windows 平台上的性能。

您也可以将此设置设为 `chokidar`，以监视源目录中的所有文件。

将设置为 `'builder'`，则重用当前构建器的文件监视器（例如，
Vite 的 `server.watcher`），而不是启动第二个监视器。这减少了
开发模式下活跃的文件监视器数量，并在
`future.compatibilityVersion` 为 `5` 时成为默认设置。如果当前构建器没有实现
其自身的监视器（目前是 webpack 和 rspack），Nuxt 会记录警告并回退到其默认选择。
back to its default selection.

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    watcher: 'chokidar-granular', // 'chokidar', 'parcel' or 'builder' are also options
  },
})
```

## scanPageMeta

Nuxt 在构建时将 `definePageMeta` 中定义的某些路由元数据暴露给模块（具体包括 `alias`、`name`、`path`、`redirect`、`props` 和 `middleware`）。

这仅适用于静态数据或字符串/数组，而不适用于变量或条件赋值。有关更多信息和背景，请参见 [原始问题](https://github.com/nuxt/nuxt/issues/24770)。

默认情况下，页面元数据仅在所有路由在 `pages:extend` 中注册后才会被扫描。之后会调用另一个钩子 `pages:resolved`。

如果此功能在项目中引发问题，你可以禁用它。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    scanPageMeta: false,
  },
})
```

## buildCache

根据配置和源文件的哈希值缓存 Nuxt 构建产物。

这仅适用于 `srcDir` 和 `serverDir` 中的 Vue/Nitro 部分源文件。

此标志默认禁用，但你可以启用它：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    buildCache: true,
  },
})
```

当启用时，以下文件的更改将触发完全重建：

```bash [Directory structure]
.nuxtrc
.npmrc
package.json
package-lock.json
yarn.lock
pnpm-lock.yaml
tsconfig.json
bun.lock
bun.lockb
```

此外，`srcDir` 中的任何文件更改都将触发 Vue 客户端/服务器捆绑包的重建。Nitro 总是会被重建（尽管目前正在努力让 Nitro 能够宣布其可缓存产物及其哈希值）。

::note
最多保留 10 个缓存 tarball。
::

## extraPageMetaExtractionKeys

`definePageMeta()` 宏是一种收集页面构建时元数据的有效方式。Nuxt 本身提供了一组支持的键列表，用于支持一些内部功能，如重定向、页面别名和自定义路径。

此选项允许在使用 `scanPageMeta` 时从页面元数据中提取额外的键。

```vue
<script lang="ts" setup>
definePageMeta({
  foo: 'bar',
})
</script>
```

```ts
export default defineNuxtConfig({
  experimental: {
    extraPageMetaExtractionKeys: ['foo'],
  },
  hooks: {
    'pages:resolved' (ctx) {
      // ✅ foo is available
    },
  },
})
```

这允许模块从构建上下文中的页面元数据访问额外元数据。如果你在模块中使用此功能，建议也 [为 `NuxtPage` 类型添加你的键](/docs/directory-structure/app/pages#typing-custom-metadata)。

## extractSerializablePageMeta

当 `future.compatibilityVersion` 为 `5` 或更高时，默认启用此功能。

默认情况下，Nuxt 在构建时仅读取固定的 `definePageMeta()` 键列表（以及 `extraPageMetaExtractionKeys` 中的内容）；其余内容则通过为每个页面生成的独立模块在运行时解析。启用此选项后，Nuxt 会将所有可序列化的 JSON 属性直接写入生成的路由记录中。

当页面的每个 `definePageMeta()` 属性都可以静态解析时，路由将不再导入该页面的元模块，从而从开发模块图中移除每个页面一个模块。

```vue
<script lang="ts" setup>
definePageMeta({
  layout: { name: 'admin', props: { collapsed: true } },
  title: 'Dashboard',
})
</script>
```

无法序列化的属性（函数、变量引用、展开运算符、计算键）不受影响，仍会在运行时解析。

当 [`scanPageMeta`](#scanpagemeta) 为 `false` 时，此选项无效，因为在这种情况下路由记录不会覆盖元模块。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    extractSerializablePageMeta: false,
  },
})
```

## navigateToEarlyReturn

将 `<script setup>` 中的顶级 `await navigateTo()` 调用在导航成功时转换为从编译后的 `setup()` 函数中的早期返回。

如果没有此标志，`await navigateTo()` 之后的代码将继续运行，这可能导致后续代码（包括后续的 `navigateTo` 调用）覆盖重定向或尝试渲染缺少数据的页面。启用此标志后，成功的导航会停止剩余 setup 代码的执行，组件会显示占位符注释，同时导航继续进行。

此标志在 `compatibilityVersion: 5` 时默认启用，但你可以禁用它：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    navigateToEarlyReturn: false,
  },
})
```

```vue [pages/example.vue]
<script setup lang="ts">
const { data } = await useFetch('/api/data')

if (!data.value) {
  await navigateTo('/fallback')
}

// with the flag enabled, this only runs if the navigation did not happen
const processed = data.value!.map(item => item.name)
</script>
```

此转换仅适用于 `<script setup>` 中的顶级 `await navigateTo()` 语句，且其结果未被使用。带有 `open` 选项或无法静态分析的选项的调用不会被转换，因为它们不应阻止当前页面渲染。

早期返回仅在导航成功时发生（即当 `navigateTo` 解析为 `undefined` 时）。如果导航被中止或失败（例如被导航保护器阻止，或导航到当前路由），剩余的 setup 代码将继续运行。在成功导航后，`navigateTo` 调用之后的所有操作都不会执行：包括 `defineExpose` 和 `<script setup>` 中后期的任何生命周期钩子注册。

::read-more{icon="i-simple-icons-github" to="https://github.com/nuxt/nuxt/issues/23698" target="_blank"}
在 GitHub issue 中可查看完整说明。
::

## normalizeComponentNames

Nuxt 将自动生成的 Vue 组件名称更新为与您用于自动导入组件的完整组件名称一致。

如果您遇到问题，可以禁用此功能。

```ts twoslash [nuxt.config.ts]

    normalizeComponentNames: false,
  },
})
```

默认情况下，如果您未手动设置，Vue 会分配一个与组件文件名相同的组件名称。
从 Vue 的角度来看，该组件名称将为 `MyComponent`。如果您想使用 `<KeepAlive>` 引用它，或在 Vue DevTools 中识别它，则需要使用此组件。

```bash [Directory structure]
├─ components/
├─── SomeFolder/
├───── MyComponent.vue
```

In this case, the component name would be `MyComponent`, as far as Vue is concerned. If you wanted to use `<KeepAlive>` with it, or identify it in the Vue DevTools, you would need to use this component.

但为了自动导入它，您需要使用 `SomeFolderMyComponent`。

通过设置 `experimental.normalizeComponentNames`，这两个值将匹配，Vue 将生成一个符合 Nuxt 组件命名模式的组件名称。

## normalizePageNames

确保页面组件名称与其路由名称一致。这设置了页面组件的 `__name` 属性，以便 Vue 的 `<KeepAlive>` 能够按名称正确识别它们。

默认情况下，Vue 根据文件名分配组件名称。例如，`pages/foo/index.vue` 和 `pages/bar/index.vue` 都将具有组件名称 `index`。这使得基于名称的 `<KeepAlive>` 过滤不可靠，因为多个页面共享相同的名称。

启用 `normalizePageNames` 后，页面组件按其路由名称命名（例如 `foo` 和 `bar`），因此您可以在 `include`/`exclude` 中使用 `<KeepAlive>，而无需为每个页面手动添加 `defineOptions({ name: '...' })`。

当 `future.compatibilityVersion` 设置为 `5` 或更高时，此标志会被启用，但您可以禁用此功能：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizePageNames: false,
  },
})
```

```vue [app.vue]
<template>
  <NuxtPage :keepalive="{ include: ['foo'] }" />
</template>
```

## spaLoadingTemplateLocation

在渲染仅客户端使用的页面时（`ssr: false`），Nuxt 可以选择从 [`spa-loading-template.html`](/docs/directory-structure/app/spa-loading-template) 渲染加载屏幕。

默认情况下（`'body'`），模板与 Nuxt 应用根目录一起渲染，并被包裹在 loader 元素中：

```html
<div id="__nuxt"></div>

  <!-- spa loading template -->
</div>
```

当第一个页面准备好渲染时，loader 元素将被移除，包括页面中的异步设置，从而避免了加载屏幕与页面之间的白色闪光。您可以使用 [`app.spaLoaderTag`](/docs/api/nuxt-config#spaloadertag) 和 [`app.spaLoaderAttrs`](/docs/api/nuxt-config#spaloaderattrs) 对其进行自定义。Nuxt 通过 `id` 找到该元素并将其移除，因此如果您更改 `spaLoaderAttrs`，请保留一个 `id`。

或者，您可以将模板设置在 `'within'` 模式下，在 Nuxt 应用根目录中渲染：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    spaLoadingTemplateLocation: 'within',
  },
})
```

这样渲染效果如下：

```html
<div id="__nuxt">
  <!-- spa loading template -->
</div>
```

在这种情况下，当 Vue 启动应用后，模板会被移除，因此屏幕可能保持空白，直到第一页准备好渲染。

## 装饰器

此选项使整个 Nuxt/Nitro 应用支持装饰器语法。

当使用 Vite 构建器（默认设置）时，装饰器通过 [Babel](https://babeljs.io/) 使用 [`@babel/plugin-proposal-decorators`](https://babeljs.io/docs/babel-plugin-proposal-decorators) 进行转换。当使用 webpack 或 rspack 构建器时，装饰器通过 [esbuild](https://github.com/evanw/esbuild/releases/tag/v0.21.3) 进行转换。

长期以来，TypeScript 通过 `compilerOptions.experimentalDecorators` 支持装饰器。这种实现早于 TC39 标准化过程。现在，装饰器是 [阶段 3 提案](https://github.com/tc39/proposal-decorators)，在 TS 5.0+ 中无需特殊配置即可支持（参见 https://github.com/microsoft/TypeScript/pull/52582 和 https://devblogs.microsoft.com/typescript/announcing-typescript-5-0-beta/#decorators）。

启用 `experimental.decorators` 会支持 TC39 提案，但**不会**支持 TypeScript 之前的 `compilerOptions.experimentalDecorators` 实现。

::warning
请注意，在该功能最终纳入 JS 标准之前可能会有所变动。
::

### 使用方式

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    decorators: true,
  },
})
```

当使用 Vite 构建器或 Nitro 服务器构建时，您需要将额外的 Babel 包作为开发依赖项安装：

::code-group
```bash [npm]
npm install -D @babel/plugin-proposal-decorators @babel/plugin-syntax-jsx
```
```bash [pnpm]
pnpm add -D @babel/plugin-proposal-decorators @babel/plugin-syntax-jsx
```
```bash [yarn]
yarn add -D @babel/plugin-proposal-decorators @babel/plugin-syntax-jsx
```
::

::tip
如果尚未安装，Nuxt 会提示您自动安装这些包。
::

```ts [app/app.vue]
function something (_method: () => unknown) {
  return () => 'decorated'
}

class SomeClass {
  @something
  public someMethod () {
    return 'initial'
  }
}

const value = new SomeClass().someMethod()
// this will return 'decorated'
```

## prefetchPreloadTags

当 `<NuxtLink>` 被预取且目标路由已启用 [payload extraction](#payloadextraction)（预渲染和缓存路由的默认设置）时，通过 [`useHead`](/docs/api/组合式函数/use-head) 或类似模块如 [`@nuxt/image`](https://image.nuxt.com)'s `<NuxtImg preload`）设置的任何 `<link rel="preload">` 提示都会被转发到当前文档中。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
```

## routeTypedFetch

从服务器构建器报告的路由中定义 `$fetch` 和 `useFetch`，而不是从
响应中通过 `InternalApi` 接口贡献给 `ServerRoutes` 的 nitro 中定义。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    routeTypedFetch: true,
  },
})
```

生成的路由集包含处理器验证的 `body`、`query` 和 `headers` 以及其
通过网络传输的已类型化响应，因此解析调用比之前更严格地类型化：

- 处理器返回的 `Date` 在调用点为 `string`
- 处理器验证的 `body` 不能省略或具有错误的格式
- 路由不响应的方法将被拒绝
- `params` 不再被接受，因为它曾经只是 `query` 的别名
- 通过手动扩展 `ServerRoutes` 注册的路由需要重写，因为这两个
  路由的描述不同（请参阅 [升级指南](https://nuxt.com/docs/5.x/getting-started/upgrade#typed-fetch-rebuilt-on-generated-route-types)）。
  使用 `Endpoint`（从 `nuxt/app` 导入）在重写后的形式中声明的路由被类型化
  `routeTypedFetch` 在启用和禁用两种情况下都适用，因此你可以在切换之前重写它

由于这些原因，它是可选的，并且 `future.compatibilityVersion: 5` 使其可用。设置它
明确选择无论兼容性版本如何都进行类型化，因此你可以在
迁移到 Nuxt 5 之前采用它，或者迁移到 Nuxt 5 时设置 `routeTypedFetch: false` 并单独采用它。

::note
此选项仅在两种类型化都支持时存在。从 Nuxt 5 开始，生成的路由集成为
唯一来源，该选项将消失。
::

## strictRouteTypes

拒绝对服务器路由不响应的路径的请求。需要
[`routeTypedFetch`](#routetypedfetch)，它从你的
服务器将提供的路由中定义 `$fetch` 和 `useFetch`
启用 `routeTypedFetch` 时，响应由响应它的处理器进行类型化，无论此选项设置为什么
```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    routeTypedFetch: true,
    strictRouteTypes: true,
  },
})
```

With `routeTypedFetch` enabled a response is typed by the handler that answers it whatever this
选项如何。选项决定的问题是 Nuxt 不识别的路径是错误还是
只是被类型化为 `unknown`。

- `false`（默认） - Nuxt 不识别的路径被接受并解析为 `unknown`，并且没有
  该方法被拒绝。Nuxt 无法看到请求可能被响应的所有方式：nitro 中间件、代理或通用处理程序。
  [`routeRules`](/docs/guide/concepts/rendering#hybrid-rendering) 代理或通用处理程序
  可以响应没有路由描述的路径。
- `true` - 仅接受服务器构建器报告的路由，以及它们响应的方法。
- `'isomorphic'` - 如同 `true`，你的页面作为 `GET` 路由返回 `string`，因此
  `$fetch('/about')` 由 Vue 路由器提供的路由定义，而不是被拒绝。

开启该选项时，拼写错误或路由不响应的方法都会成为错误：

```ts
// server/api/todos.post.ts answers POST only
await $fetch('/api/todos', { method: 'POST' })
await $fetch('/api/todo', { method: 'POST' })
//           ^ no POST route matches '/api/todo'
await $fetch('/api/todos')
//           ^ no GET route matches '/api/todos'
```

有两件事仍然被接受，因为它们无法由 Nuxt 描述：绝对 URL
（`$fetch('https://example.com')`），以及在运行时构建的路径，当

## pendingWhenIdle

`pendingWhenIdle` 控制 `useAsyncData` 和 `useFetch` 返回的 `pending` 引用。

当 `pendingWhenIdle` 为 `false`（默认值）时，在请求进行中且 `status === 'pending'` 时，`pending` 为 `true`。当 `status` 为 `idle` 时，`pending` 保持为 `false`。可以通过 `{ immediate: false }` 或在服务器渲染期间使用 `{ server: false}` 来查看此情况。

将 `pendingWhenIdle: true` 设置为 `true`，这样在 `status` 为 `idle` 且没有缓存数据时，`pending` 也为 `true`。在加载界面需要区分 `idle` 和进行中的请求时，使用 `status`。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    pendingWhenIdle: true,
  },
})
```

## entryImportMap

默认情况下，Nuxt 通过使用导入映射来稳定 chunk，从而改善捆绑文件的稳定性。

这会在 `<head>` 标签顶部注入一个导入映射：

```html
<script type="importmap">{"imports":{"#entry":"/_nuxt/DC5HVSK5.js"}}</script>
```

在 Vite 生成的脚本 chunk 中，导入将来自 `#entry`。这意味着对入口的更改不会使原本未改变的 chunk 失效。

::note
如果您将 `vite.build.target` 配置为包含不支持 import maps 的浏览器，或将 `vite.build.rolldownOptions.output.entryFileNames` 配置为不包含 `[hash]` 的值，Nuxt 会智能地禁用此功能。
::

如果您需要禁用此功能，可以这样做：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    entryImportMap: false,
  },
  // or, better, simply tell vite your desired target
  // which nuxt will respect
  vite: {
    build: {
      target: 'safari13',
    },
  },
})
```

## ssrStreaming

启用 SSR 流传输可以显著改善 Time to First Byte (TTFB)。当启用时，服务器会立即发送 HTML 壳（包括 `<head>`、样式、预加载提示和入口脚本），然后使用 Vue 的 `renderToWebStream` 逐步流式传输渲染后的内容。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    ssrStreaming: true,
  },
})
```

对于机器人和用户代理（如 Googlebot、Bingbot 等），流传输会自动禁用，以确保搜索引擎收到完全渲染的 HTML 以保障 SEO 安全。默认模式仅适用于索引爬虫；Lighthouse 和其他审计工具则故意被排除在外，以便合成测量能够反映真实用户获得的流式响应。

您可以使用 `botRegex` 自定义哪些用户代理被排除在流媒体之外。那些 `user-agent` 标头符合该模式的请求**不会**被流式传输，而是接收完整的缓冲 HTML。不符合模式的请求则会被流式传输。设置 `botRegex` 会替换默认模式，而不是在其基础上添加更多规则，因此您可以列出所有希望排除在流式传输之外的爬虫。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    ssrStreaming: {
      botRegex: /googlebot|bingbot|my-internal-crawler/i,
    },
  },
})
```

您还可以使用 `routeRules` 控制每条路由的流媒体行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    ssrStreaming: true,
  },
  routeRules: {
    '/no-stream/**': { streaming: false },
  },
})
```

::warning
**自动回退到非流式渲染。** 流式传输会在 shell 刷新时立即提交响应状态和头信息，这与需要在渲染后修改响应的功能不兼容。符合以下任一条件的请求不会被流式传输，它们使用缓冲渲染器，或直接重定向或返回错误响应：

- `routeRules` 中设置 `noScripts`、`cache`、`isr`、`swr`、`redirect` 或该路由的 `streaming: false`
- `ssr: false` 路由（已通过 SPA 渲染）
- 机器人/爬虫用户代理，即那些 `user-agent` 符合 `botRegex` 的请求
- 预渲染路由（`nuxt generate`）
- 来自插件、中间件或页面设置中的服务器端 `navigateTo()` 重定向
- 初始渲染期间产生的致命错误（在 shell 刷新之前）
::

::warning
**响应状态和头信息必须在 shell 刷新前设置。** 流式传输会在第一个字节时提交 HTTP 状态和头信息，因此任何在此之后修改响应的操作都无法到达客户端。这是流式传输的固有特性，并非 Nuxt 特有的错误。

边界点就是 shell 的刷新时刻：

- **到达客户端**：来自 Nuxt 和 Nitro 插件的修改，这些修改在渲染开始前完成。
- **被丢弃**：`setResponseStatus()`、`useResponseHeader()`、`useCookie()` 的写入操作，以及组件渲染期间进行的 h3 `setHeader()`/`appendResponseHeader()` 调用（包括路由中间件中的 `await` 或 `<script setup>` 中的调用），因为这些操作发生在 shell 已经传输到网络之后。

若需保留响应修改，请将修改逻辑放入插件中，或选择该路由不启用流式传输：

- `routeRules: { '/path': { streaming: false } }`：静态的、按路由划分。
- `render:route` 钩子设置 `ctx.prefersStream = false`：运行时、按请求划分（例如，用于条件性设置 404 的路由）。

在开发过程中，流式传输处理器会记录警告信息，说明被丢弃的修改和路由，因此这些情况不会静默失败。
::

::note
如果在 HTTP 状态已提交后流媒体过程中发生错误，`payload.error` 会被设置，且闭合标签仍会作为格式正确的文档输出，因此客户端在 hydration 过程中会捕获该错误并渲染错误页面。在壳层刷新之前抛出的错误会传递到缓冲的错误渲染器，并保留正确的状态码。
::

::note
**路由样式会进行流传输，JS 提示仅对入口页面有效。** 在路由渲染之前壳层会被刷新，因此其 `<head>` 仅包含入口分块样式和提示。一旦渲染器注册了页面和布局模块，其 CSS 就会直接在壳层之后流传输（当 `inlineStyles` 被启用时以 `<style>` 形式内联，否则以样式表链接形式提供），这样页面、布局和顶级异步组件样式会在 body 渲染之前到达（嵌套异步组件属于 FOUC 的陷阱，将在下文中说明）。特定于路由的 JS 分块不会从壳层预加载；浏览器在解析入口脚本后才会发现它们。流传输能改善每个路由的 TTFB；对于 JS 与入口分块重叠的路由，LCP 提升最大。
::

::warning
**在壳层刷新之后注册的头部标签成为客户端侧补丁。** 渲染器在第一次渲染后才会刷新壳层，因此在 `<script setup>` 中同步调用 `useHead`/`useSeoMeta`（在任何 `await` 之前）、在插件中或中间件中进行的渲染会像往常一样被放入壳层的 `<head>` 中。之后注册的标签（在 setup 中的 `await` 之后，或在嵌套的 `<Suspense>` 边界内）无法到达已发送的 `<head>`；它们以内联脚本的形式提供，在客户端上修改 DOM。

运行 JavaScript 的客户端会应用这些补丁，而符合 `botRegex` 的客户端根本不会进行流传输，因此他们会收到完整的缓冲 `<head>`。其他任何内容（你的 `botRegex` 未列出的爬虫、链接展开器、`curl` 命令）则完全看不到这些标签。JSON-LD 脚本、`noscript` 标签和位于 body 中的标签是例外：它们会在 `</body>` 之前作为真正的标记渲染，每个客户端都能读取它们。保持其他对 SEO 至关重要的标签（规范链接、社交元信息）同步，或者选择不进行流传输，设置 `routeRules: { '/path': { streaming: false } }`。
::

::note
**组件岛屿与流传输兼容。** 岛屿槽内容及选择性客户端（`nuxt-client`）组件通常会在后渲染阶段被嵌入到 HTML 中，但一旦 body 已经通过岛屿锚点流传输，这就不可能了。相反，渲染器会在文档末尾以无意义的 `<template>` 形式发出每个岛屿的传送信号，并通过一个在 hydration 之前运行的内联脚本将其重新定位到指定位置。这对应用代码是透明的。例外情况是使用 `features.noScripts` 和岛屿组件构建的应用，由于重新定位脚本无法运行，它们会回退到缓冲渲染器。
::

### 模块钩子

模块通过现有的 `render:html` 钩子参与流媒体响应（现在第二个参数带有 `streaming: true` 标志），此外还有每次请求决策钩子和两个仅用于流媒体的钩子：

- **`render:route`** 在渲染开始前每次请求触发一次，适用于所有渲染情况（无论是否启用流媒体）。读取 `ctx.canStream` 以判断该路由是否支持流媒体，并将 `ctx.prefersStream = false` 以强制此请求使用缓冲渲染，例如基于 Cookie、认证状态或 A/B 测试组。渲染器仅在 `canStream && prefersStream` 时进行流媒体传输。这是静态 `routeRules` / `botRegex` 配置的运行时绕过机制。
- **`render:html`** 在壳层刷新前触发一次，其第二个参数带有 `streaming: true`。对 `htmlAttrs`、`head`、`bodyAttrs` 和 `bodyPrepend` 的修改会生效。对 `body`/`bodyAppend` 的修改会被丢弃，因为此时即将进行流媒体传输（会发出开发模式警告）。仅修改 `head` 字段的模块（如 CSP 注入、OG 标签、分析元数据）在流媒体模式下无需任何代码修改即可工作。
- **`render:html:chunk`** 在渲染器生成每个块之前触发，用于修改 `ctx.chunk: Uint8Array` 以转换字节数据（例如 nonce 注入）；读取 `ctx.index` 以区分第一个块与后续块。
- **`render:html:close`** 在体内容流传输完成、标签关闭之前触发。通过修改 `ctx.bodyAppend: string[]` 来注入最终标记（如体内容结束后的分析标签、服务器渲染的调试小部件等）。

```ts
// modules/streaming-csp/src/runtime/server-plugin.ts
import { defineNitroPlugin } from '#imports'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('render:html', (ctx, { event }) => {
    const nonce = event.context.cspNonce
    if (!nonce) { return }
    // Works for both streaming (pre-shell) and buffered (post-render) paths.
    for (let i = 0; i < ctx.head.length; i++) {
      ctx.head[i] = ctx.head[i].replace(/<script(?![^>]*\snonce=)/g, `<script nonce="${nonce}"`)
    }
  })
})
```

::note
**CSP nonce。** 流媒体渲染器会发出几段内联脚本和样式，这些脚本和样式可以绕过未 head 的层：引导队列、IIFE、悬念 head 推送、岛迁移定位以及路由 `<style>` 块。如果渲染后的 head 脚本中存在 `nonce`，渲染器会自动在所有脚本中重复使用它，因此严格的 `script-src`/`style-src 'nonce-…'` 策略不会阻止流媒体传输。模块只需像上述那样在 head 脚本中添加 nonce；`render:html:chunk` 钩子仍可用于标记渲染到体内容中的脚本。
::

::warning
**SFC 样式的开发模式 FOUC：**在开发过程中，Vite 将 SFC `<style>` 块作为 JavaScript 模块提供，这些模块在模块评估后客户端注入样式，而壳层中没有对应的 `<link>` 标签。在流媒体模式下，浏览器会在这些样式注入模块运行之前开始绘制流媒体 DOM，因此由 SFC 定义的样式会短暂地未加样式显示。

变通方案：将影响初始绘制的样式放在通过 `css: ['~/assets/main.css']` 注册的全局 CSS 文件中。全局 CSS 文件会以 `<link rel="stylesheet">` 的形式出现在壳体的 `<head>` 中，并在页面内容流之前应用。SFC `<style>` 块仍可用于不阻碍初始绘制的组件级样式。

生产环境构建会将所有样式提取到真实的 CSS 文件中（或通过 `features.inlineStyles` 内联），因此此规则仅适用于 `nuxt dev`。可通过 `nuxt build && nuxt preview` 验证流式视觉效果。
::

::warning
**嵌套异步组件的生产环境 FOUC 处理：**渲染器会在壳体之后直接发送的块中内联路由 CSS。它只能内联那些在此时点已注册模块的组件样式：页面、布局以及直接位于 `<Suspense>` 边界内的任何异步组件（Vue 在渲染开始时会立即实例化这些组件）。

如果一个异步组件在另一个异步组件内部被渲染，则只有在其父组件解析后，第一个块流出来之后才会实例化一次。其 SFC `<style>` 块会错过壳体之后的样式块，而是会在关闭的 HTML 中由组件自身的 DOM 后面发出。浏览器会在最终块到达之前不绘制该组件的样式。

通过将影响初始绘制的样式放在深度嵌套的异步组件中之外，可以避免这种情况：

- 将影响初始绘制的样式放在全局 CSS 文件中（`css: ['~/assets/main.css']`）；这些样式会到达壳体 `<head>`。
- 使用工具类进行样式设计（Tailwind、UnoCSS）：工具类 CSS 存在于入口样式表中，而非每个组件内的 `<style>` 块中。
- 将拥有影响初始绘制的 `<style>` 的异步组件直接放在 `<Suspense>` 边界下，而不是嵌套在另一个异步父组件内部。
- 或者选择不启用流式传输，使用 `routeRules: { '/path': { streaming: false } }`。

嵌套异步组件上的非影响初始绘制的 scoped 样式是可行的：短暂的显示仅对重要内容有效。
::
