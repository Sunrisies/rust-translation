**构建器**是 Nuxt 负责打包应用程序的部分。Nuxt 提供了三个官方构建器：[Vite](https://vite.dev)（默认）、[webpack](https://webpack.js.org) 和 [Rspack](https://rspack.dev)，你可以通过 [`builder`](/docs/api/nuxt-config#builder) 选项选择其中一个，也可以自己编写。

本指南解释了构建器在 Nuxt 构建中的角色、构建器必须满足的契约以及如何编写构建器。

::note
编写构建器是一个高级主题。大多数应用不需要自定义构建器；如果你只想影响打包过程，使用注册打包器的[模块](/docs/guide/modules)通常是正确的选择。
::

## 构建器的作用

Nuxt 将**要构建的内容**与**构建方式**分开处理。

Nuxt 核心（在 [How Nuxt Works](/docs/guide/going-further/internals）中描述的 `nuxt` 上下文）和你的模块会生成虚拟应用程序：入口点、路由表、插件、组件注册表以及位于 `#build` 下的[虚拟文件系统](/docs/guide/going-further/internals#the-nuxt-interface)。构建器将这种虚拟应用程序转换为实际的 JavaScript 和 CSS 包，在开发过程中运行开发服务器来提供并热重载这些文件。

具体来说，构建器负责：

- 打包**客户端**构建（浏览器包），当启用 SSR 时，还打包**服务器**构建（SSR 应用入口）。
- 生成服务器运行时所需的文件以进行渲染和 hydrate：客户端清单、组件样式映射等（参见 [Build 输出契约](#the-build-output-contract)）。
- 在开发过程中，暴露开发服务器并在构建发生变化时触发重新加载。

可部署的服务器本身是由 [Nitro](https://nitro.build) 通过 `@nuxt/nitro-server` 生成的，而非由构建器生成。构建器通过类型化的契约将输出结果传递给 Nitro，Nitro 则将这些输出打包到最终的 `.output` 中。

## 构建器接口

构建器是一个实现 `NuxtBuilder` 接口的对象。唯一必需的方法是 `bundle`：

```ts
import type { Nuxt } from '@nuxt/schema'

export interface NuxtBuilder {
  bundle: (nuxt: Nuxt) => Promise<void>
  /**
   * Optional. When the user opts in via `experimental.watcher: 'builder'`,
   * Nuxt calls this instead of starting its own dev file watcher, letting
   * the builder reuse its own watcher. The builder should register a
   * `nuxt.hook('close', ...)` to clean up.
   */
  setupWatcher?: (nuxt: Nuxt) => Promise<void> | void
}
```

Nuxt 通过 [`builder`](/docs/api/nuxt-config#builder) 选项解析当前使用的构建器。它接受一种模块标识符，该模块默认导出一个 `NuxtBuilder`，或者一个内联对象。

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  // a package that exports `{ bundle }`
  builder: '@nuxt/vite-builder',
})
```

```ts [nuxt.config.ts]
import type { NuxtBuilder } from '@nuxt/schema'

const myBuilder: NuxtBuilder = {
  async bundle (nuxt) {
    // ...
  },
}

export default defineNuxtConfig({
  builder: myBuilder,
})
```

在 `nuxt build` 和 `nuxt dev` 过程中，Nuxt 会在虚拟应用生成且 `build:before` 钩子触发后，调用 `bundle(nuxt)` 一次。Nuxt 对你的 `bundle` 进行封装，使得任何抛出的错误都能自动触发 `build:error` 钩子。

::note
在 Nuxt 的其他部分中，只有三个官方构建器指定符（`@nuxt/vite-builder`、`@nuxt/webpack-builder`、`@nuxt/rspack-builder`）被识别为构建器特定的行为。自定义构建器仍然通过以下描述的通用契约来工作。
::

## 构建生命周期

当你运行 [`nuxt build`](/docs/api/commands/build) 或 [`nuxt dev`](/docs/api/commands/dev) 时，Nuxt 会：

1. 创建 `nuxt` 上下文并运行模块，填充 `nuxt.options` 和构建钩子。
2. 将虚拟应用（模板、路由表、插件）生成到 `#build` 虚拟文件系统中。
3. 触发 `build:before`。
4. 解析构建器并调用 `builder.bundle(nuxt)`。**这就是你的构建器运行的地方。**
5. 触发 `build:done`，在生产环境中关闭 `nuxt` 实例。

你的 `bundle` 实现通常根据 `nuxt.options.dev` 进行分支：

- 在**生产环境**中，它运行客户端和（如果 `nuxt.options.ssr`）服务器构建至完成，将产物写入 `nuxt.options.buildDir` 并将其注册为构建输出。
- 在**开发环境**中，它设置开发服务器，启动观察式构建，分配 `nuxt.server`，并持续运行。

构建器几乎完全通过 [钩子](/docs/api/advanced/hooks) 与 Nuxt 的其他部分进行通信。它从 `nuxt.options` 读取构建配置，并在适当时让模块扩展其打包器配置。

### 允许模块扩展打包器

模块通过 [Nuxt Kit](/docs/guide/going-further/kit) 辅助工具影响打包。构建器应遵循相关辅助工具：

- [`addVitePlugin`](/docs/api/kit/builder#addviteplugin) / [`addWebpackPlugin`](/docs/api/kit/builder#addwebpackplugin) 注册特定于打包器的插件。
- [`addBuildPlugin`](/docs/api/kit/builder#addbuildplugin) 注册一个 [unplugin](https://github.com/unjs/unplugin) 工厂，因此单个插件可以在所有构建器中使用。
- [`extendViteConfig`](/docs/api/kit/builder#extendviteconfig) / [`extendWebpackConfig`](/docs/api/kit/builder#extendwebpackconfig) 修改解析后的打包器配置。

官方构建器也会发出自己的钩子（例如 `vite:extendConfig`、`vite:serverCreated`、`webpack:config`），以便模块和 Nitro 能够参与构建过程。自定义构建器也可以发出自己的钩子，但以下构建输出契约使其能与 Nuxt 服务器运行时协同工作。

## 构建输出契约

服务器运行时（`@nuxt/nitro-server`）不知道是哪种构建器产生了应用。它通过稳定的 `nuxt/*` 子路径导入每个构建产物，而活跃的构建器则通过 `nuxt.buildOutputs` 填充这些子路径。这就是**构建输出契约**。

该契约由 `@nuxt/schema` 中的 `NuxtBuildOutputs` 接口定义：

```ts
export interface NuxtBuildOutputs {
  /** Module body re-exporting the SSR app entry. */
  serverEntry: () => string | Promise<string>
  /** Path to the emitted per-component SSR styles map, or `undefined` when no inline styles are produced. */
  ssrStyles: string | undefined
  /** Serialized client manifest for `vue-bundle-renderer`. */
  clientManifest: () => string | Promise<string>
  /** Serialized precomputed client dependency data for `vue-bundle-renderer`. */
  clientPrecomputed: () => string | Promise<string>
  /** Module body exporting the hashed entry chunk filename for import maps. */
  entryChunkName: () => string | Promise<string>
  /** Module body exporting the entry module IDs used for inline style extraction. */
  entryIds: () => string | Promise<string>
}
```

每个键都对应一个 `nuxt/*` 子路径，服务器运行时会导入该路径：

| 构建输出       | 子路径              | 导入方式                                  |
| ------------------ | -------------------- | -------------------------------------------- |
| `serverEntry`      | `nuxt/entry`         | 传递给 `createRenderer` 的 SSR 应用工厂 |
| `clientManifest`   | `nuxt/manifest`      | `vue-bundle-renderer` 客户端清单文件      |
| `clientPrecomputed`| `nuxt/precomputed`   | 预计算的依赖数据                        |
| `ssrStyles`        | `nuxt/styles`        | 每个组件的内联样式映射表              |
| `entryChunkName`   | `nuxt/entry-chunk`   | 哈希后的入口chunk 文件名（导入映射）   |
| `entryIds`         | `nuxt/entry-ids`     | 用于提取样式的入口模块 ID              |

每个 `nuxt/*` 子路径都在 `nuxt` 包中携带一个默认模板，因此服务器运行时在构建器运行之前就能进行类型检查并构建。构建器通过设置匹配的构建输出来覆盖该模板；其提供的值会在构建时替换模板。

### 两种类型的构建输出

这些键有两种形式：

- **值提供者**（`serverEntry`、`clientManifest`、`clientPrecomputed`、`entryChunkName`、`entryIds`）是返回**模块体为字符串**的函数。该字符串会被原样内联到服务器 bundles 中，因此它不能依赖磁盘上的文件位置。`serverEntry` 例如返回一个通过绝对路径引用的构建后的 SSR 入口体：

  ```ts
  setBuildOutput('serverEntry', () => `export { default } from ${JSON.stringify(serverEntryURL)}`)
  ```

- **发出的文件路径**（`ssrStyles`）是一个绝对路径（非代码），指向构建器生成的真实模块。运行时的 `nuxt/styles` 导入会解析到该文件，因此可部署的 bundler 会根据该文件的位置解析样式映射中的相对导入。将其视为代码字符串会丢失目录上下文并破坏相对导入，因此这里是一个路径：

  ```ts
  setBuildOutput('ssrStyles', resolve(serverOutDir, 'styles.mjs'))
  ```

  当构建不产生内联样式时，将 `ssrStyles` 保留为 `undefined`（其默认值），此时运行时会回退到空样式映射。

### 设置构建输出

使用 `@nuxt/kit` 提供的 [`setBuildOutput`](/docs/api/kit/builder#setbuildoutput) 辅助函数：

```ts
import { setBuildOutput } from '@nuxt/kit'

setBuildOutput('clientManifest', () => 'export default ' + serializedManifest)
```

`setBuildOutput` 会将内容写入 `nuxt.buildOutputs[key]`。在已经持有 `nuxt` 实例的打包插件中，可以直接赋值 `nuxt.buildOutputs[key]`；`setBuildOutput` 是一种便利方式，通过 [`useNuxt()`](/docs/api/kit/context#usenuxt) 来解析 `nuxt`。

提供器可以是异步的，并在服务器构建解析相应的 `nuxt/*` 导入时延迟加载。这允许构建器在早期注册提供器（例如在客户端构建完成之前），并在数据存在时返回最终值。

### 最小示例

满足生产构建契约的构建器的骨架结构：

```ts
import { resolve } from 'node:path'
import { pathToFileURL } from 'node:url'
import { setBuildOutput } from '@nuxt/kit'
import type { NuxtBuilder } from '@nuxt/schema'

export const bundle: NuxtBuilder['bundle'] = async (nuxt) => {
  const serverDir = resolve(nuxt.options.buildDir, 'dist/server')

  // ...run your client and server bundles here, writing artifacts to disk...
  const { serializedClientManifest } = await runBundles(nuxt, serverDir)

  if (nuxt.options.ssr) {
    // Point `nuxt/entry` at the built SSR app entry.
    const serverEntryURL = pathToFileURL(resolve(serverDir, 'server.mjs')).href
    setBuildOutput('serverEntry', () => `export { default } from ${JSON.stringify(serverEntryURL)}`)

    // Provide the client manifest produced by your client build.
    setBuildOutput('clientManifest', () => `export default ${serializedClientManifest}`)

    // If you emit a per-component styles map alongside its CSS chunks:
    setBuildOutput('ssrStyles', resolve(serverDir, 'styles.mjs'))
  }
}
```

::note
通常不需要提供所有键。默认设置是合理的（空清单、无内联样式、未定义的入口块），因此只需提供构建产生的内容。当 SSR 被禁用时，`serverEntry` 的默认值是无操作的应用，大多数其他输出也未被使用。
::

## 开发服务器

在开发过程中，构建器还负责提供和热重载应用。有两个重要方面：

- **`nuxt.server`** 持有正在运行的开发服务器。Nuxt 命令行工具会消耗它，官方构建器在其上暴露 `handler`（Node 请求监听器）、`fetch`（Web `fetch` 处理程序）以及 `reload` / `close` 方法。是否构建自己的开发服务器或委托给 Nitro（`nitro/builder` 的 `createDevServer`）由构建器决定。
- **重载**通过调用 `nuxt.server.reload()` 在编译完成时触发。官方构建器会发出 `compiled` 钩子（例如 `vite:compiled`、`webpack:compiled`），服务器集成会监听该钩子以进行重载。

在开发阶段，构建输出通常连接到实时内存源，而不是磁盘文件。例如，SSR 入口可能从打包器的内存输出提供，客户端清单可能从开发模块图计算得到，而不是从 `nuxt.options.buildDir` 读取。

## 向部署目标描述构建过程

服务器构建器描述其产生的内容，这样用于部署或预览构建的工具无需知道是哪个构建器在运行。该描述存储在 `nuxt.serverBuild` 中，并通过 `@nuxt/kit/internal` 中的 `useServerBuild()` 读取：

```ts
import { useServerBuild } from '@nuxt/kit/internal'

const build = useServerBuild()

build.output.root() // the project root: where a target's own config file lives
build.output.dir() // the build output directory
build.output.publicDir() // the deployable static assets within it
```

每个路径都是一个函数，因为构建器仅在初始化时解析它，因此应在服务器构建器运行后的钩子中调用它们。

描述还说明了服务器构建与应用构建之间的关系。服务器构建器设置 `buildsSeparately` 来声明其构建是独立的一次性构建（在应用构建之后执行，如 `@nuxt/nitro-server`），还是应用构建器负责所有构建且没有独立的一次性构建（如 `@nuxt/vite-server`）。需要了解此信息的人应从描述中读取，而非通过嗅探 Nitro 实例来获取。

`output.root()` 故意不是打包器的根目录。Nuxt 将 Vite 的 `root` 指向 [`srcDir`](/docs/api/nuxt-config#srcdir)，因此从打包器根目录解析其配置文件（或其中写入的路径）的部署目标会查看你的应用目录，而不是项目的根目录。从描述中读取信息的目标可以正确解析两者。

::warning
`nuxt.serverBuild` 和 `setServerBuild()` / `useServerBuild()` 辅助函数都是实验性功能，并从 `@nuxt/kit/internal` 导出。在重大版本发布前，其结构会发生变化，同时正在开发第二个服务器构建器。
::
