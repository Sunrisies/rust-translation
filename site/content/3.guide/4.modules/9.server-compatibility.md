---
title: 服务器兼容性
description: 提供一个模块，该模块能够支持 Nuxt 4 和 Nuxt 5 两种服务器运行时。
---

Nuxt 支持多种服务器运行时。Nuxt 3 和 4 针对的是 Nitro v2（`nitropack`），后者使用 `h3` v1；Nuxt 5 默认使用 Nitro v3（`nitro`），后者使用 `h3` v2。也可以基于 Web APIs 使用自定义服务器运行时，这种运行时可在所有环境中运行（`nuxt/server`）。

本指南介绍了如何编写能够在所有服务器运行时运行的模块代码。

::note
如果您的模块没有服务器代码，则无需遵循此处说明。
::

## 推荐迁移方案

[`nuxt/server`](/docs/guide/going-further/server-imports) 是基于 Web APIs 编写跨服务器运行时代码的导入接口，该模块在 Nuxt 4.6+ 中提供。使用该接口编写的代码可在 `nitropack` v2、Nitro v3 以及其他服务器构建器（如 `@nuxt/vite-server`）上运行。

### 事件处理器

如果您正在注册事件处理器，请保留当前的处理器（以兼容 Nuxt <4.6），并在其旁边使用 `nuxt/server` 注册一个新的可移植处理器，然后同时注册两者。Nuxt 会注册应用程序可以运行的实现：在 Nitro v3 和其他构建器下的可移植文件，以及在仍运行 `nitropack` v2 的宿主上运行的 v2 文件。

```ts [module.ts]
import { addServerHandler, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module' },
  setup () {
    const { resolve } = createResolver(import.meta.url)

    addServerHandler({
      route: '/api/my-module/status',
      handler: {
        nuxt: resolve('./runtime/server/status'),
        nitro2: resolve('./runtime/server/status.legacy'),
      },
    })
  },
})
```

这两个文件在导入方式上有所不同，当处理器使用 `h3` v1 辅助函数或 `nuxt/server` 处理方式不同的行为时：

::code-group

```ts [runtime/server/status.ts]
import { defineEventHandler, useRuntimeConfig } from 'nuxt/server'

export default defineEventHandler(() => ({
  version: useRuntimeConfig().public.myModule.version,
}))
```

```ts [runtime/server/status.legacy.ts]
// @ts-expect-error `#imports` is typed for the app, not the server build
import { useRuntimeConfig } from '#imports'
import { defineEventHandler } from 'h3'

export default defineEventHandler(event => ({
  version: useRuntimeConfig(event).public.myModule.version,
}))
```

::

::read-more{to="/docs/getting-started/upgrade#differences-from-h3-v1"}
请查看 `h3` v1 与 `nuxt/server` 之间的所有差异，以及应如何使用替代方案。
::

键值表示每个文件依赖的服务器 API：

| 键 | 文件导入项 | 运行位置 |
| --- | --- | --- |
| `nuxt` | 仅 `nuxt/server` | 任何服务器构建器，从 Nuxt 4.6 开始 |
| `nitro2` | `h3`、`nitropack/runtime`、`#imports` | `nitropack` v2 |
| `nitro3` | `nitro`、`nitro/h3`，单独使用或与 `nuxt/server` 一起使用 | Nitro 服务器构建器，v3 |
|---|---|---|
| `nuxt` | `nuxt/server` only | Any server builder, from Nuxt 4.6 |
| `nitro2` | `h3`, `nitropack/runtime`, `#imports` | `nitropack` v2 |
| `nitro3` | `nitro`, `nitro/h3`, alone or alongside `nuxt/server` | The Nitro server builder, v3 |

Nuxt 会根据用户使用的服务器构建器选择最合适的处理器。如果您注册的处理器无法被用户服务器构建器运行，则会在警告提示下被跳过。

::tip
仅针对需要仅由 Nitro v3 提供的 API 的代码使用 `nitro3`。使用 `nuxt/server` 可以使您的代码在未来更具可移植性。
::

采用这种模式意味着您将支持旧版本（<4.6）和新版本的 Nuxt（包括 Nuxt 5）。

::important
`handler` 的对象形式需要在模块的 `dependencies` 中包含 `@nuxt/kit@^4.6`，这是 [模块入门指南](/docs/guide/modules/getting-started) 中设置的。如果 `@nuxt/kit` 只是 `devDependency` 并在构建时保持外部依赖，或者作为 `peerDependency`，则应用程序将使用其版本，而版本低于 4.6 的版本在对象 `handler` 上会失败。
::

要对 `nuxt` 文件进行类型检查，请将 `nuxt@>=4.6` 作为 `devDependency` 安装。要对 `nitro3` 文件进行类型检查，也请安装 `nitro`。

如果您的模块自身的别名在 Nitro 两个版本上都能解析为正确的代码，请将同一文件注册到两个键中（`{ nitro2: file, nitro3: file }`），或设置 [`meta.compatibility.server`](#declaring-what-you-cannot-infer)。

在 `nitropack` v2 主机上，Nuxt 优先使用 `nitro2` 变体，因此 `nuxt` 变体仅在唯一注册时运行。请在 Nuxt 5 上测试 `nuxt` 变体。

在 Nuxt 5 的 playground 和测试环境中，h3 自动导入的 `defineEventHandler` 不可用：请从 `nuxt/server` 导入它。

### Dev Server Handlers

`addDevServerHandler` 使用相同的键，但每个变体都是您模块代码中的函数，在 Nuxt 进程中运行而不是在服务器构建中。`nuxt/server` 仅用于 [服务器代码](/docs/guide/going-further/server-imports#server-code-only)，因此即使是非延迟导入，也不要从模块代码中导入它。

相反，您应基于 web `Request` 和 `Response` 编写处理程序，在 `setup` 中从 `nuxt.options` 读取配置，并针对每个服务器 API 进行适配：

```ts [module.ts]
import { addDevServerHandler, defineNuxtModule } from '@nuxt/kit'
import { defineEventHandler, toWebRequest } from 'h3'

export default defineNuxtModule({
  meta: { name: 'my-module' },
  setup (_options, nuxt) {
    const greeting = nuxt.options.runtimeConfig.public.myModule.greeting

    function greet (request: Request) {
      const name = new URL(request.url).searchParams.get('name')
      if (!name) {
        return new Response('Missing name', { status: 400 })
      }
      return Response.json({ message: `${greeting}, ${name}!` })
    }

    addDevServerHandler({
      route: '/_my-module/greet',
      handler: {
        nuxt: event => greet(event.req),
        nitro2: defineEventHandler(event => greet(toWebRequest(event))),
      },
    })
  },
})
```

`nuxt` 变体接收 `RequestEvent` 并读取其 `event.req`，而 `nitro2` 变体使用 `toWebRequest()` 将 h3 v1 事件转换为 web 请求。由于该模块导入了 `h3` v1，请将 `h3@^1` 添加到您的模块 `dependencies` 中。

开发处理程序的路由在每个主机上并不匹配相同的路径。在 `nitropack` v2 主机上，每个变体都将其路由作为路径前缀匹配，就像 Nitro v2 那样，因此 `/_my-module` 也匹配 `/_my-module/inter.woff2`。在 Nitro v3 中，`nuxt` 和 `nitro3` 变体则完全匹配路由。

要让每个变体为以下路径提供路由，请在路由末尾添加 `/**`：

```ts [module.ts]
addDevServerHandler({
  route: '/_my-module/assets/**',
  handler: {
    nuxt: event => serveAsset(event.req),
    nitro2: defineEventHandler(event => serveAsset(toWebRequest(event))),
  },
})
```

这里 `serveAsset` 接收 `Request` 并返回 `Response`，类似于前例中的 `greet`。该路由匹配 `/_my-module/assets` 及其所有子路径，因此无需注册基础路径。在 `nitropack` v2 主机上，这需要在模块 `dependencies` 中添加 `@nuxt/kit@^4.6.1`。

在 `nitropack` v2 主机上，处理程序读取其路由基础相对路径的 `event.path`，因为 Nitro v2 会移除基础路径。对于请求 `/_my-module/assets/inter.woff2`，`event.path` 为 `/inter.woff2`。完整 URL 仍可通过 `toWebRequest()` 获取，`nuxt` 变体则从 `event.req.url` 读取。

### 服务器工具函数

如果您的模块提供了通过别名 `addServerImports` 或类型模板接收事件的工具函数，请将参数定义为来自 `nuxt/server` 的 `RequestEvent`，或者作为它读取的数据的一部分，例如 `Pick<RequestEvent, 'req' | 'context'>`。被定义为 `H3Event` 的参数仅接受一个 h3 major 级别的事件，因此该工具无法在 `nuxt/server` 处理程序中调用。

`getNitroVersion` 报告的是 Nitro 的主版本号，而不是主机运行了哪个服务器 API：具有不同 `server.builder` 的主机不会运行任何 Nitro 功能。

### 服务器插件

服务器插件也支持变体，但由于它们特定于 Nitro，因此没有通用的 `nuxt` 变体可以注册。

::tip
由于 `nitro` 中的 `definePlugin()` 和 `nitropack/runtime` 中的 `defineNitroPlugin()` 是恒等函数，您可能可以通过类型注解来替换它们，从而编写适用于 `nitro2` 和 `nitro3` 的可移植代码。
::

```ts [module.ts]
import { addNitroPlugin, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module' },
  setup () {
    const { resolve } = createResolver(import.meta.url)

    addNitroPlugin({
      nitro2: resolve('./runtime/server/plugin.legacy'),
      nitro3: resolve('./runtime/server/plugin'),
    })
  },
})
```

### 其他变体

对于指向服务器代码的任何其他内容，例如别名、类型模板或读取服务器事件的应用插件，您可以使用 `resolveServerVariant` 来确定适合当前 Nuxt 版本的变体，或者如果它不运行任何功能，则设置为 `undefined`。

`addServerImports` 在 `from` 中接受相同的变体。

```ts [module.ts]
import { addServerImports, createResolver, defineNuxtModule, resolveServerVariant } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module' },
  setup (_options, nuxt) {
    const { resolve } = createResolver(import.meta.url)

    const someServerFile = resolveServerVariant({
      nuxt: resolve('./runtime/server'),
      nitro2: resolve('./runtime/server.legacy'),
    })

    if (someServerFile) {
      nuxt.options.alias['#my-module/server'] = someServerFile
    }

    addServerImports({
      name: 'verifyToken',
      from: { nuxt: resolve('./runtime/verify'), nitro2: resolve('./runtime/verify.legacy') },
    })
  },
})
```

如果使用 `nitropack` v2 运行，`nitro2` 将始终优先于 `nuxt`；如果使用 `nitro` v3 运行，`nitro3` 将始终优先于 `nuxt`。因此，如果您需要测试 `nuxt` 变体，请在测试环境中将 `server.builder` 设置为非 Nitro 的构建器，例如 `@nuxt/vite-server`。

### 声明无法推断的内容

Nuxt 通过读取已注册文件的导入项来决定使用哪个 API，因此您无需声明兼容性。但如果这还不够，您可以设置 `meta.compatibility.server`：

```ts [module.ts]
export default defineNuxtModule({
  meta: {
    name: 'my-module',
    compatibility: { server: 'nuxt' },
  },
})
```

如果无法确定，代码将被视为 `nitro2`。

### 为运行时配置和事件定义类型

要为模块添加的运行时配置键定义类型，请扩展 `nuxt/schema` 中的 `RuntimeConfig`（或 `PublicRuntimeConfig`）。然后这些键在 `nuxt`、`nitro2` 和 `nitro3` 文件中都被定义类型。

```ts [module.ts]
declare module 'nuxt/schema' {
  interface RuntimeConfig {
    myModule: { apiKey: string }
  }
}
```

特定于构建器的类型，例如 `useRequestEvent()` 中的 `H3Event` 或 `nitro:config` hook 中的完整 Nitro 配置，来自生成的 `.nuxt/nuxt.d.ts`。如果没有这些文件，它们将解析为与构建器无关的类型（`RequestEvent` 和简化的 Nitro 配置）。接受针对 `RequestEvent` 的事件的类型工具可以支持任何服务器构建器。

### 插件、存储和缓存

基于服务器插件、存储或缓存构建的模块没有 `nuxt` 变体，因为 `nuxt/server` 不涵盖这些领域。现在将文件注册为 `nitro2`，在迁移时添加 `nitro3` 变体。

## 与 Nitro 相关的代码

`nuxt/server` 涵盖了请求和响应处理：处理器、错误、路由器参数、查询和正文读取及验证、头部信息、CORS、Cookie、会话、重定向、路由规则、运行时配置、应用配置、使用 `serverFetch()` 的进程内获取以及使用 `useServerHooks()` 的运行时钩子。但 Nitro 涵盖的范围更广，因此如果需要在这些领域使用功能，可能需要在 `nitro2` 或 `nitro3` 文件中使用 Nitro 自带的导入。

请使用文件所针对的版本标识。导入 `nitro/*` 的文件被视为 Nitro 3 代码，因此 `nitro2` 文件必须导入 `h3` 和 `nitropack/*`：

| 领域 | `nitro2` 文件中 | `nitro3` 文件中 |
| --- | --- | --- |
| 存储：`useStorage()` 及其驱动配置 | `nitropack/runtime` | `nitro/storage` |
| 缓存：`defineCachedEventHandler()`、`defineCachedFunction()` | `nitropack/runtime` | `nitro/cache` |
| 服务器插件 | 来自 `nitropack/runtime` 的 `defineNitroPlugin()` | 来自 `nitro` 的 `definePlugin()` |
| Nitro 自带的运行时钩子，如 `request` 和 `error` | 来自 `nitropack/runtime` 的 `useNitroApp().hooks` | 来自 `nitro/app` 的 `useNitroHooks()` |
| 惰性处理器：`lazyEventHandler()` | `h3` | `nitro/h3` |

`nuxt/server` 也不支持任务。

::

## Nitro v3 中的重要变化

如果仅发布 `nitro2` 文件，它将在 Nuxt 5 通过 Nitro v2 兼容层继续运行，该信息可在 [Nuxt 5 模块服务器兼容性指南](https://nuxt.com/docs/5.x/guide/modules/server-compatibility) 中找到，同时还有与 Nitro v3 相关的行为变化。
