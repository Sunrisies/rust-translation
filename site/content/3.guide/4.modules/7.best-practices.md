力量伴随责任。虽然模块非常强大，但在编写模块时，请记住一些最佳实践，以保持应用程序的性能并提升开发者的体验。

## 处理异步设置

如我们所见，Nuxt 模块可以是异步的。例如，您可能希望开发一个需要获取 API 或调用异步函数的模块。

但是，请注意异步行为，因为 Nuxt 会在进入下一个模块并开始开发服务器、构建过程之前等待您的模块完成设置。建议将耗时的逻辑延迟到 Nuxt hooks 中执行。

::warning
如果您的模块设置耗时超过 **1 秒**，Nuxt 会发出警告。
::

## 为导出添加前缀

Nuxt 模块应为任何暴露的配置、插件、API、组合式函数、组件或服务器路由提供明确的前缀，以避免与其他模块、Nuxt 内部功能或用户定义代码产生冲突。

理想情况下，应以模块名称作为前缀。例如，如果您的模块名为 `nuxt-foo`：

| 类型 | ❌ 避免 | ✅ 推荐 |
| --- | --- | --- |
| 组件 | `<Button>`、`<Modal>` | `<FooButton>`、`<FooModal>` |
| 组合式函数 | `useData()`、`useModal()` | `useFooData()`、`useFooModal()` |
| 服务器路由 | `/api/track`、`/api/data` | `/api/_foo/track`、`/api/_foo/data` |

### 服务器路由

对于服务器路由尤其重要，因为常见的路径如 `/api/auth`、`/api/login` 或 `/api/user` 很可能已被应用程序使用。

使用基于模块名称的唯一前缀：
- `/api/_foo/...`（使用下划线前缀）
- `/_foo/...`（用于非 API 路由）

## 使用生命周期钩子

当您的模块需要执行一次性设置任务（如生成配置文件、设置数据库或安装依赖）时，应使用生命周期钩子，而不是在主要的 `setup` 函数中运行逻辑。

```ts
import { addServerHandler, defineNuxtModule } from 'nuxt/kit'
import { isLess } from 'verkit'

export default defineNuxtModule({
  meta: {
    name: 'my-database-module',
    version: '1.0.0',
  },
  async onInstall (nuxt) {
    // One-time setup: create database schema, generate config files, etc.
    await generateDatabaseConfig(nuxt.options.rootDir)
  },
  async onUpgrade (nuxt, options, previousVersion) {
    // Handle version-specific migrations
    if (isLess(previousVersion, '1.0.0')) {
      await migrateLegacyData()
    }
  },
  setup (options, nuxt) {
    // Regular setup logic that runs on every build
    addServerHandler({ /* ... */ })
  },
})
```

这种模式可避免每次构建时的不必要的工作，并提供更好的开发者体验。更多详情请参阅 [生命周期钩子文档](/docs/api/kit/modules#using-lifecycle-hooks-for-module-installation-and-upgrade)。

## 支持 TypeScript

Nuxt 拥有一流的 TypeScript 集成，以提供最佳的开发者体验。

即使不直接使用 TypeScript，通过暴露类型并使用 TypeScript 开发模块也能为用户带来优势。

## 使用 ESM 语法

Nuxt 依赖原生 ESM。请阅读 [Native ES Modules](/docs/guide/concepts/esm) 以获取更多信息。

## 记录你的模块文档

在 README 文件中考虑记录模块的使用说明：

- 为什么使用这个模块？
- 如何使用这个模块？
- 这个模块的功能是什么？

链接到集成网站和文档总是个好主意。

## 提供演示示例

制作一个包含你模块和 [StackBlitz](https://nuxt.new/s/v4) 的简化复现示例是一个良好的实践，并将其添加到你的模块 README 中。

这不仅为潜在用户提供了快速简便的方式来测试该模块，还让他们能够轻松构建简单的复制品，在遇到问题时可以直接发送给你。

## 保持与版本无关

Nuxt、Nuxt Kit 和其他新工具都是考虑到前后兼容性而设计的。

请使用“X for Nuxt”而不是“X for Nuxt 3”，以避免生态系统中的碎片化问题，并优先使用 `meta.compatibility` 来设定 Nuxt 版本限制。

## 遵循 starter 规范

模块 starter 包含一组默认的工具和配置（例如 ESLint 配置）。如果你计划开源你的模块，坚持使用这些默认设置可以确保你的模块与其他 [社区模块](/modules) 具有一致的编码风格，从而更容易获得贡献。
