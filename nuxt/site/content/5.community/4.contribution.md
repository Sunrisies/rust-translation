你可以通过多种不同的方式为 Nuxt 生态系统做出贡献。

## 生态系统

Nuxt 生态系统包含许多不同的项目和组织：

* [nuxt/](https://github.com/nuxt) - Nuxt 框架本身的核心仓库。[**nuxt/nuxt**](https://github.com/nuxt/nuxt) 包含 Nuxt 框架（包括版本 2 和 3）。
* [nuxt-modules/](https://github.com/nuxt-modules) - 由社区贡献并维护的模块和库。有一个[将模块迁移到 nuxt-modules 的过程](/docs/guide/modules/ecosystem)。虽然这些模块有独立的维护者，但它们并不依赖单一个人。
* [unjs/](https://github.com/unjs) - 许多此类库在 Nuxt 生态系统中被使用。它们被设计成通用库，不依赖于特定框架和环境。我们欢迎其他框架和项目对它们的贡献和使用。

## 如何贡献

### 处理问题并在讨论中提供帮助

查看你想要帮助的项目的问题和讨论。例如，以下是 Nuxt 的[问题板](https://github.com/nuxt/nuxt/issues)和[讨论区](https://github.com/nuxt/nuxt/discussions)。帮助其他用户、分享解决方案、创建复现示例，甚至稍微探究一下错误并分享你的发现，都能产生巨大的影响。

### 创建问题

感谢你花时间创建问题！❤️

* **报告错误**：请查看[我们的指南](/docs/community/reporting-bugs)以了解在打开问题之前可以做的几件事。

* **功能请求**：确认没有现有问题或讨论涉及你设想的功能范围。如果该功能属于 Nuxt 生态系统的其他部分（如某个模块），请先考虑在那里提出功能请求。如果你设想的功能是通用的，或者 API 并不完全清晰，可以考虑在**Ideas**部分开启讨论，以便与社区进行讨论。

我们将尽力遵循我们的[内部问题决策流程图](https://mermaid.live/view#pako:eNqFlE1v2zAMhv8K4UuToslhx2Bo0TZt12Edhm7YMCAXWqJtorLk6qOpkfS_j7KdfpyWQ-BQr8mHL6nsCuU0FauiMm6rGvQRfq03FuRzvvvTYIQHthpcBT_ugQNwPHuZjheLxf4i1VDx8x4udrf5EBCOQvSsYg4ffS79KS9pmX9QALTgyid2KYB7Ih-4bmKWbDk2YB0E1gRUVaRi-FDmmjAmT3u4nB3DmoNKIUA1BsGSohA49jnVMQhHbDh_EZQUImyxh-gAtfaiG-KWSJ-N8nt6YtpCdgEeE5rXPOdav5YwWJIJU7zrvNADV9C7JBIyIC07Wxupkx3LFQ5vCkguRno5f9fP2qnUko0Y2dk9rGdvHAa9IIhVGlCp5FFNPN-ce4DKeXBd53xMliOLp9IZtyORQVsnrGm-WJzejtUu5fFqdr5FGQ3bLslYvGthjZbJTLpReZG5_lLYw7XQ_CbPVT92ws9gnEJj-v84dk-PiaXnmF1XGAaPsOsMKywNvYmG80ZohV8k4wDR9_N3KN_dHm5mh1lnkM5FsYzRfNiTvJoT5gnQsl6uxjqXLhkNQ9syHJ0UZZ8ERUIlNShr6N8gZDEliR-ow7QZa0fhY4LoHLRo-8N7ZxPwjRj5ZZYXpvOSNs9v3Jjs8NXB4ets92xan3zydXZHvj64lKMayh4-gZC1bjASW2ipLeWuzIuToiXfImu5rbucclMIc0ubYiWPGv3DptjYF9Fhiu5nb1Wxij7RSZE6jZHWjLXHtlhVaIJESXN0_m68_sO_wMs_oO9gyg) 来回应问题。

### 提交拉取请求

我们始终欢迎拉取请求！❤️

#### 开始之前

在修复错误之前，我们建议您先检查**是否存在描述该错误的 issue**，因为可能是文档问题，或者有一些背景信息有助于了解。

如果您正在开发功能，我们建议**先打开一个功能请求 issue**，与维护者讨论该功能是否值得开发以及其设计如何。这既能节省维护者和贡献者的时间，也能使功能更快地发布。在通过拉取请求构建功能之前，该 issue **应由框架团队成员确认**。

对于拼写错误修复，建议将多个拼写错误修复合并到同一个拉取请求中，以保持更整洁的提交历史。

对于对 Nuxt 本身的较大更改，我们建议您首先[创建 Nuxt 模块](/docs/community/contribution#create-a-module)并在那里实现功能。这样可以快速进行概念验证。然后您可以[以讨论形式创建 RFC](/docs/community/contribution#make-an-rfc)。随着用户使用并收集反馈，该方案可以进一步优化，既可以加入 Nuxt 核心，也可以作为独立模块继续使用。

#### 提交规范

我们使用[Conventional Commits](https://www.conventionalcommits.org)作为提交消息，这[允许根据提交自动生成 changelog](https://github.com/unjs/changelogen)。如果您不熟悉该规范，请阅读相关指南。

请注意，`fix:` 和 `feat:` 用于**实际代码更改**（可能影响逻辑）。对于拼写错误或文档更改，请使用 `docs:` 或 `chore:`：

* ~~`fix: typo`~~ -> `docs: fix typo`

如果您在像 `nuxt/nuxt`这样的单仓库项目中工作，请确保您在括号中指定提交的主要范围。例如：`feat(kit): add 'addMagicStuff' utility`。

#### 创建拉取请求

如果您不知道如何提交拉取请求，我们建议阅读[指南](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-a-pull-request)。

在发送拉取请求时，确保您的 PR 标题也遵循[提交规范](/docs/community/contribution#commit-conventions)。

如果您的 PR 修复了问题或解决了现有问题，请确保在 PR 描述中提及这些内容。

在单个 PR 中包含多个提交是可以的；您无需进行重新基或强制推送，因为在合并时我们将使用 `Squash and Merge` 将多个提交合并为 하나的提交。

我们不会添加任何提交钩子以允许快速提交。但在创建拉取请求之前，您应确保所有 lint/test 脚本通过。

一般来说，请确保拉取请求中没有_不相关_的更改。例如，如果您的编辑器对您编辑的文件中的其他部分进行了空格或格式调整，请恢复这些更改，以便更清楚地显示您的 PR 更改内容。同时，请避免在一个 PR 中包含多个不相关的功能或修复。如果可以分开，最好创建多个 PR 进行评审和合并。一般来说，一个 PR 应只做_一件事_。

#### 一旦您创建了拉取请求

一旦您创建了拉取请求，我们将尽力及时审查它。

如果我们将其分配给维护者，那么意味着该人员将特别注意审查它，并实施任何必要的更改。

如果我们在 PR 上要求更改，请忽略红色文本！这并不意味着我们认为它是个糟糕的 PR——这只是一种快速了解多个拉取请求状态的方式。

如果我们将 PR 标记为‘待处理’，这意味着我们可能还有其他任务需要审查该 PR——这只是内部提醒，并不一定反映该 PR 是否是个好主意。我们将尽力通过评论解释待处理状态的原因。

### AI辅助贡献

我们欢迎在为 Nuxt 贡献代码时合理使用 AI 工具，但要求所有贡献者遵循 [两个核心原则](https://roe.dev/blog/using-ai-in-open-source)。

#### 永远不要让 LLM 代你发言

* 所有评论、问题和拉取请求描述都应使用你自己的语言撰写
* 我们更重视清晰的人类沟通，而非完美的语法或拼写
* 避免复制粘贴没有反映你自身理解的 AI 生成的摘要

#### 永远不要让 LLM 替你思考

* 你可以自由使用 AI 工具来生成代码或探索想法
* 只提交你完全理解且能够解释的贡献
* 贡献应反映你自己的推理和解决问题的方式

我们的目标是确保质量，并维持与真实人士协作和沟通的乐趣。如果你有关于改进 Nuxt 社区 AI 政策的建议，我们非常欢迎！❤️

### 创建模块

如果你用 Nuxt 构建了一些很棒的东西，为什么不 [将其提取为模块](/docs/guide/modules)，以便与他人共享呢？我们已经有了 [许多优秀的模块](/modules)，但还有更多空间可以扩展。

如果你在构建过程中需要帮助，可以 [向我们咨询](/docs/community/getting-help)。

### 提交 RFC

我们强烈建议 [先创建模块](/docs/community/contribution#create-a-module)，以测试新的重要功能并获得社区采纳。

如果你已经这么做了，或者创建新模块并不合适，那么请首先创建一个新的讨论。确保尽可能清晰地说明你的思路。包含代码示例或新 API 的函数签名。引用现有的问题或痛点并给出示例。

如果我们认为这应该作为 RFC 处理，我们将将类别改为 RFC，并更广泛地发布以收集反馈。

然后，RFC 将经历以下阶段：

* `rfc: active` - 目前开放评论
* `rfc: approved` - 由 Nuxt 团队批准
* `rfc: ready to implement` - 已创建问题并分配实施
* `rfc: shipped` - 已实施
* `rfc: archived` - 未批准，但存档以供将来参考

### 生态系统中的规范

以下规范在 `nuxt/` 组织中是 _必须遵循的_，也建议生态系统中的其他维护者遵守。

#### 模块规范

模块应遵循 [Nuxt 模块模板](https://github.com/nuxt/starter/tree/module)。更多信息请参见 [模块指南](/docs/guide/modules)。

#### 使用 Core `unjs/` 库

我们推荐以下在整个生态系统中使用的库：

* [pathe](https://github.com/unjs/pathe) - 通用路径工具（替代 node `path`）
* [ufo](https://github.com/unjs/ufo) - URL 解析和拼接工具
* [obuild](https://github.com/unjs/obuild) - 基于滚动加载的构建系统
* ... 更多内容请查看 [unjs/](https://github.com/unjs) 组织！

#### 使用 ESM 语法，默认设置为 `type: module`

Nuxt 生态系统中的大多数可以直接使用 ESM。通常我们建议避免使用 CJS 特有的代码，如 `__dirname` 和 `require` 语句。您可以在 [这里阅读更多关于 ESM 的信息](/docs/guide/concepts/esm)。

#### 什么是 Corepack

[Corepack](https://github.com/nodejs/corepack) 确保您在运行相应命令时使用正确的包管理器版本。项目在 `package.json` 中可能包含 `packageManager` 字段。

在具有以下配置的项目中，Corepack 将安装 `v7.5.0` 版本的 `pnpm`（如果您尚未安装），并使用它来运行您的命令。

```jsonc [package.json]
{
  "packageManager": "pnpm@7.5.0"
}
```

#### 使用 ESLint

我们使用 [ESLint](https://eslint.org) 进行代码检查和格式化，使用 [`@nuxt/eslint`](https://github.com/nuxt/eslint)。

##### IDE 设置

我们建议使用 [VS Code](https://code.visualstudio.com) 配合 [ESLint 扩展](https://marketplace.visualstudio.com/items?itemName=dbaeumer.vscode-eslint)。如果您愿意，可以在保存编辑代码时启用自动修复和格式化：

```json [settings.json]
{
  "editor.codeActionsOnSave": {
    "source.fixAll": "never",
    "source.fixAll.eslint": "explicit"
  }
}
```

#### 不使用 Prettier

由于 ESLint 已配置用于格式化代码，无需使用 Prettier 重复功能。要格式化代码，可以运行 `yarn lint --fix`、`pnpm lint --fix`、`bun run lint --fix` 或 `deno run lint --fix`，或参考 [ESLint 部分](/docs/community/contribution#use-eslint) 了解 IDE 设置方法。

如果您在编辑器中安装了 Prettier，建议在处理项目时禁用它以避免冲突。

#### 包管理器

我们推荐 `pnpm` 作为模块、库和应用的包管理器。

启用 Corepack 非常重要，以确保您使用的包管理器与项目版本一致。Corepack 已内置于新版本的 Node.js 中，从而实现无缝的包管理器集成。

要启用它，请运行

```bash [Terminal]
corepack enable
```

您只需在计算机上安装 Node.js 后进行一次操作即可。

## 文档风格指南

文档是 Nuxt 的重要组成部分。我们的目标是打造一个直观的框架——其中重要的一部分就是确保开发体验和文档在整个生态系统中都表现完美。👌

以下是一些可能有助于改进文档的建议：

### 语言

* 使用**美式英语**拼写（_behavior_ 而非 _behaviour_，_customize_ 而非 _customise_）。

* 使用官方大小写方式书写工具和项目名称，即使 npm 包名称是小写形式（例如 _PostCSS_ 而非 _postcss_，_Vite_ 而非 _vite_，_ESLint_ 而非 _eslint_）。仅在引用包本身时，在反引号中使用小写的 npm 包名称，例如在安装说明中。

  ::caution{icon="i-lucide-circle-x"}
  Nuxt 自带支持 PostCSS。
  ::

  ::tip{icon="i-lucide-circle-check"}
  Nuxt 自带支持 PostCSS。您无需手动安装 `postcss`。
  ::

  ::note
  常见的工具名称大小写由 [case police](https://github.com/antfu/case-police) 在运行 `pnpm lint:docs` 时自动检查。
  ::

### 标题

* 遵循芝加哥标题式的大小写规则：首词、尾词以及所有主要单词（名词、动词、形容词、副词、代词）均大写；冠词、并列连词和介词无论长度如何均小写（例如 a, and, or, with, from, and to）。如有疑问，[capitalizemytitle.com](https://capitalizemytitle.com/style/Chicago) 可以提供帮助。

  ::caution{icon="i-lucide-circle-x"}
  如何为文档贡献内容
  ::

  ::tip{icon="i-lucide-circle-check"}
  如何为文档做出贡献
  ::

* 标题中的代码保持其原始大小写，不计入大写规则中（例如 _在组件中使用 `useFetch`_）。

### 内联代码

将以下内容用反引号包裹，使其作为内联代码显示：

* 文件名称和路径：`nuxt.config.ts`，`server/api/`
* npm 包名称：`@nuxt/kit`，`postcss`
* 配置键、选项和值：`ssr: false`，`css` 选项
* 代码标识符如函数、组合式函数、组件、变量和类型：`useFetch`，`<NuxtLink>`，`defineNuxtConfig`
* 终端命令：`npx nuxt init`

不要使用反引号来标注工具、项目或一般概念的名称（在指代该工具时，请使用 _Vite_，而不是 `vite`）。

### 代码示例

* 在代码块中添加文件名，以便读者知道代码属于哪个文件。如果代码不属于特定文件（例如shell命令），请使用如 `[Terminal]` 这样的描述性标签。

  ````markdown
  ```ts [nuxt.config.ts]
  export default defineNuxtConfig({
    ssr: false,
  })
  ```
  ````

* 使示例可复制粘贴。包含必要的导入语句，并避免在代码中出现读者需要粘贴到项目中的 `...` 等占位符。读者应能够将示例复制到项目中，并且只需少量修改即可正常运行。

### 链接

* 在链接到其他文档页面时，使用不包含域或版本段的相对路径： `/docs/getting-started/installation` 而不是 `/docs/4.x/getting-started/installation` 或 `https://nuxt.com/docs/4.x/getting-started/installation`。nuxt.com 会插入页面所基于分支的版本段，因此同一个链接在各个版本中都能正确解析，并且可以在不同分支之间不修改地提取文档内容。

* 只有在有意指代_另一个_版本的文档时（例如路线图中的发布表），才写入版本段。在这种情况下，请使用完整URL：`https://nuxt.com/docs/3.x/getting-started/introduction`，这样意图在审核中就能清晰明了。

* 在链接外部资源时，链接到最终URL而非重定向链接。你可以检查：

  ```bash [Terminal]
  curl -sILo /dev/null -w '%{http_code} %{url_effective}\n' https://example.com/some-page
  ```

  这会跟随任何重定向链并显示最终状态和URL。请求的URL处于 `200` 状态意味着链接正常。如果最终URL不同，则链接到该URL。

### 语气

我们力求保持友好且专业的语气。直接对读者（“你”）写作，简洁明了，并假设对方是真诚的：读者来自不同的背景和经验水平，因此避免使用可能让任何人感到被轻视的语言。热情是可以的——文档可以具有个性——但清晰永远是最重要的。

### 写作风格

* 尽可能避免使用 _simply_、_just_、_obviously..._ 这类主观词汇。

  请记住，读者可能有不同的背景和经验。因此，这些词汇无法传达意义且可能有害。

  ::caution{ icon="i-lucide-circle-x"}
  只需确保该函数返回一个 Promise。
  ::

  ::tip{icon="i-lucide-circle-check"}
  确保该函数返回 [Promise](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise)。
  ::

* 建议使用 [主动语态](https://developers.google.com/tech-writing/one/active-voice)。

  ::caution{icon="i-lucide-circle-x"}
  Nuxt 会抛出错误。
  ::

  ::tip{icon="i-lucide-circle-check"}
  Nuxt 会引发错误。
  ::

* 在记录 API 页面时，包括组合式函数、工具函数和组件，请使用一致的章节名称和顺序。仅包含适用的章节：

  1. **Usage**：说明如何使用该 API，并涵盖常见的使用场景。
  2. **Type**：提供相关的 TypeScript 声明。
  3. **Parameters**：描述每个输入参数，包括其类型、默认值及可用选项。
  4. **Return Values**：描述返回值及其类型。
  5. **Example**：展示一个实际示例。

  使用这些精确的章节名称。例如，使用 `Parameters` 而不是 `Params`，使用 `Example` 而不是 `Examples`。

* 在记录 API 页面（组合式函数、工具函数、组件）时，当引入某个功能或工具时，添加 **最小 Nuxt 版本**，以便读者知道需要哪个版本。

  使用两级标题：

  * **全局（整页）：** 在前文信息中添加 `minimalVersion: "3.9"`（不添加“v”前缀）。文档布局会自动从该字段显示版本徽章，格式为 `vX.Y`（例如 `v3.9`、`v3.15`）。
  * **局部（特定选项或功能）：** 在选项或章节旁边添加小徽章：`:badge[v3.8]{color="info" size="xs" class="align-middle"}`（例如，在 useFetch 中的 `getCachedData`，或在 callOnce 中的 `navigation` 模式）。

  要找到版本信息，可以查看源代码中 JSDoc 的 `@since` 字段、[发布说明](https://github.com/nuxt/nuxt/releases)或[Nuxt 博客](https://nuxt.com/blog)。
