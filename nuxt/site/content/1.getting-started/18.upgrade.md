## 升级 Nuxt

### 最新发布版本

要将 Nuxt 升级到 [最新发布版本](https://github.com/nuxt/nuxt/releases)，请使用 `nuxt upgrade` 命令。

::code-group{sync="pm"}

```bash [npm]
npx nuxt upgrade
```

```bash [yarn]
yarn nuxt upgrade
```

```bash [pnpm]
pnpm nuxt upgrade
```

```bash [bun]
bun x nuxt upgrade
```

```bash [deno]
deno x nuxt upgrade
```

::

### 夜间发布通道

要在发布前使用最新的 Nuxt 构建并测试新功能，请阅读 [夜间发布通道](/docs/guide/going-further/nightly-release-channel) 指南。

## 测试 Nuxt 5

Nuxt 5 **当前处于开发阶段**。从 Nuxt 4.2 开始，您可以通过将 `future.compatibilityVersion` 设置为 `5` 来测试许多破坏性变更。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  future: {
    compatibilityVersion: 5,
  },
})
```

在您的 Nuxt 配置中设置默认选项，然后改为启用 Nuxt 5 的行为。在 Nuxt 4 中包括以下内容：

- **Vite 环境 API**：`experimental.viteEnvironmentApi` 被启用，改变了 Vite 插件的注册和配置方式
- **区分大小写的路由**：页面路由与 URL 的大小写完全匹配，与 Nitro 一致，因此 `/About` 不再匹配 `pages/about.vue`
- **标准化页面名称**：页面组件名称 [与路由名称一致](/docs/guide/going-further/experimental-features#normalizepagenames)，以确保 `<KeepAlive>` 行为的一致性
- **可序列化页面元信息**：`experimental.extractSerializablePageMeta` 在构建时提取静态可分析的 `definePageMeta` 值
- **客户端侧负载提取**：`experimental.payloadExtraction` 变为 `'client'`，将负载内联到预渲染页面的 HTML 中
- **`clearNuxtState` 重置为默认值**：`clearNuxtState` 将状态重置为 [`useState`](/docs/api/组合式函数/use-state) 的初始值，而不是设置为 `undefined`
- **非异步 `callHook`**：`callHook` 可能返回 `void`，而不总是返回 `Promise`
- **从 `navigateTo` 早期返回**：`experimental.navigateToEarlyReturn` 在重定向后阻止中间件继续执行
- **仅服务器使用的头部组合式函数**：`useServerHead`、`useServerHeadSafe` 和 `useServerSeoMeta` 不再自动导入，`unhead.legacy` 被忽略，Unhead 的旧插件不再注册，且 Capo 排序始终启用
- **PostCSS 默认关闭**：除非在 `postcss.plugins` 中启用，否则 `autoprefixer` 和 `cssnano` 将不再被配置。
- **带 key 的组合式函数需要 `source`**：没有字符串 `source` 的 [`optimization.keyedComposables`](/docs/api/nuxt-config#keyedcomposables) 条目不再通过自动导入被匹配。
- **注释节点占位符**：客户端组件使用 [注释节点而非 `<div>`](/docs/guide/going-further/experimental-features#clientnodeplaceholder) 作为 SSR 占位符。
- **类型化页面**： [`experimental.typedPages`](/docs/guide/going-further/experimental-features#typedpages) 被启用用于类型检查路由。
- **错误响应格式**： `experimental.inlineErrorRendering` 被启用，因此页面错误返回错误页面，服务器路由错误返回 JSON，[与请求头无关](https://nuxt.com/docs/5.x/getting-started/upgrade#error-format-depends-on-where-the-error-is-thrown)。
- **类型化的 `$fetch`**： [`experimental.routeTypedFetch`](/docs/guide/going-further/experimental-features#routetypedfetch) 从生成的路由类型中引入 `type` 和 `useFetch`。
- **Nitro 自动导入关闭**：服务器代码[明确导入其辅助函数](https://nuxt.com/docs/5.x/getting-started/upgrade#server-auto-imports-are-now-opt-in)，例如从 [`nuxt/server`](#moving-to-nuxtserver) 导入，而不是依赖自动导入兼容层。设置 `experimental.nitroAutoImports: true` 以保留自动导入。
- **Vue Options API 禁用**：Options API 被从客户端包中编译掉以减小其大小。
- **更严格的副作用导入**：生成的 `tsconfig.json` 启用 `noUncheckedSideEffectImports`。
- **TypeScript `baseUrl` 被忽略**：生成的 TypeScript 配置不再使用 `compilerOptions.baseUrl` 来解析 Nuxt 别名。

::note
此列表描述了 Nuxt 4 中标志的变化。Nuxt 5 本身还包含进一步的变更，这些变更无法通过任何标志启用，例如升级到 Nitro v3。
::

每种变更的迁移步骤以及升级带来的其他内容，均可在 [Nuxt 5 升级指南](https://nuxt.com/docs/5.x/getting-started/upgrade) 中查看。

## 迁移至 `nuxt/server`

从 Nuxt 4.6 开始，服务器代码可以从 [`nuxt/server`](/docs/guide/going-further/server-imports) 导入其处理程序和辅助函数，而不是从 h3 导入，因此同一文件可以在 Nuxt 4（`nitropack` v2 和 h3 v1）和 [Nuxt 5](https://nuxt.com/docs/5.x/getting-started/upgrade)（Nitro v3 和 h3 v2）上运行。

在 Nuxt 4.6 中，需要明确导入 `defineEventHandler` 以及 `nuxt/server` 中的辅助函数。相同拼写的自动导入名称属于 h3 v1，而 h3 中的 `defineEventHandler` 会将事件传递给处理程序，与 `nuxt/server` 辅助函数所读取的事件不同。

```diff [server/api/hello.ts]
+ import { defineEventHandler, getQuery } from 'nuxt/server'
+
 export default defineEventHandler((event) => {
   const { name } = getQuery<{ name?: string }>(event)
   return { message: `Hello, ${name ?? 'world'}!` }
 })
```

在 Nuxt 5 中，相同的名称会从 `nuxt/server` 自动导入，因此 Nuxt 4.6 中明确编写的导入语句仍然有效。

### h3 v1 与 Nuxt 5 的差异

| h3 v1 | `nuxt/server` |
|---|---|
| `sendRedirect(event, location)` 发送响应。 | `sendRedirect(event, location)` 返回响应体：`return sendRedirect(event, '/login')`。 |
| `getRouterParam(event, name)` 和 `getRouterParams(event)` 返回解码后的值。 | 它们返回的值与 URL 中显示的值相同。传递 `{ decode: true }` 以进行解码。
| `handleCors(event, options)` 在响应预请求时返回 `true`。 | `handleCors(event, options)` 从处理程序中返回预请求的 `Response`，或返回 `false`：`const preflight = handleCors(event, options); if (preflight) return preflight`。 |
| `handleCors` 在运行时接受单个源字符串。 | `origin` 可以是 `'*'`、`'null'`、源或模式数组，或函数：将单个源包装在数组中。`maxAge` 是秒数字符串，例如 `'86400'`，或 `false`。从 `nuxt/server` 导入 `CorsOptions` 类型。
| `readValidatedBody` 和 `getValidatedQuery` 接受验证函数。 | 它们接受 [标准模式](https://standardschema.dev)或函数。
| `createError({ statusCode, statusMessage })` | `createError({ status, statusText })` |
| `isError(error)` | `isNuxtError(error)` |
| h3 的 `useSession`、`getSession`、`updateSession` 和 `clearSession` 使用你传递的 `password` 来加密 `h3`  Cookie。 | 它们加密 `nuxt-session` Cookie，默认使用从 `appSecret` 生成的密钥。两者不可互换：一个会话对象无法用另一个来解锁。
| `useRuntimeConfig(event)` | `useRuntimeConfig()`。没有请求级别的表单。
| 全局 `$fetch` | 不属于 `nuxt/server`。使用 `serverFetch(event, path)` 调用应用的路由，该方法返回 `Response`。对于其他 URL，普通的 `fetch` 在非 2xx 状态时不抛出错误，也不解析 JSON：检查 `response.ok` 并调用 `response.json()`。
| `event.path` | `getRequestURL(event).pathname`, 或 `event.url.pathname`. |
| `event.node` | 不属于 `nuxt/server`。应使用 `event.req` 和 `event.res`。 |
| `getResponseHeader`, `setResponseHeader`, `appendResponseHeader`, `removeResponseHeader` | `event.res.headers.get()`, `.set()`, `.append()`, `.delete()` |
| `getMethod(event)`, `isMethod(event, method)`, `assertMethod(event, method)` | 比较 `event.req.method`。 |
| `readMultipartFormData(event)` | `await event.req.formData()` |
| `readRawBody(event)`, `getRequestWebStream(event)` | `await event.req.arrayBuffer()` (或 `.text()`), `event.req.body` |
| `sanitizeStatusCode` | 未提供。 |

### `nuxt/server` 之外的辅助函数

对于需要 `h3` 或 `Nitro` 辅助函数的处理器，而 `nuxt/server` 不提供的功能，例如 `readMultipartFormData`、`proxyRequest`、`useStorage` 或 `defineCachedEventHandler`，请继续从 `h3` (或 `nitropack/runtime`) 导入 `defineEventHandler` 和这些辅助函数。执行此操作的代码与服务器运行时绑定，需要在 Nuxt 5 中重新访问。

```ts [server/api/upload.post.ts]
import { defineEventHandler, readMultipartFormData } from 'h3'

export default defineEventHandler(async (event) => {
  const parts = await readMultipartFormData(event)
  return { received: parts?.length ?? 0 }
})
```

### `NUXT_E8012`

当 `nuxt/server` 的辅助函数（如 `readValidatedBody`、`getValidatedQuery`、`handleCors` 或 `useSession`）接收 `h3` 事件时，如果请求失败且 `500` 状态码的消息以 `[NUXT_E8012]` 开头，则表示该处理器是用 `h3` 的 `defineEventHandler` (通常是自动导入的版本) 定义的。请将 `defineEventHandler` 从 `nuxt/server` 导入到辅助函数所在的文件中。

### 应用密钥

`nuxt/server` 的会话辅助函数和 `deriveSecret` 读取 `runtimeConfig.appSecret`，该值通过 `NUXT_APP_SECRET` 设置。在 Nuxt 4 中，`nitropack` v2 解析环境覆盖配置，因此仅由数字组成的密钥会以数字形式传递；有关避免此情况的说明，请参阅 [应用密钥](/docs/guide/going-further/runtime-config#application-secret)。

Nuxt 4 包含重要的改进和变更。本指南将帮助您将现有的 Nuxt 3 应用迁移到 Nuxt 4。

首先，升级到 Nuxt 4：

::code-group{sync="pm"}

```bash [npm]
npm install nuxt@^4.0.0
```

```bash [yarn]
yarn add nuxt@^4.0.0
```

```bash [pnpm]
pnpm add nuxt@^4.0.0
```

```bash [bun]
bun add nuxt@^4.0.0
```


### 新的目录结构

🚦 **影响级别**：重大

Nuxt 现在默认采用新的目录结构，并具备向后兼容性（因此如果 Nuxt 检测到您使用旧结构，例如顶级 `app/pages/` 目录，则不会应用此新结构）。

👉 [查看完整 RFC](https://github.com/nuxt/nuxt/issues/26444)

#### 发生了哪些变化

- 新的 Nuxt 默认 `srcDir` 为 `app/`，大多数内容都从那里解析。
- `serverDir` 现在默认为 `<rootDir>/server`，而不是 `<srcDir>/server`。
- `layers/`、`modules/` 和 `public/` 默认相对于 `<rootDir>` 进行解析。
- 如果使用 [Nuxt Content v2.13+](https://github.com/nuxt/content/pull/2649)，`content/` 相对于 `<rootDir>` 进行解析。
- 新增了 `dir.app` 目录，这是我们查找 `router.options.ts` 和 `spa-loading-template.html` 的目录——默认位于 `<srcDir>/`。
- 新增了 [`shared/`](/docs/directory-structure/shared) 目录，用于在 Vue 应用和 Nitro 服务器之间共享代码，并支持 `shared/utils/` 和 `shared/types/` 的自动导入。

<details>

<summary>一个 v4 文件夹结构的示例。</summary>

```sh
.output/
.nuxt/
app/
  assets/
  components/
  composables/
  layouts/
  middleware/
  pages/
  plugins/
  utils/
  app.config.ts
  app.vue
  router.options.ts
content/
layers/
modules/
node_modules/
public/
shared/
  types/
  utils/
server/
  api/
  middleware/
  plugins/
  routes/
  utils/
nuxt.config.ts
```

::note
有了这个新的结构， `~` 别名现在默认指向 `app/` 目录（您的 `srcDir`）。这意味着 `~/components` 解析为 `app/components/`，`~/pages` 解析为 `app/pages/`，等等。
::

</details>

👉 更多详情，请参见[实现此更改的 PR](https://github.com/nuxt/nuxt/pull/27029)。

#### 变更原因

1. **性能问题** - 将所有代码放在仓库的根目录中会导致 `.git/` 和 `node_modules/` 文件夹被 FS 监视器扫描/包含，这在非 Mac OS 系统上会显著延迟启动。
1. **IDE 类型安全** - `server/` 及应用程序的其他部分运行在完全不同的环境中，且拥有不同的全局导入项。确保 `server/` 不在应用程序其他部分的同一文件夹内，是确保在 IDE 中获得良好自动补全的重要第一步。

:video-accordion{title="Watch a video from Vue School on the new directory structure" videoId="1031028378" platform="vimeo"}

#### 迁移步骤

1. 创建一个名为 `app/` 的新目录。
1. 将 `assets/`、`components/`、`composables/`、`app/layouts/`、`app/middleware/`、`app/pages/`、`app/plugins/` 和 `utils/` 文件夹以及 `app.vue`、`error.vue`、`app.config.ts` 移动到该目录下。如果你有 `app/router-options.ts` 或 `app/spa-loading-template.html`，这些路径保持不变。
1. 确保 `nuxt.config.ts`、`content/`、`layers/`、`modules/`、`public/`、`shared/` 和 `server/` 文件夹仍位于项目的根目录，而非 `app/` 目录内。
1. 记得更新任何第三方配置文件以适应新的目录结构，例如 `tailwindcss` 或 `eslint` 配置（如果需要 - `@nuxtjs/tailwindcss` 应自动正确配置 `tailwindcss`）。

::tip
你可以通过运行 `npx codemod@latest nuxt/4/file-structure` 来自动化此迁移。
::

然而，迁移_并非必需_。如果你希望保持当前的文件夹结构，Nuxt 应自动检测它。（如果无法自动检测，请提交问题报告。）唯一的例外是如果你已经拥有自定义的 `srcDir`。在这种情况下，请注意 `modules/`、`public/`、`shared/` 和 `server/` 文件夹将从你的 `rootDir` 而不是自定义 `srcDir` 中解析。如果需要，可以通过配置 `dir.modules`、`dir.public` 和 `serverDir` 来覆盖此行为。

你也可以通过以下配置强制使用 v3 目录结构：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  // This reverts the new srcDir default from `app` back to your root directory
  srcDir: '.',
  // This specifies the directory prefix for `router.options.ts` and `spa-loading-template.html`
  dir: {
    app: 'app',
  },
})
```

### 单例数据获取层

🚦 **影响程度**：中等

#### 变更内容

Nuxt 的数据获取系统（`useAsyncData` 和 `useFetch`）已进行重大重组，以提高性能和一致性：

1. **相同键的共享引用**：现在所有使用相同键的 `useAsyncData` 或 `useFetch` 调用都会共享相同的 `data`、`error` 和 `status` 引用。这意味着所有具有明确键的调用必须避免存在冲突的 `deep`、`transform`、`pick`、`getCachedData` 或 `default` 选项。

2. **对 `getCachedData` 的更多控制**：现在每次获取数据时都会调用 `getCachedData` 函数，即使这是由观察器或调用 `refreshNuxtData` 引起的。（之前，新数据总是被获取，在这种情况下不会调用此函数。）为了更灵活地控制何时使用缓存数据以及何时重新获取数据，该函数现在会接收一个包含请求原因的上下文对象。

3. **响应式键支持**：现在可以使用计算引用、普通引用或 getter 函数作为键，从而实现自动数据重新获取（并单独存储数据）。

4. **数据清理**：当最后一个使用 `useAsyncData` 获取数据的组件被卸载时，Nuxt 会移除该数据以避免内存不断增加。

#### 变更原因

这些变更旨在改善内存使用情况，并增强 `useAsyncData` 调用中的加载状态一致性。

#### 迁移步骤

1. **检查选项不一致的情况**：审查任何使用相同键但选项或获取函数不同的组件。

   ```ts
   // This will now trigger a warning
   const { data: users1 } = useAsyncData('users', () => $fetch('/api/users'), { deep: false })
   const { data: users2 } = useAsyncData('users', () => $fetch('/api/users'), { deep: true })
   ```

   将所有使用明确键且具有自定义选项的 `useAsyncData` 调用提取到各自的组合式函数中可能更有益：

   ```ts [app/composables/useUserData.ts]
   export function useUserData (userId: string) {
     return useAsyncData(
       `user-${userId}`,
       () => fetchUser(userId),
       {
         deep: true,
         transform: user => ({ ...user, lastAccessed: new Date() }),
       },
     )
   }
   ```

2. **更新 `getCachedData` 实现**：

   ```diff
   useAsyncData('key', fetchFunction, {
   -  getCachedData: (key, nuxtApp) => {
   -    return cachedData[key]
   -  }
   +  getCachedData: (key, nuxtApp, ctx) => {
   +    // ctx.cause - can be 'initial' | 'refresh:hook' | 'refresh:manual' | 'watch'
   +    
   +    // Example: Don't use cache on manual refresh
   +    if (ctx.cause === 'refresh:manual') return undefined
   +    
   +    return cachedData[key]
   +  }
   })
   ```

或者，目前可以通过以下方式禁用此行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    granularCachedData: false,
    purgeCachedData: false,
  },
})
```

### 修正了层的模块加载顺序

🚦 **影响级别**：最小

#### 发生了什么变化

使用 [Nuxt layers](/docs/guide/going-further/layers) 时模块的加载顺序已得到修正。之前，项目根目录的模块会在扩展层的模块之前加载，这与预期行为相反。

现在模块的加载顺序如下：

1. **先加载层模块**（按扩展顺序 - 深度层优先）
2. **最后加载项目模块**（最高优先级）

这影响以下两者：
- 在 `nuxt.config.ts` 中的 `modules` 数组中定义的模块
- `modules/` 目录中自动发现的模块

#### 变更原因

此变更确保：
- 扩展层比消费项目具有更低的优先级
- 模块执行顺序符合直观的层继承模式
- 在多层设置中，模块配置和钩子功能正常运作

#### 迁移步骤

**大多数项目不需要进行变更**，因为此变更仅调整了加载顺序以符合预期行为。

然而，如果您的项目依赖于之前错误的顺序，您可能需要：

1. **审查模块依赖关系**：检查是否有模块依赖于特定的加载顺序
2. **调整模块配置**：如果模块被配置为适应错误的顺序
3. **彻底测试**：确保所有功能在修正后的顺序下都能正常运作

正确顺序的示例：
```ts
// Layer: my-layer/nuxt.config.ts
export default defineNuxtConfig({
  modules: ['layer-module-1', 'layer-module-2'],
})

// Project: nuxt.config.ts
export default defineNuxtConfig({
  extends: ['./my-layer'],
  modules: ['project-module-1', 'project-module-2'],
})

// Loading order (corrected):
// 1. layer-module-1
// 2. layer-module-2
// 3. project-module-1 (can override layer modules)
// 4. project-module-2 (can override layer modules)
```

如果您由于需要注册钩子而遇到模块顺序依赖问题，可以考虑对需要调用钩子的模块使用 [`modules:done` 钩子](/docs/guide/modules/recipes-advanced)。该钩子在所有其他模块加载完成后执行，因此使用它是安全的。

👉 请查看 [PR #31507](https://github.com/nuxt/nuxt/pull/31507) 和 [issue #25719](https://github.com/nuxt/nuxt/issues/25719) 以了解更多细节。

### 路由元数据去重

🚦 **影响程度**：轻微

#### 变更内容

可以使用 `definePageMeta` 设置部分路由元数据，例如 `name`、`path` 等。以前这些参数同时存在于路由和路由元数据中（例如，`route.name` 和 `route.meta.name`）。

现在，这些参数仅可在路由对象上访问。

#### 变更原因

这是通过默认启用 `experimental.scanPageMeta` 导致的，属于性能优化。

#### 迁移步骤

迁移过程应该很简单：

```diff
  const route = useRoute()
  
- console.log(route.meta.name)
+ console.log(route.name)
```

### 标准化组件名称

🚦 **影响程度**：中等

Vue 现在将生成符合 Nuxt 组件命名模式的组件名称。

#### 变更内容

默认情况下，如果您没有手动设置，Vue 会分配一个与
组件文件名相同的组件名称。

```bash [Directory structure]
├─ components/
├─── SomeFolder/
├───── MyComponent.vue
```

在这种情况下，从 Vue 的角度来看，组件名称将是 `MyComponent`。如果您想在其上使用 `<KeepAlive>` 或在 Vue DevTools 中识别它，则需要使用此名称。

但是为了自动导入它，你需要使用 `SomeFolderMyComponent`。

通过这一修改，这两个值将保持一致，Vue 将生成符合 Nuxt 组件命名模式的组件名称。

#### 迁移步骤

确保你在使用 `@vue/test-utils` 的 `findComponent` 的任何测试中，以及依赖组件名称的任何 `<KeepAlive>` 中，都使用更新后的名称。

或者，目前你可以通过以下方式禁用此行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizeComponentNames: false,
  },
})
```

### Unhead v2

🚦 **影响级别**：最小

#### 变更内容

曾经用于生成 `<head>` 标签的 [Unhead](https://unhead.unjs.io/) 已更新至版本 2。虽然大部分功能兼容，但包含了一些破坏性变更。
针对较低级别的 API。

- 删除了属性：`vmid`、`hid`、`children`、`body`。
- Promise 输入不再支持。
- 标签现在默认使用 Capo.js 进行排序。

#### 迁移步骤

上述变更应该对你的应用影响很小。

如果你遇到问题，应验证：

- 你没有使用任何被删除的属性。

```diff
useHead({
  meta: [{ 
    name: 'description', 
    // meta tags don't need a vmid, or a key    
-   vmid: 'description' 
-   hid: 'description'
  }]
})
```

- 如果你正在使用 [Template Params](https://unhead.unjs.io/docs/head/guides/plugins/template-params) 或 [Alias Tag Sorting](https://unhead.unjs.io/docs/head/guides/plugins/alias-sorting)，你现在需要明确启用这些功能。

```ts
import { AliasSortingPlugin, TemplateParamsPlugin } from '@unhead/vue/plugins'

export default defineNuxtPlugin({
  setup () {
    const unhead = injectHead()
    unhead.use(TemplateParamsPlugin)
    unhead.use(AliasSortingPlugin)
  },
})
```

虽然不是必需的，但建议将从 `@unhead/vue` 的导入更新为 `#imports` 或 `nuxt/app`。

```diff
-import { useHead } from '@unhead/vue'
+import { useHead } from '#imports'
```

如果你仍然遇到问题，可以通过启用 `head.legacy` 配置来恢复 v1 的行为。

```ts
export default defineNuxtConfig({
  unhead: {
    legacy: true,
  },
})
```

### SPA 加载屏幕的新 DOM 位置

🚦 **影响级别**：最小

#### 变更内容

当渲染仅客户端使用的页面（设置 `ssr: false`）时，我们可以在 Nuxt 应用根目录中可选地渲染一个加载屏幕（来自 `~/app/spa-loading-template.html` - 注意在 Nuxt 4 中这也变成了 `~/spa-loading-template.html`）：

```html
<div id="__nuxt">
  <!-- spa loading template -->
</div>
```

现在，我们默认在 Nuxt 应用根目录旁边渲染模板：

```html
<div id="__nuxt"></div>
<!-- spa loading template -->
```

#### 变更原因

这允许 spa 加载模板留在 DOM 中，直到 Vue 应用等待状态解决，从而避免出现白色闪烁。

#### 迁移步骤

如果你使用 CSS 或 `document.queryElement` 来定位 spa 加载模板，你需要更新你的选择器。为此，你可以使用新的 `app.spaLoaderTag` 和 `app.spaLoaderAttrs` 配置选项。

或者，您可以通过以下方式恢复之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    spaLoadingTemplateLocation: 'within',
  },
})
```

### 解析 `error.data`

🚦 **影响级别**：轻微

曾经可以抛出包含 `data` 属性的错误，但当时并未被解析。现在，该属性已被解析并出现在 `error` 对象中。虽然这是一个修复，但如果您依赖之前的行为并手动解析，则属于技术上的破坏性变更。

#### 迁移步骤

请更新您的自定义 `error.vue` 文件，移除对 `error.data` 的任何额外解析：

```diff
  <script setup lang="ts">
  import type { NuxtError } from '#app'

  const props = defineProps({
    error: Object as () => NuxtError
  })

- const data = JSON.parse(error.data)
+ const data = error.data
  </script>
```

### 更细粒度的内联样式

🚦 **影响级别**：中等

现在 Nuxt 仅对 Vue 组件进行内联样式处理，而不包含全局 CSS。

#### 发生了什么变化

以前，Nuxt 会内联所有 CSS，包括全局样式，并移除 `<link>` 元素以将 CSS 分离到单独的文件。现在，Nuxt 仅对 Vue 组件进行此操作（这些组件之前会产生独立的 CSS 块）。我们认为这更好地平衡了减少独立网络请求的需求（就像以前一样，首次加载时不会针对每个 `.css` 文件或每个组件产生独立请求），同时允许对单个全局 CSS 文件进行缓存，并减小初始请求的文档下载大小。

#### 迁移步骤

此功能完全可配置，您可以通过设置 `inlineStyles: true` 来恢复之前的行为，此时全局 CSS 以及每个组件的 CSS 都会被内联。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  features: {
    inlineStyles: true,
  },
})
```

### 在解析后扫描页面元数据

🚦 **影响级别**：轻微

#### 发生了什么变化

我们现在在调用 `pages:extend` 钩子之后而不是之前，扫描页面元数据（定义在 `definePageMeta` 中）。

#### 变更原因

这样做是为了允许扫描用户希望在 `pages:extend` 中添加的页面元数据。我们仍然提供在新的 `pages:resolved` 钩子中更改或覆盖页面元数据的机会。

#### 迁移步骤

如果您想覆盖页面元数据，应在 `pages:resolved` 中执行，而不是在 `pages:extend` 中。

```diff
  export default defineNuxtConfig({
    hooks: {
-     'pages:extend'(pages) {
+     'pages:resolved'(pages) {
        const myPage = pages.find(page => page.path === '/')
        myPage.meta ||= {}
        myPage.meta.layout = 'overridden-layout'
      }
    }
  })
```

或者，您可以通过以下方式恢复之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    scanPageMeta: true,
  },
})
```

### 共享预渲染数据

🚦 **影响级别**：中等

#### 发生了什么变化

我们启用了之前的一项实验性功能，允许在不同页面之间共享来自 `useAsyncData` 和 `useFetch` 调用的数据。请参阅 [原始 PR](https://github.com/nuxt/nuxt/pull/24894)。

#### 变更原因

此功能自动在预渲染的页面之间共享 `_data` 载荷。当预渲染使用 `useAsyncData` 或 `useFetch` 的网站并在不同页面获取相同数据时，这可以显著提升性能。

例如，如果您的网站每个页面都需要调用 `useFetch` 函数（例如获取菜单导航数据或从 CMS 获取网站设置），这些数据将在预渲染第一个使用它的页面时仅获取一次，然后被缓存以用于预渲染其他页面。

#### 迁移步骤

确保您数据的任何唯一键都能解析为相同的数据。例如，如果您使用 `useAsyncData` 获取与特定页面相关的数据，应提供一个能唯一匹配该数据的键。（`useFetch` 会自动完成此操作。）

```ts [app/pages/test/[slug\\].vue]
// This would be unsafe in a dynamic page (e.g. `[slug].vue`) because the route slug makes a difference
// to the data fetched, but Nuxt can't know that because it's not reflected in the key.
const route = useRoute()
const { data } = await useAsyncData(async () => {
  return await $fetch(`/api/my-page/${route.params.slug}`)
})
// Instead, you should use a key that uniquely identifies the data fetched.
const { data } = await useAsyncData(route.params.slug, async () => {
  return await $fetch(`/api/my-page/${route.params.slug}`)
})
```

或者，您可以禁用此功能：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    sharedPrerenderData: false,
  },
})
```

### `useAsyncData` 和 `useFetch` 中的默认 `data` 和 `error` 值

🚦 **影响级别**：最小

#### 变更内容

从 `useAsyncData` 返回的 `data` 和 `error` 对象现在默认为 `undefined`。

#### 变更原因

之前 `data` 被初始化为 `null`，但在 `clearNuxtData` 中重置为 `undefined`。`error` 则被初始化为 `null`。此次变更是为了提高一致性。

#### 迁移步骤

如果您曾经检查 `data.value` 或 `error.value` 是否为 `null`，可以将这些检查更新为检查 `undefined`。

::tip
您可以通过运行 `npx codemod@latest nuxt/4/default-data-error-value` 来自动化此步骤。
::

### 在 `useAsyncData` 和 `useFetch` 中调用 `refresh` 时，移除已弃用的 `boolean` 值用于 `dedupe` 选项

🚦 **影响级别**：最小

#### 变更内容

之前可以将 `dedupe: boolean` 传递给 `refresh`。这些是 `cancel`（`true`）和 `defer`（`false`）的别名。

```ts twoslash [app/app.vue]
// @errors: 2322
const { refresh } = await useAsyncData(() => Promise.resolve({ message: 'Hello, Nuxt!' }))

async function refreshData () {
  await refresh({ dedupe: true })
}
```

#### 变更原因

这些别名被移除，以提高清晰度。

当在 `useAsyncData` 中添加 `dedupe` 选项时出现了这个问题，我们移除了这些布尔值，因为它们是_相反的_。

`refresh({ dedupe: false })` 意味着**不取消现有请求，而是采用这个新请求**。但在 `useAsyncData` 的选项中传递 `dedupe: true` 则意味着**如果已有待处理请求，则不发起任何新请求。（参见 [PR](https://github.com/nuxt/nuxt/pull/24564#pullrequestreview-1764584361)）。**

#### 迁移步骤

迁移过程应该很简单：

```diff
  const { refresh } = await useAsyncData(async () => ({ message: 'Hello, Nuxt 3!' }))
  
  async function refreshData () {
-   await refresh({ dedupe: true })
+   await refresh({ dedupe: 'cancel' })

-   await refresh({ dedupe: false })
+   await refresh({ dedupe: 'defer' })
  }
```

::tip
您可以通过运行 `npx codemod@latest nuxt/4/deprecated-dedupe-value` 来自动化此步骤。
::

### 在 `useAsyncData` 和 `useFetch` 中清除 `data` 时尊重默认值

🚦 **影响级别**: 最小

#### 变更内容

如果您为 `useAsyncData` 提供自定义的 `default` 值，现在在调用 `clear` 或 `clearNuxtData` 时会使用该值，并且会重置为默认值，而不仅仅是取消设置。

#### 变更原因

通常用户会设置一个适当的空值，例如空数组，以避免在遍历时检查 `null`/`undefined`。在重置/清除数据时应该尊重这一设定。

### 在清除 `useState` 时尊重默认值

🚦 **影响级别**: 最小

#### 变更内容

随着 `compatibilityVersion: 5` 的引入，`clearNuxtState` 会将状态重置为初始值（由 `useState` 的 `init` 函数提供），而不是设置为 `undefined`。这使 `clearNuxtState` 的行为与 `clearNuxtData` 保持一致，后者已经重置为默认值。

#### 变更原因

当 `clearNuxtState` 将状态设置为 `undefined` 时，依赖该状态的组合式函数可能会崩溃，因为它们期望状态始终具有有效的结构（例如，在 `undefined` 上访问属性）。重置为 `init` 值可以确保状态始终具有可用的默认值。

#### 迁移步骤

如果您依赖 `clearNuxtState` 将状态设置为 `undefined`，可以显式传递 `{ reset: false }`：

```diff
- clearNuxtState('myKey')
+ clearNuxtState('myKey', { reset: false })
```

或者，您可以通过以下方式恢复之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    defaults: {
      useState: {
        resetOnClear: false,
      },
    },
  },
})
```

您也可以今天就选择这种行为，而无需设置 `compatibilityVersion: 5`：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    defaults: {
      useState: {
        resetOnClear: true,
      },
    },
  },
})
```

### `useAsyncData` 和 `useFetch` 中 `pending` 值的对齐

🚦 **影响级别**: 中等

从 `useAsyncData`、`useFetch`、`useLazyAsyncData` 和 `useLazyFetch` 返回的 `pending` 对象现在是一个计算属性，仅在 `status` 也处于待处理状态时才为 `true`。

#### 变更内容

现在，当传递 `immediate: false` 时，`pending` 将为 `false`，直到发出第一个请求。这与之前的行为不同，在之前的行为中，`pending` 始终为 `true`，直到发出第一个请求。

#### 变更原因

这使 `pending` 的含义与 `status` 属性保持一致，当请求进行中时 `status` 也处于待处理状态。

#### 迁移步骤

如果您依赖 `pending` 属性，请确保您的逻辑能够适应新的行为，即 `pending` 仅在 `status` 也处于待处理状态时为 `true`。

```diff
  <template>
-   <div v-if="!pending">
+   <div v-if="status === 'success'">
      <p>Data: {{ data }}</p>
    </div>
    <div v-else>
      <p>Loading...</p>
    </div>
  </template>
  <script setup lang="ts">
  const { data, pending, execute, status } = await useAsyncData(() => fetch('/api/data'), {
    immediate: false
  })
  onMounted(() => execute())
  </script>
```

或者，你可以暂时恢复之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    pendingWhenIdle: true,
  },
})
```

### `useAsyncData` 和 `useFetch` 中的关键行为变化

🚦 **影响级别**：中等

#### 发生了什么变化

当在 `useAsyncData` 或 `useFetch` 中使用反应式键时，Nuxt 会在键发生变化时自动重新获取数据。当设置 `immediate: false` 时，`useAsyncData` 仅在数据已首次获取后且键发生变化时才会重新获取数据。

以前，`useFetch` 的行为略有不同。它总是会在键发生变化时获取数据。

现在，`useFetch` 和 `useAsyncData` 的行为一致了——仅在数据已首次获取后且键发生变化时才会获取数据。

#### 变化的原因

这确保了 `useAsyncData` 和 `useFetch` 之间行为的一致性，并防止了意外的数据获取。如果你设置了 `immediate: false`，则必须调用 `refresh` 或 `execute`，否则 `useFetch` 或 `useAsyncData` 将永远不会获取数据。

#### 迁移步骤

这种变化通常应会改善预期行为，但如果你原本期望更改非即时 `useFetch` 的键或选项，现在则需要在首次使用时手动触发它。

```diff
  const id = ref('123')
  const { data, execute } = await useFetch('/api/test', {
    query: { id },
    immediate: false
  )
+ watch(id, () => execute(), { once: true })
```

要禁用此行为：

```ts
// Or globally in your Nuxt config
export default defineNuxtConfig({
  experimental: {
    alwaysRunFetchOnKeyChange: true,
  },
})
```

### `useAsyncData` 和 `useFetch` 中的浅层数据反应性

🚦 **影响级别**：最小

从 `useAsyncData`、`useFetch`、`useLazyAsyncData` 和 `useLazyFetch` 返回的 `data` 对象现在是一个 `shallowRef` 而不是 `ref`。

#### 发生了什么变化

当新数据被获取时，任何依赖 `data` 的内容仍然具有反应性，因为整个对象会被替换。但如果你的代码更改了该数据结构中的属性，则不会在应用中触发任何反应性。

#### 变化的原因

对于深度嵌套的对象和数组，这带来了**显著的**性能提升，因为 Vue 无需监控每个属性/数组的修改。在大多数情况下，`data` 也应该是不可变的。

#### 迁移步骤

大多数情况下不需要迁移步骤，但如果你依赖数据对象的反应性，则有两种选择：

1. 你可以针对每个组合式函数单独选择深度反应性：
   ```diff
   - const { data } = useFetch('/api/test')
   + const { data } = useFetch('/api/test', { deep: true })
   ```
1. 你可以全局更改默认行为（不推荐）：
   ```ts twoslash [nuxt.config.ts]
   export default defineNuxtConfig({
     experimental: {
       defaults: {
         useAsyncData: {
           deep: true,
         },
       },
     },
   })
   ```

::tip
如果需要，可以通过运行 `npx codemod@latest nuxt/4/shallow-function-reactivity` 来自动化此步骤。
::

### `builder:watch` 中的绝对 watch 路径

🚦 **影响级别**: 轻微

#### 变更内容

Nuxt `builder:watch` hook 现在会输出一个绝对路径，而不是相对于项目 `srcDir` 的相对路径。

#### 变更原因

这使我们能够支持位于 `srcDir` 之外的 watch 路径，并且为层结构和其他更复杂的模式提供更好的支持。

#### 迁移步骤

我们已经主动迁移了那些已知使用此 hook 的公共 Nuxt 模块。请参见 [issue #25339](https://github.com/nuxt/nuxt/issues/25339)。

然而，如果您是使用 `builder:watch` hook 的模块作者，并且希望保持向后/向前兼容性，可以使用以下代码确保在 Nuxt v3 和 Nuxt v4 中代码都能正常工作：

```diff
+ import { relative, resolve } from 'node:fs'
  // ...
  nuxt.hook('builder:watch', async (event, path) => {
+   path = relative(nuxt.options.srcDir, resolve(nuxt.options.srcDir, path))
    // ...
  })
```

::tip
您可以通过运行 `npx codemod@latest nuxt/4/absolute-watch-path` 来自动化此步骤。
::

### `window.__NUXT__` 对象的移除

#### 变更内容

在应用完成 hydration 后，我们将移除全局 `window.__NUXT__` 对象。

#### 变更原因

这为多应用模式提供了可能 ([#21635](https://github.com/nuxt/nuxt/issues/21635))，并使我们能够专注于一种访问 Nuxt 应用数据的方式——`useNuxtApp()`。

#### 迁移步骤

数据仍然可用，但可以通过 `useNuxtApp().payload` 访问：

```diff
- console.log(window.__NUXT__)
+ console.log(useNuxtApp().payload)
```

### 目录索引扫描

🚦 **影响级别**: 中等

#### 变更内容

您 `app/middleware/` 文件夹中的子文件夹也会被扫描 `index` 文件，这些文件现在也会被注册为项目中的中间件。

#### 变更原因

Nuxt 会自动扫描多个文件夹，包括 `app/middleware/` 和 `app/plugins/`。

您 `app/plugins/` 文件夹中的子文件夹会被扫描 `index` 文件，我们希望在被扫描的目录之间保持这种行为的一致性。

#### 迁移步骤

可能不需要进行迁移，但如果您希望恢复到之前的行为，可以添加一个钩子来过滤掉这些中间件：

```ts
export default defineNuxtConfig({
  hooks: {
    'app:resolve' (app) {
      app.middleware = app.middleware.filter(mw => !/\/index\.[^/]+$/.test(mw.path))
    },
  },
})
```

### 模板编译变更

🚦 **影响级别**: 轻微

#### 变更内容

以前，Nuxt 使用 `lodash/template` 来编译位于文件系统中的 `.ejs` 格式/语法的模板。

此外，我们提供了一些模板工具（`serialize`、`importName`、`importSources`），这些工具可用于这些模板中的代码生成，现在将被移除。

#### 变更原因

在 Nuxt v3 中，我们采用了带有 `getContents()` 函数的“虚拟”语法，这种语法更加灵活且性能更佳。

此外，`lodash/template` 存在一系列安全问题。这些问题实际上并不适用于 Nuxt 项目，因为该库是在构建时而非运行时由可信代码使用的。不过，这些问题仍会出现在安全审计中。另外，`lodash` 是一个庞大的依赖项，大多数项目都不使用它。

最后，直接在 Nuxt 中提供代码序列化函数并不是理想的做法。相反，我们维护诸如 [unjs/knitwork](https://github.com/unjs/knitwork) 这样的项目，这些项目可以作为你的项目的依赖项，并且可以在不升级 Nuxt 本身的情况下直接报告或解决安全问题。

#### 迁移步骤

我们已经提交了 PR 以使用 EJS 语法更新模块，但如果你需要自行操作，有三种向后/向前兼容的替代方案：

- 将字符串插值逻辑直接移入 `getContents()` 中。
- 使用自定义函数来处理替换，例如 https://github.com/nuxt-modules/color-mode/pull/240 中的方式。
- 使用 `es-toolkit/compat`（作为 lodash template 的直接替代方案）作为你的项目的依赖项，而非 Nuxt 的依赖项：

```diff
+ import { readFileSync } from 'node:fs'
+ import { template } from 'es-toolkit/compat'
  // ...
  addTemplate({
    fileName: 'appinsights-vue.js'
    options: { /* some options */ },
-   src: resolver.resolve('./runtime/plugin.ejs'),
+   getContents({ options }) {
+     const contents = readFileSync(resolver.resolve('./runtime/plugin.ejs'), 'utf-8')
+     return template(contents)({ options })
+   },
  })
```

最后，如果你使用模板工具（`serialize`、`importName`、`importSources`），可以用 `knitwork` 中的工具进行替换：

```ts
import { genDynamicImport, genImport, genSafeVariableName } from 'knitwork'

const serialize = (data: any) => JSON.stringify(data, null, 2).replace(/"\{(.+)\}"(?=,?$)/gm, r => JSON.parse(r).replace(/^\{(.*)\}$/, '$1'))

const importSources = (sources: string | string[], { lazy = false } = {}) => {
  return toArray(sources).map((src) => {
    if (lazy) {
      return `const ${genSafeVariableName(src)} = ${genDynamicImport(src, { comment: `webpackChunkName: ${JSON.stringify(src)}` })}`
    }
    return genImport(src, genSafeVariableName(src))
  }).join('\n')
}

const importName = genSafeVariableName
```

::tip
你可以通过运行 `npx codemod@latest nuxt/4/template-compilation-changes` 来自动化此步骤。
::

### 默认 TypeScript 配置变更

🚦 **影响级别**：最小

#### 发生了什么变化

`compilerOptions.noUncheckedIndexedAccess` 现在为 `true`，而非 `false`。

#### 变更原因

此变更是对之前的 [3.12 配置更新](https://github.com/nuxt/nuxt/pull/27485) 的跟进，我们在该更新中改进了默认设置，主要遵循了 [TotalTypeScript 的建议](https://www.totaltypescript.com/tsconfig-cheat-sheet)。

#### 迁移步骤

有两种方法：

1. 对你的应用进行类型检查并修复任何新出现的错误（推荐）。

2. 在 `nuxt.config.ts` 中覆盖新的默认设置：

   <!-- @case-police-ignore tsConfig -->

   ```ts
   export default defineNuxtConfig({
     typescript: {
       tsConfig: {
         compilerOptions: {
           noUncheckedIndexedAccess: false,
         },
       },
     },
   })
   ```

### TypeScript 配置拆分

🚦 **影响级别**：最小

#### 发生了什么变化

Nuxt 现在为不同的上下文生成独立的 TypeScript 配置，以提供更好的类型检查体验：

1. **新的 TypeScript 配置文件**：Nuxt 现在会生成额外的 TypeScript 配置：
   - `.nuxt/tsconfig.app.json` - 用于你的应用代码（Vue 组件、组合式函数等）
   - `.nuxt/tsconfig.server.json` - 用于你的服务器端代码（Nitro/server 目录）
   - `.nuxt/tsconfig.node.json` - 用于你的构建时代码（模块、`nuxt.config.ts` 等）
   - `.nuxt/tsconfig.shared.json` - 用于在应用和服务器上下文之间共享的代码（如类型和非环境特定的工具函数）
   - `.nuxt/tsconfig.json` - 用于向后兼容的旧版配置

2. **向后兼容性**：扩展 `.nuxt/tsconfig.json` 的现有项目将保持原有功能。

3. **可选的项目引用**：新项目或需要更好类型检查的项目可以采用 TypeScript 的项目引用功能。

4. **特定上下文的类型检查**：每个上下文现在都有适当的编译器选项以及包含/排除设置，以适配其特定环境。

5. **新的 `typescript.nodeTsConfig` 选项**：你现在可以自定义 Node.js 构建时代码的 TypeScript 配置。

#### 变更原因

此变更提供了多项优势：

1. **更好的类型安全性**：每个上下文（应用、服务器、构建时）都能通过特定环境的全局变量和 API 获得适当的类型检查。
2. **改进的 IDE 体验**：不同代码部分拥有更好的 IntelliSense 和错误报告功能。
3. **更清晰的分离**：服务器代码不会错误地建议客户端 API，反之亦然。
4. **性能提升**：具有适当作用域配置的 TypeScript 能更高效地检查代码。

例如，自动导入在 `nuxt.config.ts` 中不可用（但之前 TypeScript 并未检测到这些导入）。虽然 IDE 能够识别 `tsconfig.json` 在 `server/` 目录中暗示的独立上下文，但这并未反映在类型检查中（需要单独步骤）。

#### 迁移步骤

**无需迁移** - 现有项目将保持原有功能。

然而，为了利用改进的类型检查功能，你可以选择采用新的项目引用方式：

1. **更新你的根目录 `tsconfig.json`**，以使用项目引用：

   ::note
   如果当前的 `tsconfig.json` 包含 `"extends": "./.nuxt/tsconfig.json"` 行，请在添加引用前**删除该行**。项目引用和扩展是互斥的。
   ::

   ```json
   {
     // Remove "extends": "./.nuxt/tsconfig.json" if present
     "files": [],
     "references": [
       { "path": "./.nuxt/tsconfig.app.json" },
       { "path": "./.nuxt/tsconfig.server.json" },
       { "path": "./.nuxt/tsconfig.shared.json" },
       { "path": "./.nuxt/tsconfig.node.json" }
     ]
   }
   ```

2. **删除所有手动创建的服务器 `tsconfig.json` 文件**（如 `server/tsconfig.json`），这些文件扩展了 `.nuxt/tsconfig.server.json`。

3. **更新您的类型检查脚本**，以使用构建标志来引用项目：

   ```diff
   - "typecheck": "nuxt prepare && vue-tsc --noEmit"
   + "typecheck": "nuxt prepare && vue-tsc -b --noEmit"
   ```

4. **将所有类型增强函数移动到相应的上下文目录中**：
   - 如果您为应用上下文增强类型，请将文件移动到 `app/` 目录。
   - 如果您为服务器上下文增强类型，请将文件移动到 `server/` 目录。
   - 如果您为应用和服务器之间共享的类型增强类型，请将文件移动到 `shared/` 目录。

    ::warning
    从 `app/`、`server/` 或 `shared/` 目录之外增强类型将无法与新的项目引用设置一起使用。
    ::

5. **根据需要配置 TypeScript 选项**：
   <!-- @case-police-ignore tsConfig -->

   ```ts
   export default defineNuxtConfig({
     typescript: {
       // customize tsconfig.app.json
       tsConfig: {
         // ...
       },
       // customize tsconfig.shared.json
       sharedTsConfig: {
         // ...
       },
       // customize tsconfig.node.json
       nodeTsConfig: {
         // ...
       },
     },
     nitro: {
       typescript: {
         // customize tsconfig.server.json
         tsConfig: {
           // ...
         },
       },
     },
   })
   ```

6. **更新所有运行 TypeScript 检查的 CI/build 脚本**，以确保它们使用新的项目引用方法。

新的配置为选择该功能的项目提供更好的类型安全性和 IntelliSense，同时保留现有设置的完全向后兼容性。

### 实验性功能的移除

🚦 **影响程度**：最小

#### 发生了什么变化

四个实验性功能在 Nuxt 4 中不再可配置：

- `experimental.treeshakeClientOnly` 将变为 `true`（自 v3.0 起为默认值）
- `experimental.configSchema` 将变为 `true`（自 v3.3 起为默认值）
- `experimental.polyfillVueUseHead` 将变为 `false`（自 v3.4 起为默认值）
- `experimental.respectNoSSRHeader` 将变为 `false`（自 v3.4 起为默认值）
- `vite.devBundler` 不再可配置 - 默认将使用 `vite-node`

#### 变更原因

这些选项已经设置为当前值一段时间了，我们没有理由认为它们需要保持可配置。

#### 迁移步骤

- `polyfillVueUseHead` 可以通过 [此插件](https://github.com/nuxt/nuxt/blob/f209158352b09d1986aa320e29ff36353b91c358/packages/nuxt/src/head/runtime/plugins/vueuse-head-polyfill.ts#L10-L11) 在用户端实现

- `respectNoSSRHeader` 可以通过 [服务器中间件](https://github.com/nuxt/nuxt/blob/c660b39447f0d5b8790c0826092638d321cd6821/packages/nuxt/src/core/runtime/nitro/no-ssr.ts#L8-L9) 在用户端实现

### 顶级 `generate` 配置的移除

🚦 **影响级别**: 轻微

#### 发生了什么变化

在 Nuxt 4 中，顶级 `generate` 配置选项不再可用。这包括其所有属性：

- `generate.exclude` - 用于排除路由的预渲染
- `generate.routes` - 用于指定要预渲染的路由

#### 变更原因

顶级 `generate` 配置是 Nuxt 2 遗留的。我们已经支持 `nitro.prerender` 一段时间了，这是 Nuxt 3+ 中配置预渲染的首选方式。

#### 迁移步骤

用相应的 `nitro.prerender` 选项替换 `generate` 配置：

```diff
export default defineNuxtConfig({
- generate: {
-   exclude: ['/admin', '/private'],
-   routes: ['/sitemap.xml', '/robots.txt']
- }
+ nitro: {
+   prerender: {
+     ignore: ['/admin', '/private'],
+     routes: ['/sitemap.xml', '/robots.txt']
+   }
+ }
})
```

::read-more{to="https://nitro.build/config#prerender"}
了解更多关于 Nitro 的预渲染配置选项。
::

### 标准化页面组件名称

🚦 **影响级别**: 轻微

#### 发生了什么变化

当 `future.compatibilityVersion` 设置为 `5`（或启用 `experimental.normalizePageNames`）时，页面组件名称会与路由名称一致，而不是使用文件名。例如，`pages/foo/index.vue` 中的组件名称将为 `foo`，而不是 `index`。

#### 变更原因

以前，Vue 根据文件名来分配组件名称。这意味着多个页面如 `pages/foo/index.vue` 和 `pages/bar/index.vue` 都会具有相同的组件名称 `index`。这使得带有 `include`/`exclude` 过滤器的 `<KeepAlive>` 不可靠，并且需要手动在每个页面中添加 `defineOptions({ name: '...' })`。

#### 迁移步骤

如果您依赖当前的组件名称（例如在 `<KeepAlive>` 的 `include`/`exclude` 列表中），请将其更新为使用路由名称而非文件名。

```diff
<template>
  <NuxtPage :keepalive="{
-   include: ['index']
+   include: ['foo']
  }" />
</template>
```

要禁用此行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizePageNames: false,
  },
})
```
