Nuxt 支持多种渲染模式，包括 [通用渲染](/docs/guide/concepts/rendering#universal-rendering)、[客户端渲染](/docs/guide/concepts/rendering#client-side-rendering)，还提供 [混合渲染](/docs/guide/concepts/rendering#hybrid-rendering)，并允许在 [CDN Edge Servers](/docs/guide/concepts/rendering#edge-side-rendering) 上渲染应用。

浏览器和服务器都可以解析 JavaScript 代码，将 Vue.js 组件转换为 HTML 元素。这一步骤称为 **渲染**。Nuxt 支持 **通用** 和 **客户端** 渲染方式。这两种方法各有优缺点，我们将在后面介绍。

默认情况下，Nuxt 使用 **通用渲染** 以提供更好的用户体验、性能并优化搜索引擎索引，但您可以通过 [一行配置](/docs/api/nuxt-config#ssr) 切换渲染模式。

## 通用渲染

这一步骤类似于 PHP 或 Ruby 应用程序进行的传统 **服务器端渲染**。当浏览器请求启用了通用渲染的 URL 时，Nuxt 在服务器环境中运行 JavaScript (Vue.js) 代码，并向浏览器返回完全渲染的 HTML 页面。如果页面已提前生成，Nuxt 也可能从缓存中返回完全渲染的 HTML 页面。与客户端渲染不同，用户可以立即获得应用的全部初始内容。

当 HTML 文档下载完成后，浏览器会解析它，然后 Vue.js 控制文档的渲染。原本在服务器上运行的相同 JavaScript 代码现在在客户端（浏览器）**再次**运行，通过绑定监听器到 HTML 来实现交互性（即 **通用渲染**）。这被称为 ** hydration**。当 hydration 完成之后，页面可以拥有动态界面和页面过渡等优势。

通用渲染使 Nuxt 应用能够在保持客户端渲染优势的同时实现快速的页面加载速度。此外，由于内容已存在于 HTML 文档中，爬虫可以无需额外开销进行索引。

![Users can access the static content when the HTML document is loaded. Hydration then allows page's interactivity](/assets/docs/concepts/rendering/ssr.svg)

**什么是服务器渲染，什么是客户端渲染？**

在通用渲染模式下，询问 Vue 文件的哪些部分在服务器和/或客户端上运行是正常的。

```vue [app/app.vue]
<script setup lang="ts">
const counter = ref(0) // executes in server and client environments

const handleClick = () => {
  counter.value++ // executes only in a client environment
}
</script>

<template>
  <div>
    <p>Count: {{ counter }}</p>
    <button @click="handleClick">
      Increment
    </button>
  </div>
</template>
```

在初始请求时，由于 `counter` ref 是在 `<p>` 标签内渲染的，因此会在服务器中初始化。`handleClick` 的内容在此处从未被执行。在浏览器中的 hydration 过程中，`counter` ref 会被重新初始化。最终，`handleClick` 会与按钮绑定。因此可以合理推断 `handleClick` 的主体内容始终会在浏览器环境中运行。

[中间件](/docs/directory-structure/app/中间件)和[页面](/docs/directory-structure/app/pages)在 hydration 过程中会在服务器和客户端上运行。[插件](/docs/directory-structure/app/plugins)可以在服务器或客户端或两者上渲染。[组件](/docs/directory-structure/app/components)也可以被强制仅在客户端上运行。[组合式函数](/docs/directory-structure/app/组合式函数)和[工具库](/docs/directory-structure/app/utils)则根据它们的使用上下文来渲染。

**服务器端渲染的优势：**
- **性能**：用户可以立即访问页面内容，因为浏览器能够比 JavaScript 生成的内容更快地显示静态内容。同时，Nuxt 在 hydration 过程中保留了 Web 应用程序的互动性。
- **搜索引擎优化**：通用渲染将页面的完整 HTML 内容作为典型的服务器应用交付给浏览器。网络爬虫可以直接索引页面内容，这使得通用渲染成为快速索引任何内容的理想选择。

**服务器端渲染的缺点：**
- **开发限制**：服务器和浏览器环境提供的 API 不同，编写能在两侧无缝运行的代码可能会有些困难。幸运的是，Nuxt 提供了指导原则和特定变量来帮助确定代码在何处执行。
- **成本**：为了即时渲染页面，需要运行一个服务器。这就像传统服务器一样会产生每月的成本。然而，由于通用渲染使得浏览器在客户端导航时负责渲染，服务器调用次数大幅减少。通过利用[边缘渲染](/docs/guide/concepts/rendering#edge-side-rendering)，可以进一步降低成本。

通用渲染技术非常灵活，几乎适用于所有应用场景，尤其适合以内容为主的网站：**博客、营销网站、作品集、电子商务网站和市场平台**。

::tip
有关编写无需 hydration 匹配的 Vue 代码的更多示例，请参阅 [Vue 文档](https://vuejs.org/guide/scaling-up/ssr#hydration-mismatch)。
::

::important
当导入依赖浏览器 API 且具有副作用的库时，确保导入该库的组件仅在客户端调用。打包工具不会对包含副作用的模块导入进行摇树优化。
::

## 客户端渲染

传统的 Vue.js 应用默认在浏览器中渲染（或 **客户端**）。之后，Vue.js 会在浏览器下载并解析所有包含创建当前界面指令的 JavaScript 代码后生成 HTML 元素。

![Users have to wait for the browser to download, parse and execute the JavaScript before seeing the page's content](/assets/docs/concepts/rendering/csr.svg)

**客户端渲染的优势：**
- **开发速度**：完全在客户端进行开发时，无需担心代码的服务器兼容性，例如使用仅限浏览器的 API（如 `window` 对象）。
- **成本更低**：运行服务器会增加基础设施成本，因为需要在一个支持 JavaScript 的平台上运行。我们可以在任何包含 HTML、CSS 和 JavaScript 文件的静态服务器上托管仅客户端应用。
- **离线使用**：由于代码完全在浏览器中运行，因此在互联网不可用时仍能正常工作。

**客户端渲染的缺点：**
- **性能问题**：用户必须等待浏览器下载、解析并执行 JavaScript 文件。由于下载阶段依赖网络，而解析和执行阶段依赖设备，这可能需要一些时间，并影响用户体验。
- **搜索引擎优化问题**：通过客户端渲染交付的内容进行索引和更新所需的时间比服务器渲染的 HTML 文档更长。这与我们讨论的性能缺点有关，因为搜索引擎爬虫不会在首次尝试完全渲染界面时就索引页面。使用纯客户端渲染的内容在搜索结果页面中显示和更新所需的时间会更长。

对于不需要索引且用户频繁访问的高度交互式 **Web 应用**，客户端渲染是一个良好的选择。它可以利用浏览器缓存，在后续访问时跳过下载阶段，例如 **SaaS、后台应用或在线游戏**。

你可以在 `nuxt.config.ts` 中启用 Nuxt 的仅客户端端渲染：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  ssr: false,
})
```

::note
如果你确实使用 `ssr: false`，你还应该在 `app/spa-loading-template.html` 中放置一个 HTML 文件，用于渲染加载界面，直到应用准备就绪。
:read-more{title="SPA Loading Template" to="/docs/directory-structure/app/spa-loading-template"}
::

### 部署静态客户端渲染应用

如果你使用 `nuxt generate` 或 `nuxt build --prerender` 命令将应用部署到 [静态托管](/docs/getting-started/deployment#static-hosting) 中，那么默认情况下，Nuxt 会将每个页面作为独立的静态 HTML 文件进行渲染。

::warning
如果你使用 `nuxt generate` 或 `nuxt build --prerender` 命令对应用进行预渲染，那么你将无法使用任何服务器端点，因为输出文件夹中不会包含服务器代码。如果你需要服务器功能，请使用 `nuxt build`。
::

如果你仅使用客户端端渲染，那么这可能不是必需的。你可能只需要一个 `index.html` 文件，加上 `200.html` 和 `404.html` 的备用文件，你可以要求静态 Web 托管服务为所有请求提供这些文件。

为了实现这一点，我们可以改变路由的预渲染方式。只需在 `nuxt.config.ts` 中的 [钩子](/docs/api/advanced/hooks#nuxt-hooks-build-time) 中添加以下代码：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  hooks: {
    'prerender:routes' ({ routes }) {
      routes.clear() // Do not generate any routes (except the defaults)
    },
  },
})
```

这将生成三个文件：

- `index.html`
- `200.html`
- `404.html`

#### 什么是 `200.html` 和 `404.html`？

静态托管服务需要一个 HTML 壳用于客户端端路由和缺失路径。Nuxt 为此提供了两个 SPA 备用文件：

- **`200.html`**。当路径不匹配时，使用此文件，让客户端路由器处理 URL。
- **`404.html`**。当托管服务需要保持 404 状态并仍然加载应用时，使用此文件。

`nuxt generate` 和 `nuxt build --prerender` 会将这些文件写入 `.output/public/`。没有预渲染的普通 `nuxt build` 则不会生成这些文件。对于混合路由规则，可以在路由规则中添加备用文件，或者如果需要，则执行预渲染构建。将托管服务指向提供方期望的文件。

#### 服务器端渲染错误页面

默认情况下，`404.html` 是一个空壳，因此你的 `error.vue`（及其布局和数据）仅在客户端应用启动后才会显示。你可以改为对其进行预渲染：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    prerenderErrorPages: true,
  },
})
```

然后 Nuxt 在构建时以合成的 404 错误状态渲染 `error.vue`，并将结果写入 `404.html`，该文件会在托管服务提供的任何 URL 处自动填充。如果托管服务能够提供，可以通过传递一个 400 到 599 之间的状态码数组（`[404, 500]`）来生成额外的页面。

由于每个缺失路径都会提供一个单独的文件，错误页面不能依赖请求：如 `useRoute()`、`useRequestURL()` 以及基于当前路径获取的数据将在预渲染的 HTML 中保存构建时的值，并在 hydration 时得到修正。请将与请求相关的标记包裹在 [`<ClientOnly>`](/docs/api/components/client-only) 中，并使用 `import.meta.prerender` 跳过与请求相关的数据获取。

```vue [error.vue]
<script setup lang="ts">
import type { NuxtError } from '#app'

defineProps<{ error: NuxtError }>()

const route = useRoute()

const { data: suggestions } = await useAsyncData(
  'error-suggestions',
  () => $fetch('/api/suggestions', { query: { path: route.path } }),
  // at build time the path is `/404.html`, so fetch on the client instead
  { server: !import.meta.prerender },
)
</script>

<template>
  <div>
    <h1>{{ error.statusCode }}</h1>
    <ClientOnly>
      <p>Nothing found at {{ route.path }}</p>
    </ClientOnly>
    <ul v-if="suggestions">
      <li
        v-for="suggestion in suggestions"
        :key="suggestion"
      >
        {{ suggestion }}
      </li>
    </ul>
  </div>
</template>
```

`import_meta._prerender` 仅在页面生成时为真，因此当应用通过服务器部署时，相同的 `error.vue` 仍然会在服务器端渲染其数据。

#### 跳过客户端回退生成

在预渲染客户端渲染的应用时，Nuxt 默认会生成 `index.html`、`200.html` 和 `404.html` 文件。然而，如果您需要阻止这些文件中的任何（或所有）在构建过程中生成，可以使用 [Nitro](/docs/getting-started/prerendering#prerendergenerate-nitro-hook) 中的 `'prerender:generate'` 钩子。

```ts twoslash [nuxt.config.ts]
// @errors: 2353 7006
export default defineNuxtConfig({
  ssr: false,
  nitro: {
    hooks: {
      'prerender:generate' (route) {
        const routesToSkip = ['/index.html', '/200.html', '/404.html']
        if (routesToSkip.includes(route.route)) {
          route.skip = true
        }
      },
    },
  },
})
```

## 混合渲染

混合渲染允许使用 **Route Rules** 针对每个路由设置不同的缓存规则，并决定服务器如何响应给定 URL 的新请求。

以前，Nuxt 应用的每个路由/页面都必须使用相同的渲染模式，无论是通用模式还是客户端模式。在某些情况下，某些页面可以在构建时生成，而其他页面则应该以客户端方式渲染。例如，一个包含管理部分的内容网站，每个内容页面应主要为静态且一次性生成，但管理部分需要注册，行为更像动态应用。

Nuxt 包含路由规则和混合渲染支持。使用路由规则，您可以定义一组 nuxt 路由的规则，更改渲染模式或根据路由分配缓存策略！

Nuxt 服务器将自动注册相应的中间件，并使用 [Nitro 缓存层](https://nitro.build/guide/cache) 用缓存处理程序包裹路由。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    // Homepage pre-rendered at build time
    '/': { prerender: true },
    // Products page generated on demand, revalidates in background, cached until API response changes
    '/products': { swr: true },
    // Product pages generated on demand, revalidates in background, cached for 1 hour (3600 seconds)
    '/products/**': { swr: 3600 },
    // Blog posts page generated on demand, revalidates in background, cached on CDN for 1 hour (3600 seconds)
    '/blog': { isr: 3600 },
    // Blog post page generated on demand once until next deployment, cached on CDN
    '/blog/**': { isr: true },
    // Admin dashboard renders only on client-side
    '/admin/**': { ssr: false },
    // Add cors headers on API routes
    '/api/**': { cors: true },
    // Redirects legacy urls
    '/old-page': { redirect: '/new-page' },
    '/proxy/**': { proxy: 'https://api.example.com/**' },
  },
})
```

### 路由规则

您可以使用的不同属性如下：
- `redirect: string`{lang=ts} - 定义服务器端重定向。
- `proxy: string | object`{lang=ts} - 使用字符串目标或包含 `to` 和 H3 proxy 选项的对象将请求代理到另一个 URL。更多内容请参阅 [Nitro 的路由规则文档](https://nitro.build/guide/routing#route-rules)。
- `ssr: boolean`{lang=ts} - 禁用应用程序某些部分的服务器端渲染，使其仅在浏览器中渲染，使用 `ssr: false`
- `cors: boolean`{lang=ts} - 在 `cors: true` 时自动添加 CORS 头信息 - 你可以通过 `headers` 覆盖来自定义输出
- `headers: object`{lang=ts} - 为网站的部分区域添加特定头信息 - 例如你的资源文件
- `swr: number | boolean`{lang=ts} - 向服务器响应添加缓存头信息，并在服务器或反向代理上缓存，支持可配置的 TTL（生存时间）。Nitro 的 `node-server` 预设能够缓存完整响应。当 TTL 到期时，缓存的响应将被发送，同时页面将在后台重新生成。如果设置为 true，将添加 `stale-while-revalidate` 头信息，而不指定 MaxAge
- `isr: number | boolean`{lang=ts} - 其行为与 `swr` 相同，不同之处在于我们可以在支持此功能的平台（当前为 Netlify 或 Vercel）上将响应添加到 CDN 缓存中。如果设置为 true，内容将在下次部署前在 CDN 中保持有效
- `prerender: boolean`{lang=ts} - 在构建时预渲染路由，并将其作为静态资源包含在构建结果中
- `noScripts: boolean`{lang=ts} - 禁用网站某些部分的 Nuxt 脚本和 JS 资源提示的渲染。更多关于 [`noScripts`](/docs/guide/going-further/features#noscripts) 的信息请阅读
- `appMiddleware: string | string[] | Record<string, boolean>`{lang=ts} - 允许你定义应该或不应在 Vue 应用部分中的页面路径上运行的中间件（即不是你的 Nitro 路由）

::note
使用 `isr` 或 `swr` 的路由还会生成 `_payload.json` 文件与 HTML 一起。客户端导航会加载这些缓存的负载数据，而不是重新获取数据。更多关于 [负载提取](/docs/getting-started/prerendering#payload-extraction) 的信息请阅读
::

### 使用 `ssr: false` 时的服务器包大小

被 `ssr: false` 覆盖的路由仅会在浏览器中渲染，因此 Nuxt 会将其页面组件从服务器包中排除。当所有到达该页面的路径的规则可以在构建时解析时，都适用此规则，包括像 `pages/products/[id].vue` 这样的动态路由，以及 `/products/**` 规则下的路由。

当任何可能需要在服务器上渲染的路径指向某个页面时，该页面会被保留在服务器捆绑文件中：

- 一条更具体的规则会在客户端仅使用的规则下方重新启用 SSR（`'/admin/**': { ssr: false }`{lang=ts} 与 `'/admin/report': { ssr: true }`{lang=ts}）
- 该页面有一个别名，或者一个使用绝对路径声明的子页面，位于客户端仅使用的区域之外
- 该页面是一个父壳层，渲染一个仍由服务器渲染的子页面

这仅是一种构建时的优化；它不会改变服务器向浏览器发送的内容。

在可能的情况下，路由规则将自动应用于部署平台的原生规则，以实现最佳性能（目前支持 Netlify 和 Vercel）。

::important
请注意，使用 [`nuxt generate`](/docs/api/commands/generate) 时无法使用混合渲染。
::

## 边缘侧渲染

边缘侧渲染 (ESR) 是 Nuxt 引入的一项强大功能，它允许通过内容分发网络 (CDN) 的边缘服务器，将 Nuxt 应用渲染得更接近用户。通过利用 ESR，你可以确保更好的性能和更低的延迟，从而提供更出色的用户体验。

使用 ESR 时，渲染过程被推送到网络的“边缘”——即 CDN 的边缘服务器。请注意，ESR 更像是部署目标而非实际的渲染模式。

当发起页面请求时，数据不会直接传输到原始服务器，而是被最近的边缘服务器拦截。该服务器生成页面的 HTML 并发送回用户。这一过程减少了数据的传输距离，**降低了延迟并加快了页面加载速度**。

由于 [Nitro](https://nitro.build/) 这一支持 Nuxt 的[服务器引擎](/docs/guide/concepts/server-engine)，边缘侧渲染成为可能。它提供对 Node.js、Deno、Cloudflare Workers 等平台的跨平台支持。

目前可以利用 ESR 的平台包括：
- [Cloudflare Pages](https://pages.cloudflare.com) 使用 git 集成和 `nuxt build` 命令无需任何配置
- 使用 `nuxt build` 命令和 `NITRO_PRESET=vercel-edge` 环境变量，通过 [Vercel Cloud](https://vercel.com/home) 运行。
- 使用 `nuxt build` 命令和 `NITRO_PRESET=netlify-edge` 环境变量，通过 [Netlify Edge Functions](https://www.netlify.com/platform/#netlify-edge-functions) 运行。

请注意，当使用路由规则进行边缘端渲染时，可以使用 **Hybrid Rendering**。
