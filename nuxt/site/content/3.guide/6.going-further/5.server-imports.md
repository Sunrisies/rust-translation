可以使用不同的 [服务器构建器](/docs/guide/going-further/builders) 与 Nuxt 配合使用：Nitro 2（`nitropack`，Nuxt 3 和 4 的默认构建器）、Nitro 3（`nitro`，来自 Nuxt 5）或直接使用 Vite。

`nuxt/server` 的存在是为了提供与特定服务器运行时无关的服务器代码实用工具。它是 Nuxt 的第二个运行时接口，与 `nuxt/app`（也可访问为 `#app`）并列，后者用于在浏览器中运行的应用程序部分。

```ts [server/api/hello.ts]
import { defineEventHandler, getQuery } from 'nuxt/server'

export default defineEventHandler((event) => {
  const { name } = getQuery<{ name?: string }>(event)
  return { message: `Hello, ${name ?? 'world'}!` }
})
```

此代码可以在 `@nuxt/nitro-server` 和 `@nuxt/vite-server` 下运行，并且会在 h3 或 Nitro 主版本中持续运行，因为 Nuxt 会集中处理这些变更。

`nuxt/server` 从 Nuxt 4.6 开始提供，因此一个文件可以服务于运行 `nitropack` v2 的 Nuxt 4.6，运行 Nitro v3 的 Nuxt 5，以及未来构建器带来的任何内容。

::tip
`nuxt` 被安装在每个 Nuxt 应用程序中，因此 `nuxt/server` 无需别名处理，也无需添加依赖。从它导入的模块不需要对 h3 或 Nitro 的 peer 依赖。
::

## 类型与实用工具

| 导入 | 用途 |
|---|---|
| `defineEventHandler` | 定义请求处理器。 |
| `createError`, `isNuxtError` | 构建并识别 HTTP 错误。 |
| `getRequestURL`, `getRequestHost`, `getRequestProtocol` | 请求的 URL、主机和协议。在控制其覆盖的代理后面时，传递 `{ xForwardedHost: true, xForwardedProto: true }` 以信任这些头信息。 |
| `getRequestHeader`, `getRequestHeaders` | 读取请求头。 |
| `getRouterParam`, `getRouterParams` | 读取与请求匹配的动态片段。 |
| `getRequestIP` | 客户端 IP 地址，[在请求时信任转发头](#client-ip)。 |
| `getQuery`, `getValidatedQuery` | 读取查询字符串，可选[验证](#validation)。 |
| `readBody`, `readValidatedBody` | 读取并解析请求体，可选[验证](#validation)。 |
| `getCookie`, `parseCookies`, `setCookie`, `deleteCookie` | 读取一个或多个 Cookie，并写入 Cookie。 |
| `setResponseStatus` | 设置响应状态和原因短语。 |
| `handleCors` | 应用[CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) 头信息并响应预检请求。 |
| `sendRedirect` | 重定向请求。 |
| `serverFetch` | 在进程内获取应用的路由，路径相对于 `app.baseURL`，除非设置了 `forwardHeaders`，否则会转发 `cookie` 和 `authorization` 头。如果服务器构建器没有在进程内获取数据，则拒绝执行此操作。 |
| `useSession`, `getSession`, `updateSession`, `clearSession` | 读写[密封的会话 Cookie](#sessions)。 |
| `deriveSecret` | 从 `appSecret` 派生出的特定用途的秘密。 |
| `getRouteRules`, `matchRouteRules` | 与请求或其他路径匹配的[路由规则](/docs/guide/concepts/rendering#route-rules)。 |
| `useRuntimeConfig` | 服务器的[运行时配置](/docs/guide/going-further/runtime-config)。 |
| `useServerHooks` | 服务器的运行时钩子：如 `render:html` 这样的渲染器钩子，以及在 `NuxtServerHooks` 上声明的钩子。 |
| `useAppConfig` | 应用配置[目录结构](/docs/directory-structure/app/app-config)，作为事件传递时每次请求时的副本。 |

这些类型与工具一起导出：`RequestEvent`、`RequestEventContext`、`NuxtRequestEvent`、`EventHandler`、`AppRouteRules`、`ServerRoutes`、`CorsOptions`、`ValidateResult`、`NuxtError`、`NuxtErrorDetails`、`NuxtErrorJSON`、`NuxtErrorLike`、`Session`、`SessionConfig`、`SessionData`、`SessionEvent`、`SessionManager`、`SessionPassword` 和 `SessionUpdate`。

这些名称不会从 `nuxt/server` 自动导入。在服务器代码中，相同拼写的[自动导入](/docs/directory-structure/server)名称是 h3 自己的辅助函数，它们接收 h3 事件并在不同位置以不同方式行为（`defineEventHandler`、`handleCors`、`getRouterParams` 和 `readValidatedBody` 等），因此需从 `nuxt/server` 显式导入。包括 `defineEventHandler`：`nuxt/server` 辅助函数读取其传递给处理器的事件。

::read-more{to="/docs/getting-started/upgrade#moving-to-nuxtserver"}
将现有服务器代码迁移到 `nuxt/server`，以及其辅助函数与 h3 的区别。
::

::tip
`defineEventHandler` 保留处理器的返回类型，这是类型 [`$fetch` 和 `useFetch`](/docs/getting-started/data-fetching) 调用路由时所需的。应注释返回的值而非处理器本身。
::

## 事件

`RequestEvent` 是 `nuxt/server` 工具操作的事件，包括请求、其 URL、要发送的响应以及请求上下文。

```ts
interface RequestEvent {
  readonly req: Request
  url: URL
  readonly res: { status?: number, statusText?: string, readonly headers: Headers }
  readonly context: RequestEventContext
}
```

要设置、读取、追加或删除响应头，直接使用 `event.res.headers`：它是一个标准的 `Headers` 对象。

Nitro 还增加了更多属性，如 `event.node` 和 `event.waitUntil()`，但这四个核心属性在所有运行时中均有效，无需辅助函数。

```ts [server/api/echo.post.ts]
export default defineEventHandler(async (event) => {
  const { id } = await event.req.json()
  return { id, page: event.url.searchParams.get('page') }
})
```

`NuxtRequestEvent` 是配置构建器提供的相同请求形式，即 `@nuxt/nitro-server` 下的 `H3Event` (h3 v1)。

## 处理器

处理器文件必须默认导出 `nuxt/server` 中的 `defineEventHandler` 的结果。一个简单的函数，或包裹在 h3 `defineEventHandler` 中的函数，会接收运行时自身的事件。

处理器可以返回：

- 一个可序列化的 JSON 值，以 JSON 形式发送，同时 `event.res` 中设置状态和头信息。
- 一个 `Response`，附带其自己的状态。在 `event.res.headers` 中设置的头信息也会一同发送，且两者中的 `set-cookie` 值都会被保留。
- 一个 `ReadableStream`，作为正文流式传输。

## 验证

`readValidatedBody` 和 `getValidatedQuery` 可以接受任何 [标准模式](https://standardschema.dev)（如 Zod、Valibot、ArkType 等），或返回验证后值的函数。输入为 `true` 表示接受，为 `false` 表示拒绝。

```ts [server/api/users.post.ts]
import { defineEventHandler, readValidatedBody } from 'nuxt/server'
import { z } from 'zod'

export default defineEventHandler(async (event) => {
  const user = await readValidatedBody(event, z.object({ name: z.string() }))
  return { created: user.name }
})
```

无效的输入会被拒绝，并返回 `400` 状态码，其 `data.issues` 列表会显示失败原因。通过 `onError` 可以指定不同的错误进行拒绝。

## 客户端 IP

`getRequestIP(event)` 返回运行时为连接报告的地址，如果未报告则返回 `undefined`。默认情况下不信任转发头，因为客户端可以在一次请求中发送任意值。

在您控制的代理后面，可以传递 `{ xForwardedFor: true }` 来读取 `X-Forwarded-For` 的第一项。仅当代理覆盖该头时执行此操作：如果代理追加该头，则优先保留客户端发送的值。

## 会话

`useSession` 读取请求的会话信息，如果没有现有会话，则创建一个新的会话并存储在 Cookie 中。数据使用 [iron](https://github.com/brc-dd/iron-webcrypto) 加密，因此存储在 Cookie 中而非服务器存储中，且 Cookie 默认设置为 `httpOnly`、`secure`、`sameSite: 'lax'` 和 `path: '/'`。

```ts [server/api/visits.ts]
import { defineEventHandler, useSession } from 'nuxt/server'

export default defineEventHandler(async (event) => {
  const session = await useSession<{ visits: number }>(event)
  await session.update(data => ({ visits: (data.visits ?? 0) + 1 }))
  return { visits: session.data.visits }
})
```

如果没有设置 `password`，会话则使用从应用程序的 [`appSecret`](/docs/guide/going-further/runtime-config#application-secret) 派生的密钥进行加密，因此只需设置 `NUXT_APP_SECRET` 即可。可以设置至少 32 个字符的 `password` 以使用自定义密钥进行加密。设置 `maxAge`（以秒为单位）以过期 Cookie 和加密值，设置 `name` 以更改 Cookie 名称从 `nuxt-session` 改为其他名称，设置 `cookie` 以覆盖任何 Cookie 属性。

每次请求时，会话会被解封一次，因此 `getSession` 可以被调用到任意多的地方。`updateSession` 和 `clearSession` 是相同操作，但不包含管理器对象。

### 派生密钥

`deriveSecret(purpose)` 从 `appSecret` 中根据特定目的派生出一个密钥：32 字节，以十六进制编码形式存储，只要 `appSecret` 未改变，其稳定性就保持不变，并且每个用途都是不同的。这是会话辅助函数使用的密钥，模块也应使用它而不是自己请求密钥。将用途命名到拥有它的对象上。

```ts
import { deriveSecret } from 'nuxt/server'

const password = await deriveSecret('my-module:tokens')
```

当 `appSecret` 未设置或长度小于 32 个字符时，它会抛出 `500` 错误并命名为 `NUXT_APP_SECRET`。

::note
h3 提供了相同名称的会话辅助函数，在 `@nuxt/nitro-server` 下，这些就是自动导入的 `useSession`、`getSession`、`updateSession` 和 `clearSession` 所解析的对象，因此应直接从 `nuxt/server` 导入它们。它们是独立的实现，不可互换：h3 默认使用 `h3` cookie 名称而非 `nuxt-session`，拥有自己的配置，其中一个发出的会话不会与另一个解封。
::

::note
会话 API 是稳定的，但密封 Cookie 的格式可能在 minor 版本中发生变化：Nuxt 计划在 `iron-webcrypto` 发布基于 AES-GCM 的密封机制后采用该方式。届时，现有会话将以旧格式读取，并在下一次写入时以新格式重新密封，因此用户不会被注销。密封值不可与 h3 的 `useSession` 提供的密钥互换。
::

::warning
会话通过 Cookie 传输，因此受到浏览器的限制。尝试写入超过 4096 字节的会话会失败；请将大数据存储在服务器端，并通过 ID 从会话中引用它。
::

## 超越表面层次

`nuxt/server` 不是 h3 的重新导出，因此如果你需要 h3 和 Nitro 提供的其他功能，如服务器生命周期管理（`defineNitroPlugin` 和 `defineNitroErrorHandler`）或 Nitro 自身的运行时钩子，你需要直接导入它们。

对于需要 h3 自身辅助函数的处理器，例如 `readRawBody`、`readMultipartFormData`、`assertMethod`、`proxyRequest`、`fetchWithEvent` 或 `writeEarlyHints`，或者那些读取 `event.node` 或 `event.waitUntil()` 的处理器，应为该处理器从 `h3` 中导入 `defineEventHandler`：

```ts [server/api/upload.post.ts]
import { defineEventHandler, readMultipartFormData } from 'h3'

export default defineEventHandler(async (event) => {
  const parts = await readMultipartFormData(event)
  return { received: parts?.length ?? 0 }
})
```

Nitro 自身的 API 大多根本不接收事件：`defineCachedEventHandler()`、`useStorage()`、`useDatabase()` 以及相关任务。请从 `nitropack/runtime` 导入它们。

## 无法移植的内容

这些领域意味着需要绕过 `nuxt/server`，因为 Nuxt 无法为所有构建器提供这些功能：

- **存储。** `useStorage()` 来自 `nitropack/runtime`，其背后的驱动配置也是如此。
- **缓存。** `defineCachedEventHandler()` 和 `defineCachedFunction()` 来自 `nitropack/runtime`。对于在任意位置运行的缓存，需直接依赖缓存库。
- **服务器插件。** `defineNitroPlugin()` 来自 `nitropack/runtime`。在插件内部，`useServerHooks()` 来自 `nuxt/server`，用于注册渲染器钩子（包括 `render:html`）以及在 `NuxtServerHooks` 上声明的钩子；Nitro 自身的钩子，如 `request`、`beforeResponse` 和 `error`，来自 `nitropack/runtime` 中的 `useNitroApp().hooks`。
- **延迟处理器。** `lazyEventHandler()` 来自 `h3`。

## 仅限服务器代码

从 Vue 组件、插件或 `shared/` 目录导入 `nuxt/server` 会导致构建失败，错误提示会指向 `#app`、`#imports`、`$fetch` 和 `useFetch`。这些上下文中的类型仍然可以被解析，这也是 `$fetch` 能够知道服务器路由返回内容的原因。

`nuxt/server` 也仅能在由服务器构建器打包的代码中使用，因为构建器提供了运行时配置、应用配置、钩子以及背后的进程内 fetch 功能。在 Nuxt 进程内部运行的代码，如 `nuxt.config.ts`、模块的 `setup` 或传递给 `addDevServerHandler` 的函数，没有这些内容，因此不应在那里导入 `nuxt/server`：例如 `useRuntimeConfig()` 和 `useAppConfig()` 返回的是空对象。应阅读 `nuxt.options`，并参考 [开发服务器处理器](/docs/guide/modules/server-compatibility#dev-server-handlers) 以了解在模块中编写处理器的方法。

## 模块

从 v4.6 开始，仅从 `nuxt/server` 导入运行时的模块可以在任何服务器构建器下运行，无需版本检查，也无需依赖 h3 或 Nitro：

```ts [runtime/server/api/status.ts]
import { defineEventHandler, useRuntimeConfig } from 'nuxt/server'

export default defineEventHandler(() => ({
  version: useRuntimeConfig().myModule.version,
}))
```

::tip
在打包时将 `nuxt/server` 设为外部依赖；在 Nuxt 构建中，它会被解析为正确的服务器构建器工具。
::

支持 Nuxt 版本 <4.6> 需要额外一步操作，因为那些项目没有 `nuxt/server` 可供解析。你可以同时注册可移植文件和当前发布的文件，Nuxt 会选择应用程序能够运行的那个。
