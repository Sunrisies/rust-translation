title: 创建 Nuxt 层

Nuxt 层是一个强大的功能，你可以利用它在一个单仓库中，或从 git 仓库或 npm 包中共享和复用部分 Nuxt 应用。层的结构几乎与标准 Nuxt 应用相同，这使得它们易于编写和维护。

:read-more{to="/docs/getting-started/layers"}

一个最小的 Nuxt 层目录应包含一个 [`nuxt.config.ts`](/docs/directory-structure/nuxt-config) 文件，以表明它是一个层。

```ts [base/nuxt.config.ts]
export default defineNuxtConfig({})
```

此外，层目录中的某些其他文件将被自动扫描，并被 Nuxt 用于扩展该层的项目。

- [`app/components/*`](/docs/directory-structure/app/components)   - 扩展默认组件
- [`app/composables/*`](/docs/directory-structure/app/组合式函数)  - 扩展默认组合式函数
- [`app/layouts/*`](/docs/directory-structure/app/layouts)  - 扩展默认布局
- [`app/middleware/*`](/docs/directory-structure/app/中间件)  - 扩展默认中间件
- [`app/pages/*`](/docs/directory-structure/app/pages)        - 扩展默认页面
- [`app/plugins/*`](/docs/directory-structure/app/plugins)        - 扩展默认插件
- [`app/utils/*`](/docs/directory-structure/app/utils)   - 扩展默认工具函数
- [`app/app.config.ts`](/docs/directory-structure/app/app-config)  - 扩展默认应用配置
- [`server/*`](/docs/directory-structure/server)       - 扩展默认服务器端点和中间件
- [`nuxt.config.ts`](/docs/directory-structure/nuxt-config)- 扩展默认 Nuxt 配置

## 基本示例

::code-tree{defaultValue="nuxt.config.ts" expandAll}

  ```ts [nuxt.config.ts]
  export default defineNuxtConfig({
    extends: [
      './base',
    ],
  })
  ```

  ```vue [app/app.vue]
  <template>
    <BaseComponent />
  </template>
  ```

  ```ts [base/nuxt.config.ts]
  export default defineNuxtConfig({
    // Extending from base nuxt.config.ts!
    app: {
      head: {
        title: 'Extending Configs is Fun!',
        meta: [
          { name: 'description', content: 'I am using the extends feature in Nuxt!' },
        ],
      },
    },
  })
  ```

  ```vue [base/app/components/BaseComponent.vue]
  <template>
    <h1>Extending Components is Fun!</h1>
  </template>
  ```

::

## 层优先级

当从多个层进行扩展时，了解覆盖顺序非常重要。具有**更高优先级**的层会在定义相同文件或组件时覆盖低优先级的层。

从最高到最低的优先级顺序为：

1. **你的项目文件** - 始终具有最高优先级
2. `~~/layers` 目录中的**自动扫描层** - 按字母顺序排列（Z 的优先级高于 A）
3. **`extends` 配置中的层** - 第一个条目比第二个具有更高优先级

### 何时使用每种方式

- **`extends`** - 用于外部依赖（npm 包、远程仓库）或项目目录外的层
- **`~~/layers` 目录** - 用于项目中使用的本地层

::tip
如果您需要控制自动扫描层的顺序，可以在名称前添加数字：`~/layers/1.z-layer`, `~/layers/2.a-layer`。这样，`2.a-layer` 的优先级将高于 `1.z-layer`。
::

### 示例

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: [
    // Local layer outside the project
    '../base',
    // NPM package
    '@my-themes/awesome',
    // Remote repository
    'github:my-themes/awesome#v1',
  ],
})
```

如果您还有 `~~/layers/custom`，则优先级为：
- 项目文件（最高优先级）
- `~~/layers/custom`
- `../base`
- `@my-themes/awesome`
- `github:my-themes/awesome#v1`（最低优先级）

这意味着项目文件将覆盖所有层，而 `~~/layers/custom` 将覆盖 `extends` 中的任何内容。

## 启动模板

要开始使用，您可以使用 [nuxt/starter/layer 模板](https://github.com/nuxt/starter/tree/layer) 初始化一个层。这将创建一个基础结构供您构建。在终端中执行此命令即可开始使用：

```bash [Terminal]
npm create nuxt -- --template layer nuxt-layer
```

遵循 README 中的说明以进行下一步操作。

## 发布层

您可以通过使用远程源或 npm 包来发布和分享层。

### Git 仓库

您可以使用 git 仓库来分享您的 Nuxt 层。一些示例：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: [
    // GitHub Remote Source
    'github:username/repoName',
    // GitHub Remote Source within /base directory
    'github:username/repoName/base',
    // GitHub Remote Source from dev branch
    'github:username/repoName#dev',
    // GitHub Remote Source from v1.0.0 tag
    'github:username/repoName#v1.0.0',
    // GitLab Remote Source example
    'gitlab:username/repoName',
    // Bitbucket Remote Source example
    'bitbucket:username/repoName',
  ],
})
```

::note
我们建议将层的内容作为 npm 包发布（公开或私有，例如通过 [GitHub Packages](https://docs.github.com/en/packages/learn-github/Packages/introduction-to-github/Packages)），而不是依赖远程层。

或者，您可以直接将 [远程 git URL 作为依赖项](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#git-urls-as-dependencies) 添加。
::

::tip
如果您想扩展私有远程源，需要添加环境变量 `GIGET_AUTH=<token>` 以提供令牌。
::

::tip
如果您想从自托管的 GitHub 或 GitLab 实例扩展远程源，需要使用 `GIGET_GITHUB_URL=<url>` 或 `GIGET_GITLAB_URL=<url>` 环境变量提供其 URL，或者直接在 `nuxt.config` 中通过 [`auth` 选项](https://github.com/unjs/c12#extending-config-layer-from-remote-sources) 进行配置。
::

::warning
请注意，如果您将远程源扩展为层，则无法在 Nuxt 之外访问其依赖项。例如，如果远程层依赖于 eslint 插件，则无法在您的 eslint 配置中使用。这是因为这些依赖项位于特殊位置（`node_modules/.c12/layer_name/node_modules/`），无法被您的包管理器访问。
::

::note
当使用 git remote sources 时，如果某个层有 npm 依赖项且您希望安装它们，可以在该层的选项中指定 `install: true` 来安装。

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: [
    ['github:username/repoName', { install: true }],
  ],
})
```
::

### npm 包

您可以将 Nuxt 层作为 npm 包发布，该包包含您想要扩展的文件和依赖项。这允许您与他人共享配置，在多个项目中使用它，或私下使用它。

要从 npm 包进行扩展，您需要确保该模块已发布到 npm 中，并作为 devDependency 安装到用户项目中。然后可以使用模块名称来扩展当前的 nuxt 配置：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: [
    // Node Module with scope
    '@scope/moduleName',
    // or just the module name
    'moduleName',
  ],
})
```

要将层目录作为 npm 包发布，您需要确保 `package.json` 中填写了正确的属性。这样就能确保在发布包时包含这些文件。

```json [package.json]
{
  "name": "my-theme",
  "version": "1.0.0",
  "type": "module",
  "main": "./nuxt.config.ts",
  "dependencies": {},
  "devDependencies": {
    "nuxt": "^3.0.0"
  }
}
```

::important
确保层中导入的任何依赖项都**明确添加到** `dependencies` 中。`nuxt` 依赖项以及仅在发布前用于测试层的任何内容，应保留在 `devDependencies` 字段中。
::

现在您可以继续将模块发布到 npm，无论是公开还是私下。

::important
当将层作为私有的 npm 包发布时，您需要确保登录并使用 npm 认证以下载 node 模块。
::

## 提示

### 命名层别名

自动扫描的层（来自 `~~/layers` 目录）会自动创建别名。例如，您可以通过 `#layers/test` 访问 `~~/layers/test` 层。

如果您想为其他层创建命名层别名，可以在层的配置中指定名称。

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  $meta: {
    name: 'example',
  },
})
```

这将生成 `#layers/example` 的别名，指向您的层。

### 相对路径和别名

当在层组件和组合式函数中使用全局别名（如 `~/` 和 `@/`）时，请注意这些别名是相对于用户项目路径解析的。作为替代方案，您可以使用**相对路径**来导入它们，或使用命名层别名。

同样，当在层的 `nuxt.config` 文件中使用相对路径时（嵌套 `extends` 除外），它们是相对于用户项目而非层解析的。作为替代方案，请在 `nuxt.config` 中使用完全解析的路径：

```ts [nuxt.config.ts]
import { fileURLToPath } from 'node:url'
import { dirname, join } from 'node:path'

const currentDir = dirname(fileURLToPath(import.meta.url))

export default defineNuxtConfig({
  css: [
    join(currentDir, './app/assets/main.css'),
  ],
})
```

## 禁用层中的模块 :badge[v4.3]{color="info" size="xs" class="align-middle"}

在扩展层时，你可能希望禁用该层中包含的某些模块。你可以通过在 Nuxt 配置中将模块的 config 键设置为 `false` 来实现这一点。

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['./base-layer'],
  // Disable modules from the layer by setting their config key to false
  image: false, // Disables @nuxt/image
  pinia: false, // Disables @pinia/nuxt
})
```

::note
config 键由每个模块定义。常见的例子包括 `@nuxt/image` 的 `image`，`@pinia/nuxt` 的 `pinia`，以及 `@nuxt/content` 的 `content`。请查阅该模块的文档以了解其具体的 config 键。
::

这在以下情况下非常有用：
- 某个层包含你在项目中不需要的模块
- 你希望使用与层提供的实现不同的实现方式
- 你需要在特定环境中禁用分析或其他模块

::tip
你也可以使用这种方法在自己的项目中禁用模块——不仅仅是来自层的模块。将模块的 config 键设置为 `false` 可以阻止其设置函数的运行，同时仍会为该模块生成类型。
::

## Nuxt 模块的多层支持

你可以使用 Nuxt Kit 的 [`getLayerDirectories`](/docs/api/kit/layers#getlayerdirectories) 工具来支持对模块进行自定义的多层处理。

```ts [modules/my-module.ts]
import { defineNuxtModule, getLayerDirectories } from 'nuxt/kit'

export default defineNuxtModule({
  setup (_options, nuxt) {
    const layerDirs = getLayerDirectories()

    for (const [index, layer] of layerDirs.entries()) {
      console.log(`Layer ${index}:`)
      console.log(`  Root: ${layer.root}`)
      console.log(`  App: ${layer.app}`)
      console.log(`  Server: ${layer.server}`)
      console.log(`  Pages: ${layer.appPages}`)
      // ... other directories
    }
  },
})
```

**注意：**
- 数组中的早期项具有更高的优先级，会覆盖后面的项
- 用户的项目是数组中的第一个项
