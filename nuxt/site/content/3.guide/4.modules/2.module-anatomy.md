Nuxt 模块有两种类型：

- 已发布的模块通过 npm 分发——你可以在 [Nuxt 网站](/modules)上看到一些社区模块的列表。
- “本地”模块存在于 Nuxt 项目中，要么[内嵌在 Nuxt 配置中](/docs/api/nuxt-config#modules-1)，要么位于 [`modules` 目录中](/docs/directory-structure/modules)。

无论哪种情况，它们的运作方式都是相同的。

## 定义你的模块

::note
使用 starter 模板时，你的模块定义位于 `src/module.ts` 文件中。
::

模块定义是模块的入口点。当你在 Nuxt 配置中引用该模块时，Nuxt 就会加载它。

从底层来看，Nuxt 模块定义是一个简单的、可能异步的函数，它接受内联用户选项和用于与 Nuxt 交互的 `nuxt` 对象。

```ts
export default function (inlineOptions, nuxt) {
  // You can do whatever you like here..
  console.log(inlineOptions.token) // `123`
  console.log(nuxt.options.dev) // `true` or `false`
  nuxt.hook('ready', (nuxt) => {
    console.log('Nuxt is ready')
  })
}
```

你可以使用 [Nuxt Kit](/docs/guide/going-further/kit)提供的高级 `defineNuxtModule` 辅助函数为该函数添加类型提示。

```ts
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule((options, nuxt) => {
  nuxt.hook('pages:extend', (pages) => {
    console.log(`Discovered ${pages.length} pages`)
  })
})
```

然而，**我们不推荐**使用这种底层函数定义方式。相反，为了定义模块，**我们建议**使用带有 `meta` 属性的对象语法来标识你的模块，尤其是在发布到 npm 时。

该辅助函数通过实现模块所需的许多常见模式，使编写 Nuxt 模块变得更加简单，同时保证未来的兼容性并提升模块作者和用户的体验。

```ts
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: {
    // Usually the npm package name of your module
    name: '@nuxtjs/example',
    // The key in `nuxt.config` that holds your module options
    configKey: 'sample',
    // Compatibility constraints
    compatibility: {
      // Semver version of supported nuxt versions
      nuxt: '>=3.0.0',
    },
  },
  // Default configuration options for your module, can also be a function returning those
  defaults: {},
  // Shorthand sugar to register Nuxt hooks
  hooks: {},
  // Configuration for other modules - this does not ensure the module runs before
  // your module, but it allows you to change the other module's configuration before it runs
  moduleDependencies: {
    'some-module': {
      // You can specify a version constraint for the module. If the user has a different
      // version installed, Nuxt will throw an error on startup.
      version: '>=2',
      // By default moduleDependencies will be added to the list of modules to be installed
      // by Nuxt unless `optional` is set.
      optional: true,
      // Any configuration that should override `nuxt.options`.
      overrides: {},
      // Any configuration that should be set. It will override module defaults but
      // will not override any configuration set in `nuxt.options`.
      defaults: {},
    },
  },
  // The function holding your module logic, it can be asynchronous
  setup (moduleOptions, nuxt) {
    // ...
  },
})
```

`defineNuxtModule` 返回一个包装函数，其底层签名为 `(inlineOptions, nuxt)`。这个包装函数在调用你的 `setup` 函数之前会应用默认设置和其他必要操作：

- 支持 `defaults` 和 `meta.configKey`，以便自动合并模块选项
- 类型提示和自动类型推断
- 使用从 `meta.name` 或 `meta.configKey` 计算出的唯一键确保模块只安装一次
- 自动注册 Nuxt 钩子
- 根据模块 meta 信息自动检查兼容性问题
- 为 Nuxt 内部使用暴露 `getOptions` 和 `getMeta` 函数
- 只要模块使用来自最新版本 `@nuxt/kit` 的 `defineNuxtModule`，就能保证向后和向上的兼容性
- 与模块构建工具集成

## 添加运行时代码

::note
使用 starter 时，运行时目录为 `src/runtime/`。
::

像 Nuxt 配置中的其他内容一样，模块不会包含在应用程序运行时中。然而，您可能希望模块提供或注入运行时代码到其安装的应用程序中。这就是运行时目录能够实现的功能。

在运行时目录中，您可以提供与 Nuxt 应用相关的任何类型的资源：
- Vue 组件
- 组合式函数
- [Nuxt 插件](/docs/directory-structure/app/plugins)

对于 [服务器引擎](/docs/guide/concepts/server-engine)，Nitro：
- API 路由
- 中间件
- Nitro 插件

或者您希望注入到用户 Nuxt 应用中的任何其他类型的资源：
- 样式表
- 3D 模型
- 图片
- 等等

然后，您可以从 [模块定义](#define-your-module) 中将所有这些资源注入到应用程序中。

::tip
更多关于资源注入的信息，请参见 [ recipes 部分](/docs/guide/modules/recipes-basics)。
::

::warning
已发布的模块无法在其运行时目录内利用自动导入功能来引入资源。相反，它们必须从 `#imports` 或类似位置显式导入这些资源。
:br :br
出于性能原因，`node_modules` 中的文件（已发布模块最终将存放的位置）不会启用自动导入功能。
::
